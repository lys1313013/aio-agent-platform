# 运行环境查询

`get_runtime_info` 是后端直接执行的只读内置工具，用于回答“智能体运行在哪台设备”“当前是 macOS 还是 Linux”“沙箱是否可用”。不需要配置设备名称、设备 ID 或新的环境变量。

## 使用

默认调用参数为 `{}`；需要资源信息时传入：

```json
{
  "include_resources": true,
  "check_sandbox": true
}
```

`include_resources` 默认 `false`，`check_sandbox` 默认 `true`。关闭 `check_sandbox` 时完全不连接 Docker。工具遵循现有智能体工具白名单和信任级别规则，不绕过 `enabled_tools`、`allowed_tools` 或渠道工具黑名单。

## 返回内容与边界

| 字段 | 内容 |
| --- | --- |
| `collected_at` | 查询时刻，包含 UTC 偏移 |
| `device` | 设备显示名称、名称来源、hostname、基于 hostname 哈希生成的标识 |
| `os` | 系统、发行版、版本、内核、CPU 架构 |
| `runtime` | 后端进程位置、Python/平台版本、PID、实例标识、工具模块初始化时间与运行时长、容器检测证据 |
| `time` | 本地时区缩写和 UTC 偏移；缩写不等于 IANA 时区名 |
| `execution` | 当前已绑定的执行租户、智能体、会话和工作区标识 |
| `resources` | 可选：逻辑 CPU 数、进程可用 CPU 数、系统负载、内存及后端工作目录所在文件系统容量 |
| `sandbox` | 可选：Docker 连接状态及当前用户、当前部署的沙箱状态 |

- macOS 优先执行固定命令 `/usr/sbin/scutil --get ComputerName` 获取电脑名称，读取失败或一秒超时后回退 hostname；Linux 直接使用 hostname。
- 设备标识是 hostname 的哈希，不是硬件 ID。hostname 修改后标识会变化，同名设备也可能相同。实例标识仅用于区分后端进程。
- 后端运行在容器内时，返回容器中的可见信息，不能可靠确定物理宿主机名称。容器标记检测是启发式判断，未检测到标记不保证未容器化。
- 信息来自智能体编排后端，不是打开网页的设备或远程 LLM 服务。Docker 可能位于另一台设备，不能据此推断沙箱与后端共用宿主机。
- 资源标注为 `backend_os_view`，可能显示宿主机容量，不代表容器配额或沙箱资源。macOS 只报告物理内存总量，未测量的可用内存返回 `null`；无法读取的资源部分返回 `unknown`。
- 执行租户只从已绑定的执行上下文读取，不查询、缓存或写回用户界面当前租户。跨用户上下文会拒绝查询。该工具不构成新的智能体执行入口。
- 返回字段使用白名单，不枚举环境变量、密钥、网络接口、硬件序列号或完整路径。

## 沙箱检查和降级启动

检查使用独立的 Docker 客户端，每个请求一秒超时，不修改执行客户端的超时。只执行连接检查及当前用户固定容器名的 inspect，校验用户、部署、临时沙箱标签后才返回容器信息；不会枚举其他用户容器、创建或启动容器、执行命令、接管容器、同步文件或刷新空闲时间。

Docker 可连接不代表代码执行成功，因此返回 `execution_verified=false`。容器不存在返回 `not_created`；Docker 不可用时仍返回设备信息及脱敏错误原因。

`SandboxManager` 连接 Docker 改为异步懒加载。启动恢复遇到 Docker 连接错误时记录 `sandbox_startup_degraded` 并启动后台维护，不终止后端；其他数据库、配置和文件归属错误仍按原规则处理。需要沙箱的操作会重试连接，仍失败则明确报错；后台维护也会按现有周期重试恢复。实际执行超时保持原值，设备查询不触发恢复或清理。

## 验证

`backend/tests/test_runtime_info.py` 覆盖自动命名、系统和资源来源、只读沙箱查询、Docker 故障、白名单、并发租户上下文、异常及取消清理。`backend/tests/test_sandbox_lifecycle.py` 覆盖离线降级启动、连接恢复、安全关闭及原有容器生命周期约束。
