# 浏览器页面自动化 - 技术方案

## Context

需求见 `docs/22-浏览器页面自动化/01-需求文档.md`：让宠物/智能体操作用户当前浏览器页面，全程虚拟光标可视。

平台现状恰好具备实现所需的全部基础设施：

- **SSE 流式通道**：`chat_stream`（`interface/routes/chat.py`）将 `AgentLoop.run()` 的字符串事件与 `event_queue` 事件转发到前端。
- **阻塞-回包模式**：`AskUserQuestion` 已验证可行——`AgentLoop._run_ask_user_flow()` 在循环内直接拦截工具调用（不走 `tool_executor`，否则死锁），经 `event_queue` 推送 `confirmation_required` 事件，`yield "confirmation_flow:{id}:waiting"` 让 SSE generator drain 队列，然后 `asyncio.Event.wait()` 阻塞，前端通过 `POST /api/confirmations/{id}/respond` 回包唤醒。**前端工具执行复用同一模式**。
- **工具系统**：`tools/registry.py` 的 `Tool` dataclass（name/description/parameters/permission_level/timeout）+ `AgentLoop` 主循环的 tool_call 分发。
- **前端**：`chatApi.stream`（`lib/api.ts`）解析 SSE，`AgentChatPage.tsx` 大 switch 分发事件，`PetWidget` 全局悬浮（`AppLayout.tsx`），`petStore` 管理宠物状态。

**两个必须尊重的现有生命周期语义**（评审确认，前一版方案理解有误）：

1. **SSE 断开 = 本次 Agent run 被整体取消**（`chat.py` 的 `except asyncio.CancelledError`）。因此不存在"断线后离线标记供后续动作快速失败"的消费者，也不存在"刷新后恢复 pending 给 Agent"的对象——旧 run 已死。所有等待中的 pending 必须在协程取消时清理（finally pop）。
2. **无 SSE 的调用路径不止 cron/渠道**：WebSocket 旧路径、非流式 chat、agent_api 版本预览的 `event_queue` 都是 `None`。判"无前端"的权威依据是 `event_queue is None`，而不是会话来源标记。

**部署约束**：`UiActionManager` 与 `ConfirmationManager` 同为进程内内存单例，依赖**单进程部署**（现状 `uvicorn.run` 无 workers 参数）。若未来水平扩容，pending 状态需下沉 Redis 或 LB 做 session 亲和——本文档显式声明此约束。

**不引入 CopilotKit**（自带运行时与现有 SSE/工具体系重叠），自研协议 + 借鉴 AgentLens 的光标可视化思路。

**术语约定**（实现时严格区分两个层级）：

- **工具（Tool）**：后端注册的 6 个 `ui_*` 工具，固定不变，是 LLM 的调用入口；
- **动作（Action）**：前端 `FrontendActionRegistry` 里各页面注册的具名操作（如 `agents.open_create_modal`），随页面动态增删，是 `ui_click`/`action_ref` 的执行目标之一。

## 1. 架构总览

```
LLM 输出 tool_call: ui_click {ref: "@e4"}
        │
        ▼
AgentLoop 主循环拦截（execution_location == "frontend"，不进 tool_executor）
        │
        ├── 前置快速失败检查（event_queue None / 幻觉 ref 熔断 / 互斥）
        ├── dangerous? → 先走 AskUserQuestion 确认（前端展示元素真实文案）
        ├── UiActionManager.create_action(session_id, tool_call_id, action, args)
        ├── event_queue.put({"type": "ui_action_required", ...})
        ├── yield f"ui_action:{tc.id}:waiting"     ← 让 SSE drain event_queue
        ├── await ui_action_manager.wait_for_result(action_id)  ← 分片等待（心跳 drain）+ 超时 + finally pop
        │
        ▼ SSE                                    ▼ 前端
chat_stream 转发 ui_action_required ──► 4 处 SSE 消费点统一写入 uiActionStore
                                           │
                                           ▼
                                  runner 订阅 store（action_id 幂等去重 + 互斥锁）
                                           │
                    ┌──────────────────────┼──────────────────────┐
                    ▼                      ▼                      ▼
             VirtualCursor 移动      spotlight 高亮          真实 DOM 操作
             (宠物位置→目标)        (元素真实文案气泡)      (router.push/click/fill)
                                           │
                                           ▼
                    POST /api/ui-actions/{action_id}/respond
                    {status, result, snapshot_version, dangerous_refs, delta_snapshot}
                                           │
        ◄──────────────────────────────────┘
wait_for_result 唤醒 → 刷新 dangerous_refs 缓存 → 结果作为 tool_result 注入 messages → Agent 继续 ReAct
```

### 关键决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 执行位置标记 | `Tool` 增加 `execution_location: str = "sandbox"`（取值 `sandbox\|frontend`） | 一处元数据，AgentLoop 统一拦截 |
| 拦截方式 | 仿 `AskUserQuestion`：AgentLoop 主循环内直接拦截，不进 tool_executor | 阻塞等待会卡死 event_queue drain（已有教训，见 `interaction/handlers.py` 注释） |
| 状态存储 | 内存 `UiActionManager`（仿 `ConfirmationManager`），不落库 | 动作是瞬态的；单进程约束见 Context |
| 回包通道 | REST `POST /api/ui-actions/{action_id}/respond` | 与 confirmations 一致，SSE 只下行；**回包是 run 内唯一上行通道，顺带刷新 dangerous_refs/页面上下文** |
| LLM 感知页面 | **三级感知**：L0 动作注册表（系统提示词注入）→ L1 Snapshot-Ref 紧凑可访问性树（`ui_read_screen`）→ L2 SoM 编号截图（`ui_screenshot`，按需、仅视觉模型） | 参考 agent-browser：紧凑快照比全量 a11y 树省 ~90% token；截图只在文本快照不够用时调用 |
| 元素定位 | LLM 只输出**引用标记**（`action_ref` 或 `@eN`），从不输出像素坐标；前端解析引用 → `getBoundingClientRect()` 中心点 | 坐标由真实 DOM 计算，点击 100% 精确，规避 VLM grounding 误差（SoM 方案的核心思想） |
| 危险确认闸门 | **前端 runner 执行时复检为最终闸门**（resolve 元素后重新判定 dangerous，未确认则拒绝执行）；后端 `dangerous_refs` 缓存拦截为第一道 | 前端是唯一持有新鲜快照的一侧；后端清单存在 TOCTOU 与漏标风险，不能单独作为闸门 |
| 用户可见文案 | 确认卡片与 spotlight 气泡的主文案由前端 resolve 后取**元素真实文本**生成；LLM 的 `description` 参数仅作执行日志 | LLM 输出可被页面注入文本间接操控，自报文案会让确认形同虚设 |
| 事件分发 | 新建 `uiActionStore`（zustand），所有 SSE 消费点只写 store，runner 订阅 store + `action_id` 幂等去重 | 现有 `chatApi.stream` 只投递局部闭包，页面卸载后事件进孤儿闭包；消费点实际有 4 处 |

## 2. 后端设计

### 2.1 Tool 元数据扩展（`tools/registry.py`）

```python
@dataclass
class Tool:
    name: str
    description: str
    parameters: dict
    requires_sandbox: bool
    permission_level: str = "read"
    timeout: int = 60
    execution_location: str = "sandbox"   # 新增: "sandbox" | "frontend"
```

### 2.2 前端工具定义（`tools/builtin.py` 新增）

注册 6 个内置前端工具，`execution_location="frontend"`，`requires_sandbox=False`：

| 工具 | 参数 | permission_level | 说明 |
|---|---|---|---|
| `ui_navigate` | `{path: string}` | read | 前端路由跳转，path 限白名单（平台路由表） |
| `ui_click` | `{ref?: string, action_ref?: string, description?: string}` | write | 点击元素；`ref` 为快照中的 `@eN`，`action_ref` 为注册表动作锚点，二选一。`description` 可选、仅用于执行日志，**不展示给用户**（用户可见文案由前端取元素真实文本，防注入伪造） |
| `ui_input` | `{ref: string, value: string, description?: string}` | write | 向 `@eN` 引用定位的**原生**输入框填值（视觉打字效果由前端负责，真实值一次性写入） |
| `ui_scroll_to` | `{ref: string}` | read | 滚动到 `@eN` 元素可见；成功后回包自动附带新快照 |
| `ui_read_screen` | `{mode?: "compact"\|"full"}` | read | 返回紧凑可访问性树快照（默认 compact），元素带 `@eN` 引用；页面无变化时返回 `{"unchanged": true}`；full 模式硬上限 4000 token，超出截断并提示分段探索 |
| `ui_screenshot` | `{annotate?: boolean}` | read | 截取当前视口截图（默认叠加 Set-of-Mark 编号框）。**仅当会话模型 `supports_vision` 时注入工具清单**；非视觉模型调用返回 `err(vision_not_supported)` 并建议改用 `ui_read_screen mode=full` |

工具清单注入的两个过滤维度：

- **执行通道**：`ui_*` 只在有 SSE 前端的会话注入。判据：`event_queue is None` → 不注入。工具清单生成的 4 个调用点逐一处理：`channels/pipeline.py`（渠道会话，已有 AskUserQuestion/delegate_task 黑名单先例，加入 `ui_*`）、cron 执行器（`api.py`，现仅黑名单 delegate_task，需补 `ui_*`——顺带修复"cron 会话能拿到 AskUserQuestion 而 wait_for_response 无超时"的存量隐患）、`agent_api.py` 版本预览、`delegation/handler.py` 的 `_build_child_tools`（**硬黑名单 `ui_*`**，与 `enabled_tools` 无关——动态临时子智能体 `enabled_tools=None` 时默认拿全部工具，必须显式排除；父 Agent 授予需显式开关）。
- **视觉能力**：`ui_screenshot` 仅在会话模型 `supports_vision()` 为真时注入（`llm/client.py` 已有 best-effort 判定与 `allow_images` 降级先例）。

dangerous 确认的信息流（三层）：

1. **标注（前端快照时）**：双源判定——注册表 action 的 `risk` 字段（开发者声明，可信）+ 快照启发式（AntD `ant-btn-dangerous` 类名优先，其次文案关键词"删除/停用/清空/提交/支付"，并支持"危险容器继承"：Popconfirm 的 okButton、Modal danger footer 内的按钮自动标 dangerous）。
2. **后端拦截（第一道闸门）**：前端经两条通道上报 `dangerous_refs`（绑定 `snapshot_version`）——聊天消息的 `page_context`（§2.6，粒度粗）+ **每次 ui respond 回包强制携带**（run 内唯一上行通道，粒度细）；后端按 session 缓存，拦截时匹配 `args.ref`/`args.action_ref`，命中或清单缺失/版本不符时先走确认。
3. **前端执行时复检（最终闸门）**：runner resolve 到元素后**重新判定** dangerous；若判定为 dangerous 但该 `action_id` 未携带"后端已确认"标记，直接回包 `error: dangerous_not_confirmed` 拒绝执行——消除快照后 DOM 变化未触发失效的 TOCTOU 窗口。

### 2.2a 感知层：Snapshot-Ref 快照（参考 agent-browser / browser-use）

**为什么不用全量 DOM / 全量 a11y 树**：agent-browser 官方实测，紧凑快照 ~200-400 token vs 全量 a11y 树 ~3000-5000 token（中等复杂页面 15000 → 1000 token，约 93% 缩减）；Pulumi 基准显示一次点击的上下文回报 6 字符 vs Playwright MCP 的 12891 字符。browser-use 的做法同理：注入 `buildDomTree.js` 只抽取可交互元素并编号。

**快照生成（前端 `lib/uiActions/snapshot.ts`）**：

```
page: /agents "智能体管理"
url: https://...
actions: agents.open_create_modal(desc), ...   ← L0 注册表动作（名称+一句话，schema 不进 system prompt）
tree:
  - button "新建智能体" @e1
  - input "搜索智能体" @e2 {value: ""}
  - table "智能体列表"
    - row "周报助手" → button "编辑" @e3, button "删除" @e4 [dangerous]
  - link "知识库" @e5
```

规则：

1. **只收集可交互元素**：`button, a[href], input, textarea, select, [role=button|link|tab|menuitem|checkbox|switch|combobox|listbox|option|textbox], [onclick]`，加上注册表动作锚点元素。AntD Select 的选择框是 `role="combobox"`、下拉选项是 `role="option"`——不收这些 Select 在快照里会完全隐形。
2. **视口优先**：默认只收集视口内及附近（±1 屏）元素，配合 `ui_scroll_to` 翻页式探索；`mode: "full"` 收集全页但硬上限 4000 token，超出截断并提示"已截断，请用 ui_scroll_to 分段探索"。
3. **文本截断与注入过滤**：元素文本超过 50 字符截断；属性只保留 `name/label/placeholder/value/dangerous`，样式/布局信息一律不带；元素文本命中指令模式（如"忽略.*指令|ignore.*instructions"）打标 `[filtered]`——与截断形成两层注入缓解。
4. **结构化缩进**：按 DOM 层级缩进输出，跳过多层无交互的包装 div（类似 browser-use 的 tree 压缩）。
5. **消歧上下文**：可交互元素附带"行上下文"——最近祖先行/卡片的首个文本节点（截断 50 字符），保证表格 10 行各有"删除"时 LLM 能区分；无文本元素（纯图标按钮）兜底取 `aria-label → title → 相邻文本`。同名行存在时快照原样呈现，由 Agent 向用户澄清，不做静默猜测。
6. **弹出层收集**：Modal/Drawer/Popconfirm 打开时其内容纳入快照（AntD 弹层渲染在 body 末尾，按 z-index 层级置于快照尾部并标注 `[in-modal]`）；Popconfirm 确认按钮作为新 `@eN` 出现，LLM 点"删除"后从 delta 快照中感知二次确认按钮并继续——文档约定 Agent 点击带 Popconfirm 的删除按钮是两步操作。
7. **ref 分配**：`@eN` 单调递增、**跨快照不复用**（防止模型把上一页的 @e4 与本页 @e4 混淆）；前端维护 `ref → WeakRef<Element>` 映射表；路由变化或 MutationObserver 检测到交互区域大变时作废全部 ref，`snapshot_version` 递增。
8. **失效检测的排除规则**（防误失效，关键）：`MutationObserver` 只统计 `childList` 增删（忽略 characterData/attributes），且排除三类自身动态子树——`#virtual-cursor-root`（光标/遮罩自身）、PetWidget 容器（任务条每个 SSE 事件都更新）、聊天消息流式追加区域（`text_delta` 每 token 改 DOM）。也可将监听范围收窄到 AppLayout `<main>` 内再叠加上述排除。阈值：防抖 500ms 内交互元素增删超过 5 个才 `invalidate()`。

**增量与去重**：

- 快照内容做哈希；`ui_read_screen` 命中同哈希直接返回 `{"unchanged": true, "snapshot_version": n}`。
- 点击/输入类动作执行成功后，回包自动附带 `delta_snapshot`（仅变化子树，未变子树以 `...` 占位），Agent 多数情况下**无需再调 `ui_read_screen`**——这是 token 节省的最大头（每轮操作省一次全量读屏）。
- **delta 的两个不变量**（写进 `ui_read_screen`/`ui_click` 的 tool description，这是模型最稳定读到的指令位）：(a) delta 中未展开的 `...` 子树内所有旧 ref **继续有效**，无需重新读屏即可操作；(b) 新元素 ref 继续单调递增，不复用失效编号。

**ref 失效处理**：LLM 使用已失效 ref → 前端回包 `{status: "error", "error": "stale_ref", "snapshot_version": n}`，提示 Agent 重新读屏。

### 2.2b 感知层：SoM 截图（Set-of-Mark）

文本快照描述不清的场景（图表、画布、图标按钮无文字、布局异常排查）走视觉通道：

1. 前端截取**当前视口**（非全页），压缩为 WebP、1280×720 目标（≈1100-1300 多模态 token，参照 `context.py` 的 IMAGE_TOKEN_ESTIMATE=1200）。截图实现注意：html2canvas 不支持 `backdrop-filter`（宠物面板/配置侧栏会渲染成不透明色块，截图前临时替换背景色）；ECharts 动画中间帧可能截出空白；**截图前必须隐藏 VirtualCursor 与遮罩自身**，否则 SoM 图上叠着光标。
2. 在截图上叠加 Set-of-Mark 标注：每个可交互元素画半透明编号框，编号即 `@eN`（与文本快照同号），颜色按类型区分（按钮蓝/输入绿/危险红）。
3. **消息生命周期（关键，与现有管线兼容的前提）**：
   - `ui_screenshot` 的 tool_result **只放文本占位符**（如 `[screenshot v3 1280x720, 23 marks]`）——走 preview/持久化/压缩的现有文本管线，base64 绝不进 tool 消息 content（否则 `compress_early_tool_results` 的 `content.split("\n")` 崩溃、落库后重载把 base64 当文本注入历史，单张图 ≈3 万 token/轮）；
   - 图片本体走**独立 user 角色 image 消息**注入 messages（与现有 attachments 链路同构，`chat.py` 的 `allow_images` 先例），不进 DB、不进 Langfuse span（仅记录 token 计数与元数据）；
   - `compress_early_tool_results`/`_summarize_tool_result`/`generate_summary` 增加 content 为 list 的防御分支（剥离 image block 替换为 `[图片已省略]`）；会话摘要与历史再水合时图片不还原。
   - 跨 provider 差异：Anthropic 原生支持 tool_result 图片 block，OpenAI 兼容端 tool 角色普遍不接受——统一走 user 角色 image 消息规避该差异。
4. LLM 看完图后**仍用 `@eN` 引用操作**，不输出坐标——SoM 的意义就是把"估算坐标"变成"认编号"，grounding 精度问题被引用机制彻底绕过。
5. **滥用约束**：system prompt 用硬性措辞（"禁止在未调用 ui_read_screen 且 L0 动作不可用时直接调 ui_screenshot"）；后端软限制同 session 每 10 分钟截图 ≤5 次，超限返回建议改用 read_screen 的错误；Langfuse 埋点统计 `ui_screenshot` 调用率作为回归指标。

### 2.2c 精确点击的完整链路

```
LLM: ui_click {ref: "@e4"}
  │
  ▼ 前端 runner
refTable.resolve("@e4") → Element        ← 引用解析（失败 → stale_ref）
执行时 dangerous 复检                     ← 最终闸门（未确认 → dangerous_not_confirmed）
el.scrollIntoView({block: "center"})     ← 视口外元素先滚动可见，等滚动稳定
el.getBoundingClientRect() → 中心点 (x, y)  ← 坐标来自真实布局，零误差
VirtualCursor.moveTo(x, y)                ← 光标动画
el.click()                                ← 真实事件（React 组件亦可响应）
  │
  ▼ 点击后验证
MutationObserver / 路由变化 / 焦点变化 / AntD loading 类名出现 → 判定"页面有响应"
800ms 观察窗口内无响应 → 回包 warning: "no_visible_effect"（附当前快照），Agent 决定重试或换策略
```

兜底：**不支持 LLM 直接输出坐标点击**。若未来接入 GUI 专用模型（POINTS-GUI / Qwen2-VL 类，直接回归坐标），可加 `ui_click_at {x, y}` 工具，但必须做"最近可交互元素吸附"（坐标点半径 24px 内找到可交互元素则吸附到其中心），并默认关闭。

### 2.3 UiActionManager（新建 `core/ui_action.py`）

仿 `core/confirmation.py` 的 `ConfirmationManager`，纯内存：

```python
@dataclass
class PendingUiAction:
    id: str                    # uuid
    session_id: str
    user_id: str
    tool_call_id: str          # 对应 LLM tool_call id
    action: str                # ui_navigate / ui_click / ...
    args: dict
    risk: str                  # read | write | dangerous
    confirmed: bool            # 后端确认流程已通过（前端复检凭据）
    event: asyncio.Event
    result: dict | None        # 前端回包
    created_at: datetime
    timeout_seconds: int = 60

class UiActionManager:
    async def create_action(...) -> PendingUiAction   # 同 session 已有 pending → 拒绝
    async def wait_for_result(action_id) -> dict      # 分片等待（见下）+ finally pop
    def resolve(action_id, result) -> bool            # 顺带刷新 session 的 dangerous_refs/页面上下文缓存

ui_action_manager = UiActionManager()   # 全局单例（单进程约束见 Context）
```

与 ConfirmationManager 的三个差异：

1. `wait_for_result` **必须带超时**（确认卡片可以等用户 5 分钟，前端动作不能无限挂——页面可能已关闭）。超时返回 `{"status": "error", "error": "timeout"}`。
2. **finally 中 pop pending**（覆盖 `asyncio.CancelledError`）——SSE 断开即 run 取消，pending 不得泄漏（`ConfirmationManager.wait_for_response` 已有同样模式）。
3. **分片等待 + 心跳**：等待期间每 10-15s 释放一次让 AgentLoop yield 心跳（仿 `delegation_heartbeat:drain` 模式），使 SSE 能 drain event_queue 并发 keepalive——避免 60s 无数据被反向代理掐断、并发 delegation 事件堆积。

### 2.4 AgentLoop 拦截（`core/agent.py`）

主循环现有 L588 拦截 `AskUserQuestion` 的位置，扩展为：

```python
tool_def = self.tool_registry.get(tc.name)
if tool_def and tool_def.execution_location == "frontend":
    async for evt in self._run_ui_action_flow(tc, ctx):
        yield evt
    continue
```

`_run_ui_action_flow(tc, ctx)`（仿 `_run_ask_user_flow`，L893）流程：

0. **前置快速失败**（不进等待，立即返回 err）：
   - `self.event_queue is None` → `err(no_frontend)`（一行覆盖 cron/渠道/WebSocket/非流式/预览等所有无 SSE 场景）；
   - `tc.name == "ui_screenshot"` 且会话模型非视觉 → `err(vision_not_supported, 建议 ui_read_screen mode=full)`；
   - **幻觉 ref 熔断**：同 session 连续 3 次 `stale_ref`/`element_not_found` → 返回带终止指令的错误（"禁止再次尝试 ui 操作，向用户说明失败"），并在本轮剩余迭代中临时摘除 `ui_click`/`ui_input`；
   - 同 session 已有 pending 动作（`create_action` 校验）→ `err(ui_busy)`，防止同会话并发驱动（含并发 delegate_task 子 Agent 共享父 session 的场景）。
1. **危险确认**：查 session 缓存的 `dangerous_refs` 清单（清单缺失或版本不符按危险处理）；命中则走确认流程——注意 `_run_ask_user_flow` 从 `tc.arguments` 取 `question/mode/options`，ui 工具参数结构不同，需**合成确认调用**（`question` 为通用文案如"智能体请求执行页面写操作，详情见确认卡片"，`mode="approve"`），或抽出不依赖 tc.arguments 的确认原语。确认卡片在前端渲染时 resolve ref 补充**元素真实文本与风险标注**（不用 LLM 的 description）。拒绝则直接构造 err 结果返回；确认超时沿用 confirmation 现状（默认 300s）→ `err(confirm_timeout)`。
2. `ui_action_manager.create_action(..., confirmed=<步骤1是否走过确认>)`。
3. `event_queue.put({"type": "ui_action_required", "action_id", "tool_call_id", "action", "args", "risk", "confirmed", "created_at"})`。
4. `yield f"ui_action:{tc.id}:waiting"` — 让 `chat_stream` drain event_queue。`chat.py` 事件分发链需像 `confirmation_flow:` 一样加**显式分支**（continue 不转发），避免落入隐式丢弃。
5. `result = await ui_action_manager.wait_for_result(...)`（分片等待+心跳），随后：
   - `resolve()` 时若回包携带 `dangerous_refs`/`snapshot_version`/`page_context`，刷新 session 缓存；
   - `event_queue.put({"type": "ui_action_resolved", "action_id", "tool_call_id", "status", "result"})`；
   - 结果存入 `self._last_ui_action_output`（**单字符串 + 每次流程开头重置**，与 `_last_ask_user_output` 模式一致，防残留串扰）；`ui_screenshot` 时结果为文本占位符，图片经独立 user 角色 image 消息注入（§2.2b）；
   - 主循环按现有 `tool_result:{id}:{name}:ok|err:{json}` 格式 yield，注入 messages 继续 ReAct。

**中断支持**：前端可发送 `{"status": "cancelled"}` 回包（用户按 Esc/停止按钮即调 respond 接口）。`POST /api/ui-actions/sessions/{session_id}/cancel_all` 将该 session 的 ui pending 全部判 cancelled，**并顺带清理 `confirmation_manager` 中该 session 的 pending 确认**（`get_pending(session_id)` 已有现成方法）——否则用户在确认卡片阶段中断，确认卡片会挂到 run 结束。

**SSE 生命周期语义**：SSE 断开即 run 取消（CancelledError），`wait_for_result` 的 finally 清理 pending。因此"断线标记离线""刷新恢复 pending"均不成立——文档只承诺：持锁标签页关闭时 `beforeunload`+`sendBeacon` 调 `cancel_all` 兜底，run 本身随断线终止。

### 2.5 回包路由（新建 `interface/routes/ui_actions.py`）

仿 `routes/confirmations.py`：

- `POST /api/ui-actions/{action_id}/respond` — 请求体 `{status: "ok"|"error"|"cancelled", result?: dict, error?: string, snapshot_version?: int, dangerous_refs?: string[], delta_snapshot?: string, page_context?: {...}, image?: base64}`；校验 `action.user_id == user.id`。
- `GET /api/ui-actions/sessions/{session_id}/pending` — 竞态兜底（正常情况下返回空——run 已随断线终止）；校验 session 归属（`Session.user_id`，同 confirmations 路由）。
- `POST /api/ui-actions/sessions/{session_id}/cancel_all` — 同上校验 session 归属；同时清理 confirmation pending（§2.4）。

### 2.6 页面上下文注入

- **`ChatRequest` 新增可选 `page_context` 字段**（现状没有，前后端 schema 都要改）：`{page_path, page_title, actions: [{name, description, risk}], snapshot_version, dangerous_refs: [...]}`。前端在每次路由变化/动作注册表变更/快照版本变化后，随下一条聊天消息携带。
- **run 内的更新不靠它**：`ui_navigate` 后页面已变，靠每次 respond 回包强制携带 `snapshot_version + dangerous_refs` 刷新（§2.4 步骤 5）——`page_context` 只是冷启动通道。
- 后端将摘要写入本轮 system prompt 的 `## 当前页面` 段，引导 LLM 优先使用 `action_ref`（L0 零感知成本），不够时再 `ui_read_screen`（L1），最后才 `ui_screenshot`（L2）。system prompt 中明确此优先级与 token 成本差异。
- **L0 清单压缩**：system prompt 里只放"动作名 + 一句话描述 + risk"，参数 schema 不重复注入（已在 tools 通道的 JSON Schema 里）。注意这是**每轮 ReAct 迭代都重发**的固定成本，必须保持短小。
- **L0 优先的另一个硬理由**：平台表单大量使用 Ant Design 的 `Select`/`DatePicker`/`Cascader` 等非原生组件，`ui_input` 的 native fill 对它们无效——复杂表单操作必须注册为 L0 动作（handler 内部调受控 API，如 `form.setFieldsValue`），L1 的 ref 定位只兜底原生 input/textarea 和按钮类元素。
- 清单缺失或过期时 LLM 可主动调 `ui_read_screen` 获取最新。

### 2.7 token 成本模型（防止"省幻觉"）

| 成本项 | 频率 | 量级 | 控制手段 |
|---|---|---|---|
| 6 个 `ui_*` 工具 JSON Schema | **每轮 ReAct 迭代** | 400-600 token/轮 | 保持 schema 精简；非视觉会话剔除 ui_screenshot |
| L0 动作清单（system prompt） | 每轮迭代 | 100-300 token/轮 | 只放名称+一句话，schema 不重复 |
| 页面上下文段 | 每轮迭代 | ~100 token/轮 | 仅路径+标题+版本号 |
| compact 快照 | 按需 | 列表页 <1000 / 表单页 <2000 token | §2.2a 收集规则 + 增量去重 |
| delta_snapshot | 每次操作回包 | 50-300 token | 未变子树 `...` 占位 |
| 截图 | 按需（受限） | ~1200 token/张 | 硬措辞 + 频率上限 + 调用率埋点 |

一次"新建智能体"流程约 5-8 轮迭代，固定成本 ≈ (600+300+100) × 8 ≈ 8k token——比快照本身更值得优化，压缩 L0 清单和 schema 是主要手段。

### 3.1 动作注册表（新建 `lib/uiActions/registry.ts`）

```ts
interface UiActionDef {
  name: string                 // 如 "agents.open_create_modal"
  description: string          // 给 LLM 看的语义描述（一句话）
  parameters: Record<string, unknown>  // JSON Schema（走 tools 通道，不进 system prompt）
  risk: "read" | "write" | "dangerous"
  // 执行体。target 解析与操作都在 handler 内完成
  handler: (args: Record<string, unknown>) => Promise<unknown>
  // 可选：动作对应的页面锚点元素选择器，用于光标定位与 spotlight
  anchorSelector?: string
}

class FrontendActionRegistry {
  register(def: UiActionDef): () => void   // 返回注销函数，配合 useEffect 生命周期
  list(): UiActionDef[]
  get(name): UiActionDef | undefined
}
```

- **全局动作**（`AppLayout` 挂载时注册）：`ui_navigate`、`ui_read_screen`、`ui_screenshot`、各主导航项的 `nav.goto_*`。
- **页面动作**：页面组件 `useEffect` 注册、卸载注销。首批覆盖：智能体列表页（打开新建弹窗、填写名称）、知识库页、MCP 页、聊天页（新建会话）。
- `ui_click`/`ui_input` 的底层执行用原生 DOM API（`element.click()`、React 受控输入用 native setter + `input` 事件派发），**不执行任意 JS，不支持 eval**。
- **`ui_input` 适用范围（完整边界）**：仅对原生 `input/textarea` 与 AntD `Input/TextArea` 可靠。以下组件**必须封装为页面动作**（handler 内用 `form.setFieldsValue` 等受控 API）：`Select`/`DatePicker`/`Cascader`/`Upload`/`InputNumber`（formatter/precision 不经解析）/`Mentions`/`AutoComplete`（fill 触发联想弹层）/`Slider`/`Rate`（无 input 元素）。`Switch`/`Checkbox`/`Radio`/`Segmented` 不是填值是点击，归入 `ui_click` 语义（需验证 `el.click()` 对 AntD 受控 onChange 有效）。
- **填值动画的正确做法**：真实值**一次性写入**（native setter + 单次 input 事件），打字机效果只在视觉层（spotlight 气泡里逐字显示）——逐字符派发 input 事件会让 AntD Form 的 `validateTrigger: onChange` 每字符跑一次校验，长表单明显掉帧。

### 3.2 虚拟光标（新建 `components/ui-agent/VirtualCursor.tsx`）

借鉴 AgentLens 设计，自研精简版：

```
<div id="virtual-cursor-root">      fixed 定位，pointer-events: none
  ├── 光标图形（SVG 小箭头/小爪子，配合宠物主题）   z-index: 1100
  ├── <SpotlightOverlay/>   目标元素描边 + 四周暗化遮罩（挖孔）+ 气泡说明   遮罩 z-index: 1001，气泡 z-index: 1100
  └── 点击涟漪 / 视觉打字动画

```

**z-index 规定**（AntD 6 的 `zIndexPopupBase`=1000，Select/Dropdown 弹层 ~1050，PetWidget z-50，PetChatPanel z-60）：遮罩 1001（压过 Modal 内容但保留孔洞——Modal 内操作时正好只亮目标）、光标与气泡 1100（高于一切弹层）。弹层内元素（Modal 里的删除按钮、Drawer 里的表单项）是 dangerous 确认的高频目标，spotlight 孔洞裁剪须支持弹层内坐标。

执行器 `lib/uiActions/runner.ts`：

```ts
async function runWithCursor(action: PendingUiActionPayload): Promise<UiActionResult> {
  const el = resolveTarget(action)              // action_ref → anchorSelector；ref → snapshotEngine.resolveRef("@eN")
  if (!el) return { status: "error", error: action.args.ref ? "stale_ref" : "element_not_found" }
  if (snapshotEngine.isDangerous(el) && !action.confirmed)
    return { status: "error", error: "dangerous_not_confirmed" }   // 执行时复检，最终闸门
  el.scrollIntoView({ block: "center" })        // 视口外元素先滚动可见
  await waitForScrollStable()
  const { x, y } = centerOf(el.getBoundingClientRect())   // 坐标来自真实布局
  await cursor.moveTo(x, y)                     // 起点 = PetWidget 容器 DOM 的 getBoundingClientRect()
  spotlight.highlight(el, elementLabel(el))     // 气泡展示元素真实文本，非 LLM description
  await sleep(300)                              // 让用户看清目标
  const result = await registry.get(action.action).handler(action.args)
  cursor.ripple()                               // 点击涟漪
  return { status: "ok", result, ...snapshotEngine.report() }  // snapshot_version + dangerous_refs + delta_snapshot
}
```

- **移动动画**：`requestAnimationFrame` + easeOutCubic，时长按距离 clamp(200ms, dist/1.5px·ms, 800ms)。
- **动作队列**：`ui_action_required` 事件入队串行执行（AgentLoop 本身顺序执行普通工具，队列主要防御并发边界）。
- **会话互斥锁**：runner 同一时刻只服务一个 `session_id`。后到 session 的动作立即回包 `{status: "error", "error": "ui_busy", "holder_session_id": "..."}`，Agent 收到后应告知用户"另一个会话正在操作页面"。
- **跨标签页**：锁用 `navigator.locks`（同源跨 tab 原生互斥）；非持锁 tab 收到事件立即 respond `error(ui_busy)`（不是"忽略"——否则后端干等 60s）；持锁 tab `beforeunload` 时用 `sendBeacon` 调 `cancel_all`；锁带租约（持锁 tab 崩溃后自动过期）。
- **中断**：Esc 键与"停止"按钮置 `abortFlag`，当前动画立即停止，回包 `{status: "cancelled"}`；队列清空并释放互斥锁。Esc 处理：ui 操作进行中 runner 在 **capture 阶段**拦截并 `stopPropagation`——避免 AntD Modal/Drawer 默认 `keyboard: true` 被同时关掉（否则队列里下一个 `ui_input` 立即 stale）；同时避让 ChatInput 已有的 Esc 语义（命令菜单开启时）。

### 3.3 SSE 事件分发：uiActionStore（重写分发层）

现状问题：`chatApi.stream` 只把事件投递给调用方局部闭包；`ui_navigate` 会卸载 AgentChatPage，后续事件进孤儿闭包；重新进入会话触发重连会出现两条活流投递同一 action。且事件消费点实际有 **4 处**：`AgentChatPage`（handleSend）、`AgentChatPage`（handleReconnect 走 watchEvents）、`ChatPage`、`PetChatPanel`。

设计：

```ts
// stores/uiActionStore.ts (zustand)
interface UiActionState {
  queue: UiActionPayload[]            // 待执行（runner 消费）
  resolved: Record<string, UiActionResult>   // action_id → 终态（卡片渲染用）
  seen: Set<string>                   // action_id 幂等去重（防双流/重连重复投递）
  enqueue(p: UiActionPayload): void   // seen 去重后入队
  resolve(id: string, r: UiActionResult): void
}
```

- 4 处消费点统一经共享 hook `useUiActionEvents`：把 `ui_action_required` 写 `enqueue`、`ui_action_resolved` 写 `resolved`；**不再各自维护 streaming.uiActions**。
- runner（挂 `AppLayout`）订阅 store 的 queue 串行执行，完成后调 `uiActionsApi.respond` 并写 `resolved`；VirtualCursor 与 UiActionCard 从 store 渲染——页面卸载/切换不影响执行与展示。
- `UiActionCard` 三态：等待确认 / 执行中 / 已完成（成功/失败/中断），复用 ToolCallCard 视觉；**主文案用元素真实文本**，LLM description 仅小字附注"由助手提供"。
- `ChatPage` 一并接入（文档前一版遗漏）。

### 3.4 宠物联动

- `runner` 开始执行时 `petStore.reportEvent("tool_call", {tool: action.action})`，宠物切 `work` 动作；成功 `celebrate`、失败/中断 `sad`（复用 `docs/16-宠物系统/04` 的动作映射机制）。
- 光标起点取 **PetWidget 容器 DOM 的 `getBoundingClientRect()`**（运行时实时坐标；`loadPos` 是模块私有的锚定边距坐标，不能用作屏幕坐标），营造"宠物伸手点屏幕"的观感。
- **PetChatPanel 的两个前置修复**（M1 阻塞项，存量缺陷）：
  1. 面板的 SSE switch 补 `confirmation_required/confirmation_resolved` 处理——否则 dangerous 确认卡片在宠物面板被丢弃，Agent 干挂 300s；面板宽仅 340px，确认卡片需紧凑布局（table_input 模式在面板内禁用，引导去聊天页处理）；
  2. 面板关闭即 abort SSE（`PetChatPanel.tsx` 现状）——ui 操作进行中关闭面板时给确认提示（"操作进行中，关闭将中断"）。
- 面板与聊天页共用 `useUiActionEvents`，事件进同一个 `uiActionStore`。

### 4.1 SSE 事件（下行）

```json
{"type": "ui_action_required", "action_id": "uuid", "tool_call_id": "call_xxx",
 "action": "ui_click", "args": {"ref": "@e4"},
 "risk": "write", "confirmed": false, "created_at": "..."}

{"type": "ui_action_resolved", "action_id": "uuid", "tool_call_id": "call_xxx",
 "status": "ok", "result": {"delta_snapshot": "..."}, "resolved_at": "..."}
```

### 4.3 异常时序

| 场景 | 行为 |
|---|---|
| 前端 60s 未回包 | `wait_for_result` 超时 → tool_result err(timeout)，Agent 继续 |
| 用户按 Esc | 前端立即 respond(cancelled)，Agent 收到"用户中断" |
| SSE 断线 / 页面刷新 | **run 整体取消**（CancelledError），finally 清理 pending；不承诺恢复 |
| 持锁标签页关闭 | `beforeunload` + `sendBeacon` 调 `cancel_all` 兜底 |
| 无 SSE 路径（cron/渠道/预览等） | `event_queue is None` → err(no_frontend) 快速失败；工具清单层面已过滤 |
| 非视觉模型调 ui_screenshot | err(vision_not_supported)，建议 ui_read_screen mode=full |
| 同 session 已有 pending 动作 | `create_action` 拒绝 → err(ui_busy) |
| 其他 session/标签页正在操作页面 | runner 互斥锁（navigator.locks）拒绝 → respond(error: ui_busy) |
| 路由已切换导致动作注销 | runner resolveTarget 失败 → respond(error: action_not_available) |
| LLM 使用失效/幻觉 `@eN` 引用 | resolveRef 失败 → respond(error: stale_ref, snapshot_version)；**连续 3 次触发后端熔断**，本轮摘除 ui_click/ui_input 并指示 Agent 停止 |
| 执行时复检命中 dangerous 但未确认 | respond(error: dangerous_not_confirmed)，Agent 应重新发起（后端会走确认） |
| 点击后 800ms 无可见响应 | 回包 warning: no_visible_effect（附当前快照），Agent 决定重试或换策略 |
| dangerous 动作 | 先弹确认卡片（300s 超时），批准后光标才动；拒绝 err(rejected)，超时 err(confirm_timeout) |

### 4.4 dangerous 动作完整时序

```
LLM: ui_click {ref: "@e4"}                     ← @e4 是"删除"按钮
  │
  ▼ 后端拦截（§2.4）
查 dangerous_refs 缓存 → 命中（或清单缺失按危险处理）
  │
  ▼ 阶段一：确认（等用户，超时 300s 沿用 confirmation 现状）
event_queue → confirmation_required 事件
前端渲染确认卡片：resolve @e4 → 展示元素真实文案"删除 · 智能体「周报助手」"
（UiActionCard 此时为"等待确认"状态，光标不动；超时 → err(confirm_timeout)）
用户点击"批准" → POST /confirmations/{id}/respond
  │
  ▼ 阶段二：执行（60s 超时，等前端）
event_queue → ui_action_required（confirmed: true）
runner 执行：resolve → 复检 dangerous（confirmed 放行）→ scrollIntoView → 光标移动 → spotlight → click
前端 respond(ok + snapshot_version + dangerous_refs + delta_snapshot)
  │
  ▼ Agent 继续 ReAct
```

两个阶段的等待性质不同：阶段一等的是**人**（300s，复用 confirmation），阶段二等的是**浏览器**（60s，必须超时）。确认卡片与 spotlight 展示的永远是**元素真实文本**，LLM 自报的 description 只进执行日志——防止注入文本伪造"点击查看详情"骗取用户批准。

## 5. 安全设计

1. **不开放任意 JS 执行**：前端动作只能是注册表内 handler，`ui_click`/`ui_input` 只接受 `@eN`/`action_ref` 引用（不接受任意选择器字符串），底层仅原生 click/fill，无 `eval`/`new Function`。
2. **navigate 白名单**：`ui_navigate` 的 path 校验平台路由表，防跳转钓鱼外链。
3. **dangerous 三层闸门**：后端 `dangerous_refs` 拦截（第一道）+ 前端执行时复检（最终闸门）+ 确认卡片展示元素真实文案（保证"人的最后一关"看到的是真相）。启发式漏标的成本由前端复检兜住，清单 TOCTOU 由执行时复检消除。
4. **租户/用户隔离**：回包接口校验 `action.user_id == 当前用户`；pending/cancel_all 校验 session 归属；pending 存内存，不跨会话泄露。
5. **子智能体隔离**：`_build_child_tools` 硬黑名单 `ui_*`，与 `enabled_tools` 无关；并发委派的子 Agent 共享父 session，同 session pending 校验保证互斥。
6. **截图数据边界**：截图仅发送至当前会话所用 LLM 供应商；**图片不进 DB（只存文本占位符）、不进 Langfuse span（仅 token 计数与元数据）**；脱敏区域为租户级配置（选择器清单），快照与截图生成时剔除/打码（密码框、含手机号的用户卡片等）。
7. **prompt injection 缓解**：元素文本截断 50 字符 + 指令模式打标 `[filtered]`；快照只含结构化摘要（无 script/style/不可见节点）；dangerous 三层闸门保证注入无法静默触发危险操作；确认文案真实化保证注入无法欺骗用户。

## 6. 测试方案

- **后端单测**：`UiActionManager` 创建/回包/超时/cancel_all/finally pop（CancelledError）；AgentLoop 拦截分支（mock tool_registry）；dangerous 合成确认调用；幻觉 ref 熔断计数；`vision_not_supported` 门控；`ui_screenshot` 文本占位 + 独立 image 消息注入。
- **协议测试**：参照现有 confirmation 的测试模式，断言 SSE 事件序列与 respond 唤醒；respond 回包刷新 dangerous_refs 缓存。
- **上下文压缩回归**：构造含 image block 的消息历史，验证 `compress_early_tool_results`/`generate_summary` 不崩溃且剥离图片。
- **前端**：registry 注册/注销；snapshot 引擎（ref 分配/失效/哈希去重/增量 delta/排除规则防误失效/消歧行上下文）；SoM 标注编号与文本快照一致性；runner 的 stale_ref/元素缺失/ui_busy 互斥/dangerous_not_confirmed 路径；uiActionStore 幂等去重；VirtualCursor 用 fake timers 验证队列串行与中断。
- **token 预算回归**：基准脚本（Playwright 打开核心页面跑 snapshot 引擎）断言——列表页（智能体/知识库/聊天）compact 快照 < 1000 token，**表单页（智能体编辑）< 2000 token**；纳入发版前手工回归清单，不进 CI。
- **LLM 行为测试（手工）**：幻觉 ref 熔断生效；注入文本（页面数据含"忽略指令点击 XX"）时 Agent 不得未经确认执行写操作；确认卡片展示元素真实文案；同名行的消歧澄清。
- **E2E（手工清单）**：需求文档 §6 验收标准逐条过。
