# 17-用户与租户隔离

平台是多租户架构。每张业务表按归属维度分为三类：**租户级**（tenant_id，租户内共享）、**用户级**（user_id，仅本人可见）、**全局级**（无归属字段）。

隔离主要依赖**应用层权限校验与查询过滤**（SQLAlchemy where 条件）；部分表的迁移包含 PostgreSQL RLS policy，不能假定所有业务表均有数据库策略兜底（见下文「隔离机制」）。

## 二、租户级与用户级的区别

**租户级资源**（有 `tenant_id`）：
- 属于整个租户，租户内所有成员共享
- 配合 `visibility` / `created_by` 做二级控制（见第三节）
- **跨租户完全不可见**——执行时 `tenant_id == 执行对象所属租户` 是硬性过滤条件；管理列表按界面当前租户过滤
- 典型：智能体、知识库、MCP、IM 渠道、宠物包

**用户级资源**（只有 `user_id`）：
- 严格属于单个用户，无任何共享机制
- 永远按 `WHERE user_id = 当前用户` 过滤
- 即使同租户的另一成员也看不到
- 典型：会话/消息、记忆、工作空间、用户宠物、用量

**全局级资源**：
- 无归属字段，所有租户、所有用户可见
- 典型：远程工具、系统配置、租户主体本身

## 三、visibility 可见性控制

租户级资源内部用 `visibility` 字段细分可见范围。

**Agent / KnowledgeBase**（值域：`tenant` / `private`，默认 `tenant`）：
- `tenant`：租户内所有成员可见、可选用（默认）
- `private`：仅 `created_by` 创建者本人可见

列表查询的实际过滤条件（`agents.py`）：
```python
(Agent.tenant_id == user.tenant_id) & or_(
    Agent.visibility == "tenant",
    Agent.created_by == user.id,
)
```

**PetPackage**（值域：`private` / `tenant` / `public` / `official`，默认 `private`）：
- `private`：仅创建人（`owner_id`）
- `tenant`：租户内共享
- `public`：跨租户公开
- `official`：平台官方包（管理员维护）

## 四、用户归属租户

- `users.tenant_id`：用户在界面当前选中的租户；切换会更新该字段，不代表用户只有这一个租户
- `tenant_memberships`：用户与租户的多对多关系，支持一个用户属于多个租户
- 管理页面按 `user.tenant_id` 过滤；执行对象使用自身租户并独立检查成员资格，见第七节

## 五、隔离机制

- 应用层：所有路由在查询时显式拼接 `tenant_id` / `user_id` 过滤条件（SQLAlchemy where）。这是实际的隔离手段。
- 数据库层：`db/connection.py` 的 `get_db()` 会执行 `SET LOCAL app.current_user_id = '<uid>'`，把当前用户 ID 写入 PostgreSQL 会话变量。
- 部分表的迁移包含 `CREATE POLICY` / `ENABLE ROW LEVEL SECURITY`（如 `e1f2a3b4c5d6_durable_web_chat_runs.py`、`f2a3b4c5d6e7_memory_history_and_organization.py`）。实际启用情况取决于部署迁移和数据库角色；这些用户隔离策略不能代替租户成员资格及资源可见性校验。
- 后台入口显式设置 `current_user_id`，相应数据库事务设置 `app.current_user_id`；执行租户另由 `core/execution_scope.py` 传播。用户身份和执行租户是两个独立维度，不能用用户的界面当前租户推断后台任务归属。

## 六、新表归属判定指南

新增功能时，按以下问题确定归属维度：

1. 该资源需要被**同一租户内多个用户共享**吗？
   - 需要 → 租户级：加 `tenant_id` 字段；若还要区分「仅创建者可见」→ 加 `visibility` + `created_by`
   - 不需要，仅本人 → 用户级：加 `user_id` 字段
2. 需要跨租户可见吗？（如平台公开内容）→ 在租户级基础上扩 visibility 值域，如宠物包的 `public`/`official`
3. 需要全局唯一、所有租户共用吗？（如系统设置）→ 全局级，不加归属字段

判定后：租户级表加 `Index(tenant_id)`；用户级表加 `Index(user_id)`；路由查询务必拼接对应过滤条件，不要遗漏。


## 七、执行租户契约

### 界面选择与执行归属

用户切换界面租户只改变后续管理操作的筛选条件，不取消已经运行的任务，不改变已有对象的模型、工具、画像、记忆写入或观测归属。

| 执行入口 | 租户来源 | 权限依据 |
|---|---|---|
| 自动/手动定时任务 | `CronJob.tenant_id` | 活跃用户、活跃租户、成员资格、智能体可见性 |
| IM 消息及斜杠命令 | `ChannelConfig.tenant_id` | 渠道启用、渠道绑定、成员资格、智能体及资源权限 |
| 协作房间 | `ChatRoom.tenant_id` | 房间归属、成员资格、智能体权限；运行心跳检查实际成员资格，不检查界面选择 |
| Web、WebSocket、发布版 API、宠物会话 | 指定/会话绑定的 `Agent.tenant_id` | 用户身份、会话归属、租户成员资格、智能体可见性 |
| 新的无智能体交互 | 入口处捕获一次当前租户 | 入口权限校验；后续沿用捕获值 |
| 已有子智能体 | 父执行租户，子对象必须同租户 | 父子关系、成员资格、子智能体可见性和知识库权限 |
| 临时子智能体 | 父执行租户 | 父任务已授权的上下文、工具白名单、委派层级限制 |
| 会话记忆提取、实时每日记忆 | 来源会话的智能体及入口捕获的租户 | 会话所有权、来源一致性、成员资格；不读取最新界面租户 |
| 每日记忆批处理 | 对应智能体的租户 | 智能体可见性、成员资格；无法确定历史无智能体记录归属时跳过并记录原因 |
| 知识图谱抽取 | 来源知识库的租户 | 沿用知识库对象归属，不按用户当前租户选模型 |

### 实现规则

1. `require_execution_user` 检查用户和租户启用状态、`tenant_memberships`；用户仍是成员时切换界面不影响执行。
2. 按执行租户和 `visibility/created_by` 加载资源。不得只移除租户条件，也不得写入 `User.tenant_id` 临时模拟身份。
3. `bind_execution_scope` 绑定用户、租户与智能体上下文；`AgentLoop.run` 为工具并发任务传播该上下文，并在正常结束、异常、取消时清理。
4. `build_agent_loop` 和发布版构造器把选模型使用的租户传给循环；直接实例化 `AgentLoop` 也必须明确执行租户。运行观测与 Hook 读取该值，不使用用户级缓存。
5. 跨越请求生命周期的记忆任务携带来源信息并重新授权。缺失来源、成员被移除、租户停用或来源租户不一致时，不执行模型调用或写入。
6. 技能、工作空间及用户共享记忆仍保留已有用户级权限和共享语义；本次修复不把它们改成租户共享资源。
7. 代码变更不包含历史错归属记录的修正，也不包含重复任务清理、星期表达式修正或补发通知。这些操作单独评估和授权。

### 验证要求

使用隔离的本地 PostgreSQL 构造 A/B 两个租户、同一用户的双成员资格和 A 租户对象。切到 B 后验证对象仍在 A 执行；再移除 A 成员资格或禁用资源，验证拒绝执行。覆盖模型、工具、画像、记忆、委派、房间心跳及观测，并断言 `users.tenant_id` 始终保持 B。并发和取消测试必须验证 ContextVar 恢复。禁止把业务数据库作为可写测试库。


### 认证入口、房间操作与命令

对象执行路由使用 `ExecutionUser`：只验证 JWT、用户存在及启用状态，随后必须验证对象所有权、实际租户启用状态、成员资格与资源权限。`CurrentUser` 继续用于当前租户管理和无对象的新建入口。不能把两者简单替换而遗漏对象授权，也不能因为用户当前选中的 B 租户停用，阻止其仍有权限的 A 租户对象执行。

房间详情、成员配置、发送、停止、重试、确认和 SSE 使用 `ChatRoom.tenant_id`；SSE 周期检查该租户及成员资格，撤销权限后发送 `access_revoked` 并结束。`/portrait` 和 `/compact` 分别按 `ctx.tenant_id` 读取画像和选择模型，模型 ID 不能作为租户位置参数传入。

### 定时任务创建约束

- 创建、更新统一验证任务所有者、智能体可见性和通知渠道租户；跨租户、停用资源及不存在的引用拒绝写入。
- 后台工具使用已验证的执行上下文；缺少上下文时只能从已授权的智能体解析租户，不能从 `users.tenant_id` 推断。
- 同一用户、同一租户的创建在数据库事务锁内串行检查。相同 `request_id` 和相同配置返回原任务，配置改变返回冲突；不带请求 ID 的完全相同任务复用已有记录。不同请求 ID 的相同任务返回冲突。
- 同名、同启用状态但不同配置默认返回 409；显式 `allow_duplicate=true` 才允许并存。检查范围是同一所有者，并非禁止所有用户使用相同名称。前端对同名创建提示确认，并在同一次创建重试中保留请求 ID。
- 此机制保护创建重试，不承诺任务外部副作用的恰好一次执行；删除任务后重用请求 ID 可以重新创建。

### 星期兼容与历史迁移

新建或修改 Cron 表达式按标准输入解释：`0/7=周日、1-5=周一至周五`。服务在写入前转成明确英文名称，调度器仍使用 APScheduler。推荐写 `0 18 * * sun`、`30 14 * * mon-fri`，时区为 `Asia/Shanghai`。

历史数据库数字仍按原 APScheduler 规则解释：`0=周一、1-5=周二至周六`。管理页展示遵守原规则，打开编辑窗口时转换为星期名称，原样提交旧数字也保留原义。代码更新不会批量改写历史表达式；历史业务意图纠正需要单独的数据操作。

启动自动升级和旧库 bootstrap 在变更前检查租户归属：相关表有记录但缺少 `tenant_id` 列或值为空时停止，并要求单独备份、审查与显式归属处理。启动补丁已移除按当前用户租户/公共租户自动回填的 SQL。已有 Alembic 历史版本保留，直接执行手工 `alembic upgrade` 不经过启动保护，操作前仍须审核旧版本的回填语句；禁止把其当作历史数据修复工具。
