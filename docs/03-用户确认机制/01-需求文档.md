# 用户确认系统 - 需求文档

> 版本：v1.0 | 日期：2026-05-29 | 状态：草案

---

## 1. 背景与动机

当前智能体平台的对话模式是单向的：用户发送消息，Agent 自主推理并执行，最终返回结果。

但在实际使用中，Agent 经常需要在执行过程中**暂停并征求用户意见**：

- 生成了多个方案，不知道该选哪个
- 即将执行高风险操作（如删除文件、修改数据库），需要用户批准
- 需求描述不够清晰，需要追问用户
- 从对话中提取了可复用的技能，问用户是否保存

如果没有确认机制，Agent 只能"猜"用户意图然后直接执行——猜对了浪费一次确认，猜错了可能产生不可逆的后果。

### 1.1 设计参考

参考 Claude Code 的三种确认机制：

| Claude Code 机制 | 核心思路 | 我们如何借鉴 |
|---|---|---|
| **AskUserQuestion** | Agent 主动提问，提供 2-4 个选项供用户单选/多选，支持 preview 预览对比 | 适配为 Web 聊天中的选项卡片，扩展支持自由输入和审批模式 |
| **ExitPlanMode** | Agent 生成计划后请求用户审批，用户批准后才开始执行 | 适配为 approve 模式，增加"提出修改"按钮支持多轮循环 |
| **Permission Prompt** | 工具执行前弹出确认（Allow once / Always / Deny） | 适配为风险等级标签 + 确认卡片 |

## 2. 功能概述

### 2.1 一句话定义

Agent 在推理过程中可以调用 `AskUserQuestion` 工具，向前端用户展示一个问题（带选项），**暂停执行**直到用户做出选择后继续。

### 2.2 核心能力

| 能力 | 说明 |
|------|------|
| 方案选择 | Agent 给出多个方案，用户选一个（单选） |
| 批量确认 | Agent 列出多个操作项，用户勾选要执行的（多选） |
| 需求追问 | Agent 提出开放式问题，用户自由输入回答 |
| 操作审批 | Agent 展示即将执行的操作详情，用户批准/拒绝/提修改意见 |
| 超时自动恢复 | 用户长时间不响应时，Agent 按策略自行决定继续 |
| 多智能体支持 | 子智能体的确认请求冒泡到前端，标注来源 |

## 3. 确认类型

### 3.1 六种触发场景

| 场景 | 示例 | 风险等级 | 默认交互模式 |
|------|------|---------|------------|
| **方案选择** | "请选择重构方案：A/B/C" | 中 | 单选 |
| **批量操作** | "以下 15 个文件需要修改，请勾选范围" | 中 | 多选 |
| **危险操作确认** | "即将执行 `rm -rf ./dist`，是否继续？" | 高 | 审批 |
| **需求澄清** | "你说的'优化性能'具体指哪个接口？" | 低 | 自由输入 |
| **计划审批** | "以下是数据库迁移计划，请审批" | 高 | 审批（支持多轮修改） |
| **技能保存** | "我从对话中提取了一个技能，是否保存？" | 低 | 审批 |

### 3.2 风险等级

每个确认请求携带风险等级，影响 UI 展示样式：

| 等级 | 颜色 | 含义 |
|------|------|------|
| **低 (low)** | 蓝色 | 常规选择，无副作用 |
| **中 (medium)** | 黄色 | 会影响代码或配置，但可回退 |
| **高 (high)** | 橙色 | 可能产生不可逆操作 |
| **严重 (critical)** | 红色 | 涉及系统级变更或数据删除 |

## 4. 四种交互模式

### 4.1 单选 (single_select)

**用途**：从 N 个选项中选 1 个。

**前端表现**：
- 选项以卡片列表形式排列
- 每个卡片包含：标题、描述、可选的代码预览
- 点击选中，再次点击取消
- 底部两个按钮：「跳过」和「确认选择」
- 代码预览支持展开/折叠

**典型对话**：

> Agent：我分析了三种重构方案：
>
> ┌─────────────────────────────────────────┐
> │ ○ **方案 A：渐进式迁移**                  │
> │   保留旧接口兼容，逐步迁移。约 2 周。       │
> │   [查看预览]                              │
> ├─────────────────────────────────────────┤
> │ ● **方案 B：一次性重写**        ← 已选中  │
> │   完全重写认证模块。约 1 周。              │
> ├─────────────────────────────────────────┤
> │ ○ **方案 C：引入第三方库**                │
> │   使用 Auth0。有外部依赖。                │
> └─────────────────────────────────────────┘
>
> [跳过]  [确认选择]

### 4.2 多选 (multi_select)

**用途**：从 N 个选项中选多个。

**前端表现**：
- 带复选框的选项列表
- 顶部显示"已选择 X / N 项"
- 点击整行可切换选中状态
- 底部按钮：「跳过」和「确认选择 (X)」

**典型对话**：

> Agent：以下文件需要更新导入路径，请勾选要修改的文件：
>
> 已选择 3 / 5 项
>
> ☑ src/auth/login.py — 导入旧模块
> ☑ src/auth/register.py — 导入旧模块
> ☐ src/api/middleware.py — 导入旧模块
> ☑ src/utils/helpers.py — 间接引用
> ☐ tests/test_auth.py — 测试文件
>
> [跳过]  [确认选择 (3)]

### 4.3 自由输入 (free_input)

**用途**：需要用户用自然语言补充信息。

**前端表现**：
- 多行文本输入框
- 提交按钮

**典型对话**：

> Agent：你提到要"优化性能"，能具体描述一下遇到的问题吗？
> 比如哪个接口慢、预期响应时间是多少？
>
> ┌─────────────────────────────────────────┐
> │ 主要是 /api/chat/stream 接口，            │
> │ 在对话超过 20 轮后响应时间从 2s 变成 8s，  │
> │ 希望能控制在 3s 以内。                     │
> └─────────────────────────────────────────┘
>
> [提交]

### 4.4 审批 (approve)

**用途**：对即将执行的操作进行审批，支持多轮修改循环。

**前端表现**：
- 操作详情面板（标题 + 描述 + 代码预览）
- 三个按钮：「拒绝」「提出修改」「批准执行」
- 点击"提出修改"展开文本框，用户输入修改意见后提交
- Agent 收到修改意见后调整方案，**再次**请求审批

**典型对话（多轮循环）**：

> **第一轮**
>
> Agent：以下是数据库迁移计划，请审批：
>
> **迁移计划：users 表添加 phone 字段**
> 1. 创建 Alembic migration
> 2. 添加 NOT NULL phone 字段
> 3. 默认值空字符串
> 4. 添加索引
>
> [拒绝]  [提出修改]  [批准执行]
>
> ---
>
> *用户点击「提出修改」，输入："第 3 步不要用空字符串，用 NULL"*
>
> **第二轮**
>
> Agent：已根据你的反馈修改（变更：默认值改为 NULL），请重新审批：
>
> **迁移计划：users 表添加 phone 字段（已修改）**
> 1. 创建 Alembic migration
> 2. 添加 phone 字段（可空）
> 3. 默认值 NULL ← 已修改
> 4. 添加索引
>
> [拒绝]  [提出修改]  [批准执行]

## 5. 交互流程

### 5.1 完整流程

```
用户发送消息
  → Agent 开始推理
  → Agent 判断需要用户决策
  → Agent 调用 AskUserQuestion 工具
  → 前端弹出确认卡片（Agent 暂停，等待中）
  → 用户做出选择并提交
  → 确认卡片切换为"已确认"状态（展示用户的选择结果）
  → Agent 收到用户选择，继续推理
  → Agent 输出后续内容
```

### 5.2 确认卡片状态

每个确认卡片有三种状态：

| 状态 | 外观 | 说明 |
|------|------|------|
| **等待中** | 完整交互（选项 + 按钮） | 用户可以操作 |
| **已确认** | 折叠为结果摘要 | 展示"你选择了：方案 B" |
| **已超时** | 灰色 + 超时提示 | 展示"超时未响应，Agent 已自行决定" |

### 5.3 超时处理

如果用户在限定时间内未响应，Agent 根据场景类型自动处理：

| 场景 | 默认超时 | 超时行为 |
|------|---------|---------|
| 方案选择 | 5 分钟 | Agent 自行选择最优方案继续 |
| 危险操作确认 | 3 分钟 | 跳过此操作，尝试安全替代方案 |
| 需求澄清 | 10 分钟 | 基于已有信息继续 |
| 技能保存 | 5 分钟 | 不保存 |
| 批量操作 | 5 分钟 | 执行全部 |
| 计划审批 | 10 分钟 | 暂停，不自动执行 |

前端显示倒计时，最后 30 秒高亮提醒。

## 6. 多智能体场景

### 6.1 子智能体确认冒泡

当 Agent 将子任务委派给子智能体时，子智能体也可能需要用户确认。

**规则**：
- 子智能体的确认请求冒泡到前端，与父智能体的确认请求共用同一界面
- 确认卡片标注来源："来自子智能体 CodeHelper"（紫色标签）
- 用户响应后，结果返回给发起确认的子智能体

**前端表现**：

```
┌─ 来自 CodeHelper ──────────────────────────────────┐
│                                                     │
│  请选择代码风格：                                     │
│                                                     │
│  ○ Prettier 默认配置                                 │
│  ● ESLint Airbnb 规范                               │
│  ○ 自定义规范                                       │
│                                                     │
│                                    [跳过] [确认选择]  │
└─────────────────────────────────────────────────────┘
```

### 6.2 并发确认

当多个子智能体同时需要确认时：
- 确认卡片按时间顺序排列在对话流中
- 每个卡片独立响应，互不阻塞
- 已确认的卡片折叠为结果摘要

## 7. 与信任级别的联动

现有的信任级别（trust_level）影响确认行为：

| trust_level | 对 AskUserQuestion 的影响 |
|---|---|
| `ask_always` | 所有需要确认的场景都弹出确认卡片 |
| `ask_dangerous` | 仅高/严重风险等级弹出确认，低/中风险自动选择最优选项 |
| `auto_all` | 全部自动处理，不弹出确认卡片（仅记录日志） |

用户在「设置 → 安全配置」中可随时调整信任级别。

## 8. 用户体验要求

### 8.1 选项设计规范

Agent 生成的选项应遵循以下规范：

- **标题简洁**：每个选项的标题不超过 20 个字
- **描述具体**：说明该选项的影响、耗时、风险
- **可预览**：如果涉及代码变更，提供 diff 或代码片段预览
- **互斥清晰**：选项之间应有明显区别，避免模糊重叠
- **数量控制**：单选不超过 5 个选项，多选不超过 20 个

### 8.2 防确认疲劳

- 同一对话中连续弹出超过 3 次确认时，前端折叠为摘要模式
- 审批模式支持"提出修改"，避免用户只能被动接受或拒绝
- 低风险操作在 `ask_dangerous` 模式下自动通过

### 8.3 页面刷新恢复

- 用户刷新页面后，前端请求待确认列表并恢复确认卡片
- 确认卡片保持"等待中"状态，倒计时继续

### 8.4 可访问性

- 确认卡片支持键盘操作（Tab 切换选项，Enter 确认）
- 风险等级通过颜色 + 文字双重传达（兼顾色盲用户）
- 超时倒计时使用 aria-live 区域播报

## 9. 验收标准

### 9.1 功能验收

| # | 验收项 | 验收标准 |
|---|--------|---------|
| 1 | 单选确认 | Agent 调用 AskUserQuestion(mode=single_select) → 前端展示选项卡片 → 用户选中并提交 → Agent 收到选择结果继续推理 |
| 2 | 多选确认 | Agent 调用 AskUserQuestion(mode=multi_select) → 前端展示复选框列表 → 用户勾选多项并提交 → Agent 收到选中列表 |
| 3 | 自由输入 | Agent 调用 AskUserQuestion(mode=free_input) → 前端展示输入框 → 用户输入并提交 → Agent 收到文本内容 |
| 4 | 审批确认 | Agent 调用 AskUserQuestion(mode=approve) → 前端展示审批面板 → 用户点击批准 → Agent 继续执行 |
| 5 | 审批修改 | 用户在审批面板点击"提出修改" → 输入修改意见 → Agent 收到反馈，修改方案后再次请求审批 |
| 6 | 跳过 | 用户点击"跳过" → Agent 收到拒绝，选择其他方案 |
| 7 | 超时 | 用户未在限定时间内响应 → 确认卡片变为超时状态 → Agent 按策略自动处理 |
| 8 | 风险标签 | 高风险确认卡片显示橙色/红色边框和风险徽标 |
| 9 | 多智能体 | 子智能体发起确认 → 卡片标注来源智能体名称 |
| 10 | 页面刷新 | 刷新页面后 → 待确认卡片恢复显示 |
| 11 | 信任级别 | trust_level=auto_all 时 → 不弹出确认卡片，Agent 自动处理 |
| 12 | 已确认状态 | 用户提交后 → 卡片折叠为结果摘要，按钮消失 |

### 9.2 非功能验收

| # | 验收项 | 验收标准 |
|---|--------|---------|
| 1 | 响应延迟 | 确认请求到前端展示 < 500ms |
| 2 | 并发 | 支持同一用户多个会话的并发确认 |
| 3 | 内存 | 确认请求仅存于内存，不增加数据库负担（Phase 1） |

## 10. 不在范围内

以下功能不在本版本范围内，将在后续迭代中考虑：

- 确认操作的历史记录页面
- 确认操作的审计日志持久化
- "本次会话信任此工具"等细粒度信任授权
- 确认卡片的离线推送（如通知/邮件）
- 确认请求的批量操作（一键全部批准）
- 管理员查看其他用户的确认记录

## 附录 B：场景示例汇总

### B.1 方案选择

```
Agent → AskUserQuestion(
  question = "请选择认证模块的重构方案：",
  mode = "single_select",
  options = [
    { label: "方案 A：渐进式迁移", description: "保留旧接口，约 2 周", preview: "..." },

    { label: "方案 C：第三方库", description: "使用 Auth0，有外部依赖" },
  ],
  risk = "medium"
)

用户选择 → "方案 B"

Agent 收到 → 继续按方案 B 执行
```

### B.2 危险操作

```
Agent → AskUserQuestion(
  question = "即将执行以下命令：",
  mode = "approve",
  options = [
    { label: "rm -rf ./dist && npm run build", description: "删除并重新构建" }
  ],
  risk = "high"
)

用户批准 → Agent 执行命令
用户拒绝 → Agent 跳过，尝试替代方案
```

### B.3 计划审批（多轮）

```
Agent → AskUserQuestion(mode = "approve", ...)  // 展示计划 v1
用户 → 提出修改："第 3 步用 NULL"
Agent → AskUserQuestion(mode = "approve", ...)  // 展示计划 v2
用户 → 批准
Agent → 开始执行
```

### B.4 需求澄清

```
Agent → AskUserQuestion(
  question = "你说的'优化性能'具体指哪个接口？",
  mode = "free_input",
  risk = "low"
)

用户输入 → "主要是 /api/chat/stream，超过 20 轮后变慢"
Agent 收到 → 针对性分析和优化
```
