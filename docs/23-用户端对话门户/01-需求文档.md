# 用户端对话门户 — 需求文档

## 一、背景

当前平台的所有对话界面（`AgentChatPage`、`ChatPage`）都是管理端形态：与管理功能（agent 配置、workspace、沙箱文件、斜杠命令、页内操作等）深度耦合，面向的是租户管理员/超级管理员。

租户内普通用户（role=user）只需要一个纯净的对话界面：选 agent、聊天、管理自己的会话。不需要看到 prompt、工具配置、模型参数等管理与实现细节。

### 定位决策（已定）

| 项 | 结论 |
|---|---|
| 面向对象 | 已注册平台用户（role=user），租户内门户 |
| 鉴权 | 复用现有 JWT 双 token 体系，无改动 |
| 对外访客/匿名访问 | **本期不做**，作为后续扩展预留（见第八节） |

## 二、目标

1. 普通用户拥有独立于管理端的对话门户，UI 只做对话与会话管理
2. 后端聊天协议（SSE 事件流）零改动复用
3. agent 信息对普通用户脱敏（不泄露 system prompt、工具配置等实现细节）
4. 前端聊天流式逻辑抽取为公共 hook，消除现有三份重复（`AgentChatPage.handleSend` / `handleReconnect` / `ChatPage`），用户端不再产生第四份

## 三、功能需求

### 3.1 门户布局 `PortalLayout`

- 独立路由分支（同 SPA，不新建前端工程），路由前缀 `/portal`：
  - `/portal` — agent 列表（门户首页）
  - `/portal/agents/:agentId/chat[/:sessionId]` — 对话页
- 无管理端侧边菜单（仪表盘/模型/系统配置/租户/用户等一律不出现）
- 顶栏仅保留：平台标识、用户信息（用户名、退出登录）
- 登录后按角色分流：role=user 默认进 `/portal`，admin/superadmin 维持现状进 `/agents`

### 3.2 Agent 列表页

- 卡片式展示当前用户可用 agent：图标、名称、描述、`welcome_message`
- 数据源：现有 `GET /api/agents`（`_agent_visible_to` 已做 tenant/private 过滤，直接复用）
- **不展示**：模型 Tag、工具数量、迭代次数等管理端信息
- 遵循前端 Loading 规范：首屏 Spin → 空态 Empty → 卡片列表，Header 常驻

### 3.3 对话页

在现有聊天能力基础上做减法：

**保留**：
- SSE 流式输出（`thinking` / `text_delta` / `tool_call` / `tool_result` / `done` / `error`）
- thinking 折叠块、工具调用卡片、委派卡片（`ToolCallCard` / `DelegationCard`）
- 用户确认卡片全部五种模式（`ConfirmationCard`：single_select / multi_select / free_input / approve / table_input）
- 图片附件上传（≤10MB）
- 消息编辑重发、流式中消息排队（`useMessageQueue`）
- 会话自动建标题、URL 与 sessionId 双向同步

**移除**：
- 斜杠命令面板（`/stop` 等命令）
- workspace 选择器与工作区文件上传（≤500MB 文件上传）
- `SandboxFilePanel`（沙箱文件浏览）、`WebpagePreviewPanel`（网页产物预览）
- `AgentConfigSidebar` 的全部配置区（prompt/tools/mcp/knowledge/skills/children）
- `page_context` 注入、`uiActionStore` 页内操作事件
- 渠道任务重连入口（`sessionsApi.getStatus` / `watchEvents`，管理端排查用途）

### 3.4 会话管理

- 侧栏复用 `SessionSidebar` 能力：搜索、新建、重命名（行内编辑）、删除、置顶、归档、刷新
- 会话列表硬过滤 `user_id`（后端现成），门户内只展示 `source=chat` 的界面会话
- 新建对话防重守卫（`if (busy) return`，沿用 `ChatPage` 做法）

### 3.5 移动端适配

- 对话页响应式：侧栏在小屏折叠为抽屉，输入框自适应
- 管理端目前桌面优先，门户需覆盖手机浏览器基础可用（可读、可发消息、可答确认卡片）

## 四、后端需求（改动极小）

| # | 需求 | 说明 |
|---|---|---|
| 1 | 新增精简 agent 接口 `GET /api/portal/agents` | 只返回：id、name、description、icon、welcome_message、starter_prompts。**必须脱敏**——现有 `GET /api/agents/{id}` 会把 system prompt、工具列表、模型配置返回给普通用户，管理端无妨，门户不可使用 |
| 2 | 其余 API 零改动 | `POST /api/chat/stream`、`/api/sessions/*`、`/api/confirmations/*` 已按 `user_id` 隔离，直接复用；SSE 事件协议不变 |

## 五、前端工程改造（支撑项，先于门户开发）

### 5.1 抽取 `useChatStream` hook

现状问题：SSE 事件处理的 switch 逻辑在 `AgentChatPage` 内重复两份（`handleSend` + `handleReconnect`），`ChatPage` 还有一份更老的变体，且耦合 petStore / uiActionStore / page_context。

要求：
- 抽为 `frontend/src/hooks/useChatStream.ts`，输入：chatStore 引用、`StreamingState` setter 集合、可选事件钩子（onSession / onTitle / onError 等）
- 管理端两个页面与用户端门户共用同一实现；管理端的渠道重连（`watchEvents` 回放）也走该 hook
- 门户不使用的扩展点（uiAction、petStore）以可选回调注入，hook 本体不含管理端依赖

### 5.2 组件复用

直接复用：`MessageList`、`StreamingMessage`、`ConfirmationCard` 全家、`ChatInput`（以 `simple` 模式为底子再裁剪：去掉斜杠命令、workspace 选择、工作区文件上传）、`SessionSidebar`。

## 六、非功能需求

- **安全**：门户链路任何接口不得返回 agent 的 prompt / 工具配置 / 模型名（见 4.1）；图片访问沿用 `withImageAuth()` 带 token 方案
- **性能**：门户首屏不加载管理端重组件（沙箱面板、配置侧栏按需移除后，注意路由级代码分割）
- **观测**：门户会话 `source=chat` 不变，Langfuse trace 无需改造

## 七、验收标准

1. role=user 登录后落在 `/portal`，能看到本租户可见 agent 卡片列表，点击进入对话
2. 对话全流程可用：流式输出、工具调用展示、委派展示、五种确认卡片可交互、图片上传、编辑重发、消息排队
3. 门户中通过接口/页面均无法获取 agent 的 system prompt 与工具配置
4. 会话管理（新建/重命名/删除/置顶/归档/搜索）在门户可用，且只能看到自己的会话
5. 管理端 `AgentChatPage` / `ChatPage` 切换到 `useChatStream` 后功能无回归（含渠道任务重连）
6. 手机宽度（375px）下可正常对话与回答确认卡片

## 八、边界与后续扩展（本期不做）

- **对外访客端**（未登录用户通过分享链接/嵌入组件使用 agent）：需要新建发布配置模型（`agent_publish_configs`）、访客 token、限流配额、`sessions.source` 扩展，独立立项。届时门户 UI 壳可直接复用
- 门户内的记忆/技能/画像等个人功能入口：本期门户只做对话，其余功能用户仍可在管理端个人区访问
- agent  Marketplace / 跨租户可见：依赖 `visibility` 增加 `public` 档，随访客端一并设计
