# AIO Agent Platform — 会话压缩技术方案

> 本文档定义会话历史压缩的需求与实现方案，用于在上下文窗口接近模型限制时，自动保留关键信息、释放 token 预算。

---

## 1. 背景

Agent 在长对话场景下（复杂编码任务、多轮调试、跨日会话恢复）会快速逼近模型的上下文窗口上限。一旦超限：

- 早期关键信息被简单截断，Agent 丢失决策上下文
- Token 成本随 prompt 长度线性增长
- 工具调用历史（含完整 stdout/stderr）占据大量预算，但绝大多数内容后续不再被引用

当前的 `context.py` 已实现基于字符的 token 估算、消息截断和基础摘要能力（`context_summary.j2`），但缺乏一套**分阶段、可配置、可恢复**的压缩策略。需要在此基础上演进为完整的会话压缩子系统。

---

## 2. 需求

### 2.1 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| R1 | 当会话 token 数接近阈值时，自动触发压缩（无需用户干预） | P0 |
| R2 | 压缩必须保留：用户显式指令、已做的技术决策、关键文件路径、未解决的问题 | P0 |
| R3 | 压缩必须丢弃：寒暄、完整工具输出、中间推理、重复确认 | P0 |
| R4 | 保留最近 N 轮原始消息不动（"热区"），只压缩更早的历史 | P0 |
| R5 | 压缩结果以 `summary` 系统消息形式注入到会话头部，后续轮次可继续累积 | P0 |
| R6 | 支持多级压缩：先轻度（丢弃工具细节）→ 再中度（合并相邻轮次）→ 最后深度（LLM 摘要） | P1 |
| R7 | 压缩后的会话仍可被用户在前端查看完整历史（原始消息归档，不物理删除） | P1 |
| R8 | 支持用户主动触发压缩（`/compact` 指令或 UI 按钮） | P2 |
| R9 | 压缩事件记录到 `traces` 表，便于事后审计"为什么 Agent 忘了某件事" | P2 |

### 2.2 非功能需求

| 维度 | 要求 |
|------|------|
| **延迟** | 单次压缩耗时 < 5s（含 LLM 摘要调用） |
| **成本** | 摘要调用使用廉价小模型（如 Haiku / GPT-4o-mini），单次成本 < $0.01 |
| **幂等性** | 同一会话多次触发压缩，结果一致且不重复丢失信息 |
| **多租户隔离** | 压缩流程复用 `user_id` 过滤，不会把 A 用户的历史塞进 B 用户的摘要 |
| **可观测** | 每次压缩记录：触发原因、压缩前后 token 数、使用的压缩级别、耗时 |
| **可配置** | 阈值、保留轮数、摘要模型、压缩策略均可在 `settings` 中调整 |

## 3. 现有状态分析

### 3.1 当前表结构

```
┌─────────────────────────┐          ┌──────────────────────────────┐
│       sessions          │          │         messages              │
│─────────────────────────│          │──────────────────────────────│
│ id (PK)                 │◄──1:N───│ session_id (FK)              │
│ user_id                 │          │ id (PK)                      │
│ agent_id                │          │ user_id                      │
│ workspace_id            │          │ role (user/assistant/system)  │
│ title                   │          │ content                      │
│ is_pinned               │          │ tool_calls (JSONB)           │
│ is_archived             │          │ tool_call_id                 │
│ context_summary (Text) ─┤── 摘要  │ token_usage (JSONB)          │
│ created_at              │          │ created_at                   │
│ updated_at              │          │                              │
└─────────────────────────┘          └──────────────────────────────┘
```

### 3.2 当前压缩数据流

```
 用户发消息
    │
    ▼
_load_conversation_history()
    │ SELECT * FROM messages WHERE session_id = ? ORDER BY created_at
    │ 读取 session.context_summary
    │
    ▼
prepare_context()  ← 纯内存操作
    │
    ├─ 估算 token → 未超阈值 → 直接组装，发给 LLM
    │
    └─ 超阈值 →
         │
         ├─ Step 1: truncate_history_messages()（内存裁剪）
         ├─ Step 2: generate_summary()（LLM 摘要，内存中）
         │
         └─ 组装 [system + summary + 热区消息] 发给 LLM
    │
    ▼
Agent Loop 执行 → 保存 user/assistant 消息到 messages 表
    │
    ▼
_update_context_summary()  ← 后台 fire-and-forget
    │ UPDATE sessions SET context_summary = ? WHERE id = ?
    │
    ▼
  ❌ 问题：被"压缩掉"的消息仍然留在 messages 表中，
     下次加载时又会被全部读出来，重复压缩
```

### 3.3 当前方案的问题

| 问题 | 影响 |
|------|------|
| `messages` 表不区分"活跃"和"已压缩"消息 | 每次加载全量，压缩收益被抵消 |
| `context_summary` 是纯 Text 字段 | 没有结构化元数据，不知道压缩了哪些消息 |
| 没有压缩日志 | 无法审计"为什么 Agent 忘了某件事" |
| 重复压缩 | 每轮对话都重新摘要，浪费 token |
| 前端无法区分 | 用户看历史时不知道哪些已被压缩成摘要 |

## 4. 表结构设计

### 4.1 方案选型

| | 方案 A：JSONB 塞进 sessions | 方案 B：独立压缩表 + 消息标记 |
|--|---|---|
| **结构** | sessions 表加 3 个 JSONB 字段 | 新建 `session_compressions` 表 + messages 加标记列 |
| **多次压缩** | JSONB 数组越滚越大，session 行膨胀 | 每次压缩一行记录，天然支持审计 |
| **消息过滤** | 加载时仍读全量 messages，靠内存判断 | SQL 直接过滤 `WHERE compressed_at IS NULL` |
| **前端展示** | 需额外逻辑区分已压缩/未压缩 | 直接查，标记列告诉前端 |
| **迁移成本** | 小（只加列） | 中（新建表 + 加列） |
| **适合** | 压缩次数少、不需要审计的简单场景 | 生产级：可审计、可观测、前端友好 |

**选择方案 B**。理由：
1. `messages` 表加一个 `compressed_at` 列就能让 SQL 层直接过滤已压缩消息，避免重复加载
2. 独立的 `session_compressions` 表支持完整审计链
3. 前端可通过标记列直接展示"此处已压缩"分界线

```
│────────────────────────────────│ │ │──────────────────────────────────│
│ id (PK)                        │ │ │ id (PK)                          │
```

### 4.3 DDL：新建 `session_compressions` 表

```sql
CREATE TABLE session_compressions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id      UUID NOT NULL,            -- 关联会话
    user_id         UUID NOT NULL,            -- 关联用户（多租户隔离）

    -- 压缩产物
    summary_text    TEXT NOT NULL,             -- LLM 生成的摘要文本
    compressed_message_ids JSONB NOT NULL,     -- 被压缩的 message.id 列表
                                                -- 例: ["uuid-1", "uuid-2", ...]

    -- 范围描述（便于快速定位，不需要解 JSONB）
    message_range   JSONB NOT NULL,            -- {first_id, last_id, first_at, last_at, count}

    -- 压缩元数据
    tokens_before   INTEGER NOT NULL,          -- 压缩前估算 token 数
    tokens_after    INTEGER NOT NULL,          -- 压缩后估算 token 数
    stages_applied  JSONB NOT NULL DEFAULT '[]', -- ["truncate", "merge", "llm_summary"]
    model_used      VARCHAR(128),              -- 摘要使用的模型名（Stage 3 时）
    duration_ms     INTEGER,                   -- 压缩耗时（毫秒）
    triggered_by    VARCHAR(16) NOT NULL       -- "auto" | "manual" | "emergency"
                DEFAULT 'auto',

    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 按会话查询压缩历史（最新一条用于加载摘要）
CREATE INDEX idx_compression_session
    ON session_compressions(session_id, created_at DESC);

-- 多租户隔离
CREATE INDEX idx_compression_user
    ON session_compressions(user_id);

COMMENT ON TABLE session_compressions IS '会话压缩日志表：每次压缩产生一条记录';
COMMENT ON COLUMN session_compressions.compressed_message_ids
    IS '被压缩的消息ID列表(JSONB数组)，用于审计和前端展示';
COMMENT ON COLUMN session_compressions.stages_applied
    IS '本次压缩应用的阶段列表，如 ["truncate", "llm_summary"]';
```

### 4.4 DDL：`messages` 表新增标记列

```sql
ALTER TABLE messages
    ADD COLUMN compressed_at TIMESTAMPTZ DEFAULT NULL;

COMMENT ON COLUMN messages.compressed_at
    IS '消息被压缩的时间戳。NULL 表示活跃消息（未被压缩），非 NULL 表示已被压缩归档';

-- 用于高效加载"仅活跃消息"
CREATE INDEX idx_messages_active
    ON messages(session_id, created_at)
    WHERE compressed_at IS NULL;
```

### 4.5 DDL：`sessions` 表新增计数列

```sql
ALTER TABLE sessions
    ADD COLUMN compression_count INTEGER NOT NULL DEFAULT 0;

COMMENT ON COLUMN sessions.compression_count
    IS '该会话累计压缩次数，用于前端展示和触发"建议新开会话"的提示';
```

### 4.6 ORM 模型变更

```python
# ---- db/models.py ----

class Session(Base):
    __tablename__ = "sessions"
    # ... 现有字段 ...

    # 新增
    compression_count: Mapped[int] = mapped_column(
        Integer, default=0, comment="累计压缩次数"
    )

    # 新增 relationship
    compressions: Mapped[list["SessionCompression"]] = relationship(
        back_populates="session",
        order_by="SessionCompression.created_at.desc()",
    )


class Message(Base):
    __tablename__ = "messages"
    # ... 现有字段 ...

    # 新增
    compressed_at: Mapped[datetime | None] = mapped_column(
        DateTime(timezone=True), default=None, comment="压缩时间戳，NULL=活跃"
    )


class SessionCompression(Base):
    """会话压缩日志 — 每次压缩产生一条记录。"""
    __tablename__ = "session_compressions"

    id: Mapped[UUID] = mapped_column(
        PG_UUID(as_uuid=True), primary_key=True, default=uuid4
    )
    session_id: Mapped[UUID] = mapped_column(
        PG_UUID(as_uuid=True), nullable=False
    )
    user_id: Mapped[UUID] = mapped_column(
        PG_UUID(as_uuid=True), nullable=False
    )

    # 压缩产物
    summary_text: Mapped[str] = mapped_column(Text, nullable=False)
    compressed_message_ids: Mapped[dict] = mapped_column(
        JSONB, nullable=False, comment="被压缩的message.id列表"
    )
    message_range: Mapped[dict] = mapped_column(
        JSONB, nullable=False, comment="{first_id, last_id, first_at, last_at, count}"
    )

    # 元数据
    tokens_before: Mapped[int] = mapped_column(Integer, nullable=False)
    tokens_after: Mapped[int] = mapped_column(Integer, nullable=False)
    stages_applied: Mapped[dict] = mapped_column(
        JSONB, default=list, nullable=False
    )
    model_used: Mapped[str | None] = mapped_column(String(128))
    duration_ms: Mapped[int | None] = mapped_column(Integer)
    triggered_by: Mapped[str] = mapped_column(
        String(16), default="auto", nullable=False
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), default=func.now()
    )

    session: Mapped["Session"] = relationship(back_populates="compressions")

    __table_args__ = (
        Index("idx_compression_session", "session_id", "created_at"),
        Index("idx_compression_user", "user_id"),
        {"comment": "会话压缩日志表"},
    )
```

### 4.7 表关联关系汇总

```
sessions  1 ──── N  messages
   │                  │
   │                  └─ compressed_at: NULL=活跃, 非NULL=已归档
   │
   └── 1 ──── N  session_compressions
                    │
                    ├─ summary_text: 当前生效的摘要
                    ├─ compressed_message_ids: 指向 messages.id（JSONB 数组）
                    └─ message_range: {first_id, last_id, count, ...}
```

关联方式：
| 关系 | 类型 | 说明 |
|------|------|------|
| `sessions` → `messages` | 1:N FK (`messages.session_id`) | 已有，不变 |
| `sessions` → `session_compressions` | 1:N FK (`session_compressions.session_id`) | **新增** |
| `session_compressions` → `messages` | JSONB 引用 (`compressed_message_ids`) | **新增**，非 FK，逻辑关联 |
| `messages.compressed_at` | 标记列 | **新增**，标记消息是否已被压缩 |

为什么 `compressed_message_ids` 不用外键：
- JSONB 数组无法建 FK 约束
- 消息不会被物理删除，所以不需要级联
- 审计场景只需逻辑关联即可

## 5. 数据流详解

### 5.1 写入路径：压缩发生时

```
用户发消息 → prepare_context() 检测超阈值
    │
    ▼
┌─ 分割消息 ──────────────────────────────────────────────────┐
│                                                              │
│  messages 表（按 created_at 排序）:                           │
│                                                              │
│  msg-1  msg-2  msg-3  msg-4  msg-5  msg-6  msg-7  msg-8     │
│  │                                    │                      │
│  │◄──── 冷区（待压缩）────────────────►│◄── 热区 ──►│        │
│  │         8 条消息                    │   保留不动  │        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Stage 1-3 压缩 ────────────────────────────────────────────┐
│                                                              │
│  冷区 8 条消息 → LLM 摘要 → summary_text (约 500 字)        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ 数据库写入（一个事务）──────────────────────────────────────┐
│                                                              │
│  ① UPDATE messages                                           │
│     SET compressed_at = now()                                │
│     WHERE id IN (msg-1, msg-2, ..., msg-5)                  │
│                                                              │
│  ② INSERT INTO session_compressions                          │
│     SET session_id = ?,                                      │
│         user_id = ?,                                         │
│         summary_text = "用户使用 PostgreSQL + asyncpg...",    │
│         compressed_message_ids =                             │
│             '["msg-1","msg-2","msg-3","msg-4","msg-5"]',     │
│         message_range = '{                                   │
│             "first_id": "msg-1",                             │
│             "last_id": "msg-5",                              │
│             "first_at": "2026-05-29T10:00:00Z",              │
│             "last_at": "2026-05-29T10:30:00Z",               │
│             "count": 5                                       │
│         }',                                                  │
│         tokens_before = 12000,                               │
│         tokens_after = 3200,                                 │
│         stages_applied = '["truncate","llm_summary"]',       │
│         model_used = 'claude-haiku-4-5',                     │
│         duration_ms = 1820,                                  │
│         triggered_by = 'auto'                                │
│                                                              │
│  ③ UPDATE sessions                                           │
│     SET context_summary = "用户使用 PostgreSQL + asyncpg...",│
│         compression_count = compression_count + 1            │
│     WHERE id = ?                                             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 读取路径：加载历史给 LLM

```
用户发消息 → _load_conversation_history()
    │
    ▼
┌─ SQL 查询（只加载活跃消息）─────────────────────────────────┐
│                                                              │
│  SELECT * FROM messages                                      │
│  WHERE session_id = ?                                        │
│    AND compressed_at IS NULL    ← 关键：只加载未被压缩的消息 │
│  ORDER BY created_at                                         │
│  LIMIT ?                                                     │
│                                                              │
│  结果: msg-6, msg-7, msg-8  （热区消息，数量少）             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ 加载最新摘要 ──────────────────────────────────────────────┐
│                                                              │
│  SELECT context_summary FROM sessions WHERE id = ?           │
│                                                              │
│  结果: "用户使用 PostgreSQL + asyncpg，不用 ORM..."          │
│                                                              │
│  或者（需要完整元数据时）：                                    │
│                                                              │
│  SELECT summary_text, created_at                             │
│  FROM session_compressions                                   │
│  WHERE session_id = ?                                        │
│  ORDER BY created_at DESC                                    │
│  LIMIT 1                                                     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ 组装发给 LLM 的消息列表 ──────────────────────────────────┐
│                                                              │
│  [0] system: "你是 AI 助手，人格设定..."（system prompt）    │
│  [1] system: "[Previous conversation summary]:               │
│              用户使用 PostgreSQL + asyncpg，不用 ORM..."      │
│  [2] user:   msg-6 的内容                                    │
│  [3] assistant: msg-7 的内容                                 │
│  [4] user:   msg-8 的内容                                    │
│  [5] user:   当前用户输入                                    │
│                                                              │
│  对比压缩前: 原来 8+1=9 条 → 现在 5+1=6 条                 │
│  Token 估算: 12000 → 3200                                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

```
│  │  User: 再加一个数据库连接池                           │   │

│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 5.4 多次压缩的数据状态

一个长会话可能经历多次压缩。每次压缩产生一条 `session_compressions` 记录：

```
时间线:

10:00  msg-1 ~ msg-5   产生
10:30  第 1 次压缩 → compression-1: 压缩 msg-1~5，summary-A
10:35  msg-6 ~ msg-10  产生（热区）
11:00  msg-11 ~ msg-15 产生（热区增长）
11:30  第 2 次压缩 → compression-2: 压缩 msg-6~12，summary-B
                       （summary-B 应包含 summary-A 的关键信息）

数据库状态:

messages 表:
  msg-1 ~ msg-5:   compressed_at = 10:30  ← 第 1 次压缩
  msg-6 ~ msg-12:  compressed_at = 11:30  ← 第 2 次压缩
  msg-13 ~ msg-15: compressed_at = NULL   ← 当前活跃

session_compressions 表:
  compression-1: summary-A, ids=[msg-1..5],  created_at=10:30
  compression-2: summary-B, ids=[msg-6..12], created_at=11:30

sessions 表:
  context_summary = summary-B  （始终指向最新摘要）
  compression_count = 2
```

LLM 加载时只看到：
```
[system prompt]
[summary-B]           ← context_summary（包含了 summary-A 的信息）
[msg-13, msg-14, msg-15]  ← 活跃消息
[当前用户输入]
```

### 5.5 增量摘要策略（多次压缩时）

第 2 次压缩时，`generate_summary()` 的输入应包含上一次的摘要：

```python
# 伪代码
async def compress(session_id, provider):
    # 加载活跃消息
    active_messages = load_messages(where_compressed_at_is_null)

    # 加载上一次摘要（作为增量上下文）
    prev_summary = session.context_summary  # 即 summary-A

    # 把上一次摘要作为"前置消息"一起送入 LLM
    input_messages = []
    if prev_summary:
        input_messages.append(
            LLMMessage(role="system",
                       content=f"[Previous summary to incorporate]: {prev_summary}")
        )
    input_messages.extend(cold_messages)  # 本次待压缩的冷区消息

    # LLM 生成新摘要（自然融合旧摘要的关键信息）
    new_summary = await generate_summary(input_messages, provider)

    # 写入数据库（一个事务）
    mark_messages_compressed(cold_message_ids)
    insert_compression_log(...)
    update_session_context_summary(new_summary)
```

这样 summary-B 自然包含 summary-A 的关键信息，避免多次压缩后的信息断裂。

## 6. 实现方案

### 6.1 三级压缩策略

按成本从低到高逐级升级，每级都重新估算 token，一旦低于阈值即停止。

#### Stage 1 — 工具输出裁剪（规则，零成本）

- 对 `tool_result` 类消息，超过 `MAX_TOOL_OUTPUT_CHARS`（默认 2000）的部分替换为 `[truncated]`
- 保留工具名、参数摘要、执行状态
- 完全确定性，不调用 LLM

#### Stage 2 — 历史轮次合并（规则，零成本）

- 将"热区"之外的连续同主题轮次合并为单条 `user`/`assistant` 消息
- 合并规则：同一工具调用链（`tool_call` → `tool_result` → 紧跟的 `assistant` 文本）打包为一条摘要消息
- 仍然不调用 LLM，只是结构性压缩

#### Stage 3 — LLM 摘要（小模型，低成本）

- 使用 `context_summary.j2` 模板，调用配置好的摘要模型（默认 Haiku / GPT-4o-mini）
- 输入：Stage 1/2 处理后的历史（不含热区）+ 上一次摘要
- 输出：一段结构化摘要，包含 `decisions / instructions / pending / key_paths` 四个区块
- 摘要写入 `sessions.context_summary` + `session_compressions.summary_text`

### 6.2 触发时机

```python
def should_compress(used_tokens: int, budget: int) -> bool:
    return used_tokens > budget * COMPRESS_THRESHOLD  # 默认 0.75
```

触发点：
1. **每轮消息发送前**：`prepare_context()` 内部检查（主路径）
2. **工具调用返回后**：工具输出特别大时立即尝试 Stage 1
3. **用户显式触发**：`/compact` 命令或前端按钮，强制进入 Stage 3
4. **溢出重试**：`emergency_compress()` 触发，`triggered_by = "emergency"`

## 7. 风险与权衡

| 风险 | 缓解 |
|------|------|
| 摘要丢失关键细节 | Stage 3 强制结构化输出；`session_compressions` 保留完整审计；`messages` 不物理删除 |
| 压缩调用本身失败 | 失败时回退到 Stage 1+2 的结果继续推理；不写 DB，不标记消息，下次重试 |
| 用户感知到"Agent 忘了事" | 前端展示压缩分界线 + "查看摘要"按钮；`compression_count` 过高时提示新开会话 |
| 增量摘要累积失真 | `stages_applied` 记录累计次数；超过 3 次压缩时建议用户新开会话 |
| `compressed_message_ids` JSONB 过大 | 单次压缩通常 < 50 条消息；超长会话建议分段压缩 |
