# AIO Agent Platform — 多智能体需求文档

> 为现有智能体系统引入层级化的智能体关系与任务委派机制，支持任务专业化分工和智能体克隆/变体两大场景。

---

## 1. 背景与动机

### 1.1 现状

当前项目的智能体系统是完全扁平的：每个 `Agent` 都是独立实体，拥有自己的 system prompt、模型绑定、工具列表和技能绑定，但智能体之间没有任何关联关系。用户在一个会话中只能与一个智能体交互，无法让智能体之间协作完成更复杂的任务。

### 1.2 需求场景

#### 场景一：任务专业化分工

用户创建一个「项目经理」智能体，同时创建多个专家子智能体（「编码专家」「代码审查员」「测试工程师」）。当用户向「项目经理」发出复杂任务时，项目经理自动将子任务委派给合适的专家子智能体执行，收集结果后综合输出最终答案。

**示例对话**：
```
用户: 帮我写一个用户登录模块，包含后端 API 和前端页面

项目经理（推理）: 这个任务需要分工完成
  → 委派「编码专家」: 编写后端登录 API（JWT 认证、密码哈希、数据库查询）
  → 委派「前端工程师」: 编写 React 登录页面组件（表单、状态管理、API 调用）
  → 委派「测试工程师」: 为上述代码编写单元测试

项目经理（综合）: 以下是完整的登录模块实现方案...
```

#### 场景二：智能体克隆/变体

用户从一个基础「编程助手」智能体派生出多个变体：一个绑定 Python 相关工具用于后端开发，一个绑定前端工具用于 React 开发，一个绑定运维工具用于 DevOps。每个变体继承父级的记忆和人格，但有不同的工具和提示词。

### 1.3 核心约束

- 子智能体**必须**关联到父智能体，父智能体才能使用它
- 父智能体可以同时委派多个子智能体并行执行
- 子智能体与父智能体**共享沙盒环境**，可以直接读写父级创建的文件
- 现有扁平智能体完全不受影响（100% 向后兼容）

## 3. 功能详细需求

### F14. 智能体层级关系

> 在现有扁平智能体模型上引入有向无环图（DAG）层级结构。

**优先级：P0**

#### F14.1 层级关联

**描述**：智能体之间通过 `agent_relationships` 关联表建立多对多层级关系，形成有向无环图（DAG）结构。一个子智能体可以被多个主控智能体关联。

**用户故事**：
- 作为管理员，我可以创建一个「项目经理」智能体，然后在它下面创建「编码专家」「测试工程师」等子智能体。
- 作为管理员，我可以将一个已有的智能体设为另一个智能体的子级。

**验收标准**：
- [ ] 新增 `agent_relationships` 关联表，存储 `(parent_id, child_id)` 多对多关系
- [ ] 一个智能体可以有多个父级（多亲）
- [ ] 一个智能体可以有多个子级
- [ ] 没有父级的智能体为根智能体（向后兼容）
- [ ] 层级深度默认不超过 3 层（可配置）
- [ ] 不允许自引用（不能将自己设为自己的子级）
- [ ] 不允许形成循环引用（A→B→C→A）

#### F14.2 层级验证

**描述**：创建和更新智能体时，自动验证层级关系的合法性。

**验收标准**：
- [ ] 创建/更新关系时验证子智能体存在且处于激活状态
- [ ] 更新关系时检测循环引用，拒绝非法操作
- [ ] 更新时检测是否超过最大深度限制
- [ ] 删除智能体时，自动清理其所有层级关系（parent 和 child 双向）
- [ ] 所有层级验证错误返回清晰的中文错误信息

#### F14.3 层级查询

**描述**：支持查询智能体的层级关系。

**用户故事**：
- 作为管理员，我可以在智能体管理页面看到层级结构。
- 作为用户，我可以在智能体列表中看到哪些智能体有子级。

**验收标准**：
- [ ] 提供接口查询指定智能体的所有子级
- [ ] 提供接口查询指定智能体的完整父级链
- [ ] 提供接口查询以指定智能体为根的完整层级树
- [ ] 智能体列表接口返回 `children_count` 字段
- [ ] 智能体详情接口返回 `children` 子级列表和 `parent` 父级信息

### F15. 任务委派机制

> 父智能体通过工具调用将子任务委派给子智能体执行。

**优先级：P0**

#### F15.1 委派工具（delegate_task）

**描述**：注册一个名为 `delegate_task` 的内置工具，父智能体的 LLM 通过 function calling 决定何时委派、委派给哪个子智能体。

**用户故事**：
- 作为用户，我只需要向父智能体描述任务，它自动判断是否需要委派，不需要我手动指定。

**验收标准**：
- [ ] 工具参数包含 `child_agent_id`（必填，子智能体 UUID）、`task`（必填，任务描述）、`context`（可选，背景上下文）
- [ ] `delegate_task` 仅在父智能体拥有活跃子级时出现在工具列表中
- [ ] 子智能体必须验证调用方是其关联的主控智能体之一，拒绝非法委派
- [ ] 工具执行返回子智能体的最终输出文本

#### F15.2 顺序委派

**描述**：父智能体在一轮 ReAct 迭代中委派一个子智能体，等待结果后决定下一步。

**验收标准**：
- [ ] 委派期间父智能体的 ReAct 循环暂停等待子智能体完成
- [ ] 子智能体的输出作为 `tool_result` 注入父智能体的消息列表
- [ ] 父智能体可以根据子智能体的结果决定是否继续委派其他子智能体
- [ ] 单次委派超时为 300 秒（可配置）

#### F15.3 并行委派

**描述**：父智能体在一轮 ReAct 迭代中同时调用多次 `delegate_task`，多个子智能体并行执行。

**用户故事**：
- 作为用户，我说「帮我同时写前端和后端代码」，父智能体同时委派给前端和后端两个子智能体，并行执行，总时间取决于最慢的那个子智能体，而非两者之和。

**验收标准**：
- [ ] 同一轮迭代中的多个 `delegate_task` 调用并行执行（`asyncio.gather`）
- [ ] 所有并行委派完成后，结果一起注入父智能体的消息列表
- [ ] 某个并行委派失败或超时时，不影响其他并行委派的执行
- [ ] 失败委派返回错误信息给父智能体，让 LLM 决定如何处理

#### F15.4 子智能体执行

**描述**：子智能体收到委派任务后的执行行为。

**验收标准**：
- [ ] 子智能体使用自己的 system prompt（如有），否则继承父级的
- [ ] 子智能体使用自己的模型绑定（如有），否则继承父级的，都没有则使用全局默认
- [ ] 子智能体没有对话历史（任务描述即上下文）
- [ ] 子智能体最大迭代次数为 10（父级为 20），可配置
- [ ] 子智能体在父级的共享沙盒中执行，可以读写父级创建的文件
- [ ] 子智能体可以调用所有已启用的工具（包括沙盒工具）
- [ ] 子智能体在达到最大深度限制时不能继续委派（`delegate_task` 工具被移除）

### F16. 层级管理 UI

> 在前端界面中管理智能体的层级关系。

**优先级：P1**

#### F16.1 智能体管理页面增强

**描述**：在现有的智能体管理页面中增加层级关系的展示和管理功能。

**验收标准**：
- [ ] 智能体列表以层级结构展示（缩进或树形组件）
- [ ] 创建智能体对话框中增加「父智能体」下拉选择器
- [ ] 编辑智能体对话框中可以修改父智能体
- [ ] 父智能体下拉列表中排除自身和自身的子级（防止循环引用）
- [ ] 智能体卡片上显示子智能体数量徽章
- [ ] 删除父智能体时弹出警告，提示子智能体将变为根智能体

#### F16.2 委派过程可视化

**描述**：在聊天界面中实时展示多智能体的委派交互过程。

**用户故事**：
- 作为用户，我能看到父智能体正在委派哪个子智能体、子智能体在做什么、结果是什么。

**验收标准**：
- [ ] 委派开始时，在消息流中插入可折叠的委派卡片，显示子智能体名称和任务描述
- [ ] 委派过程中，卡片内实时显示子智能体的推理过程和工具调用
- [ ] 委派完成后，卡片内显示子智能体的最终输出和执行耗时
- [ ] 并行委派时，多个委派卡片纵向排列，各自独立更新状态
- [ ] 委派卡片支持折叠/展开，默认展示摘要，展开查看完整过程
- [ ] 委派失败时，卡片以红色高亮显示错误信息
- [ ] 委派执行中时，卡片标题栏显示蓝色脉冲动画表示进行中

**UI 设计方案**：

委派卡片嵌入在聊天消息流中，视觉上像一个"子窗口"。每个卡片包含：
- **标题栏**：智能体图标 + 名称 + 状态标识 + 耗时 + 折叠按钮
- **任务描述**：一行摘要
- **展开内容**：推理过程（💭）、工具调用（📋）、结果输出

状态标识规范：

| 状态 | 图标 | 颜色 | 说明 |
|------|------|------|------|
| 执行中 | ⏳ | 蓝色脉冲 | 子智能体正在运行 |
| 完成 | ✅ | 绿色 | 成功返回结果 |
| 失败 | ❌ | 红色 | 执行出错 |
| 超时 | ⚠️ | 橙色 | 超过时间限制 |

### F17. 配置继承规则

> 定义子智能体如何继承或覆盖父智能体的配置。

**优先级：P1**

#### F17.1 配置继承策略

**描述**：子智能体可以选择继承父级配置或使用自己的配置。

| 配置项 | 继承规则 |
|--------|----------|
| 系统提示词 (system_prompt) | 子级有自己的则用自己的；没有则继承父级的 |
| LLM 模型 (model_id) | 子级有自己的则用自己的；没有则继承父级的；都没有则用全局默认 |
| 启用工具 (enabled_tools) | 子级有自己的则用自己的；没有则继承父级的 |
| 绑定技能 (skills) | 子级有自己的绑定技能则用自己的；没有则继承父级的 |
| 沙盒环境 | 始终共享父级沙盒（通过复用 session_id） |
| 用户记忆 | 始终共享用户记忆（同一个 user_id），但用子级的任务描述做搜索查询 |

**验收标准**：
- [ ] 上述每项配置均按规则正确继承或覆盖
- [ ] 继承链支持多层传递（祖父 → 父 → 子，各层正确 fallback）
- [ ] 管理员可以明确看到每个子智能体的配置来源（自有 vs 继承）

### F18. 委派记录与追踪

> 记录每次委派的完整生命周期，用于审计和分析。

**优先级：P1**

#### F18.1 委派记录

**描述**：每次委派调用都持久化到数据库。

**验收标准**：
- [ ] 新增 `delegations` 表，记录：父会话 ID、父智能体 ID、子智能体 ID、用户 ID、委派深度、任务描述、执行状态、执行结果、错误信息、token 用量、执行耗时
- [ ] 委派状态流转：pending → running → completed / failed / timeout
- [ ] 委派记录按 `user_id` 隔离（RLS）
- [ ] 委派记录关联到父级会话，可在会话上下文中查看

#### F18.2 委派历史查询

**描述**：提供 API 查询委派历史。

**验收标准**：
- [ ] 提供接口查询指定会话的所有委派记录
- [ ] 提供接口查询单次委派的详细信息
- [ ] 委派记录包含子智能体名称、任务描述、执行状态、耗时等摘要信息
- [ ] 支持按状态、时间范围过滤

#### F18.3 Token 用量统计

**描述**：子智能体的 token 消耗计入用户的每日用量统计。

**验收标准**：
- [ ] 子智能体执行期间的 prompt_tokens 和 completion_tokens 记录到委派记录中
- [ ] 委派完成后，token 用量合并计入 `token_usage_daily` 表
- [ ] 管理后台可以区分直接调用和委派调用的 token 用量

### F19. 安全与限制

> 防止委派机制被滥用或产生安全问题。

**优先级：P0**

#### F19.1 深度限制

**描述**：限制委派的最大嵌套深度，防止无限递归。

**验收标准**：
- [ ] 默认最大深度为 3 层（可通过配置修改）
- [ ] 三层防护机制：
  - 工具过滤层：达到最大深度时从工具列表移除 `delegate_task`
  - Handler 验证层：处理函数中检查当前深度
  - 数据库约束层：`delegations` 表 CHECK 约束 `depth <= 10`
- [ ] 深度限制触发时返回清晰的错误信息

#### F19.2 循环引用防护

**描述**：防止智能体层级形成循环。

**验收标准**：
- [ ] 创建/更新智能体时，遍历 parent 链检测循环
- [ ] 循环检测在数据库写入之前完成（应用层校验）
- [ ] 检测到循环时返回 400 错误和清晰的中文提示

#### F19.3 资源限制

**描述**：限制委派执行的资源消耗。

**验收标准**：
- [ ] 单次委派超时 300 秒（可配置）
- [ ] 子智能体最大迭代次数为 10（父级为 20，可配置）
- [ ] 子智能体继承父级的 trust_level 安全设置
- [ ] 所有委派操作记录审计日志

#### F19.4 权限控制

**描述**：委派的权限边界。

**验收标准**：
- [ ] 子智能体只能被其父智能体委派（不能跨级委派）
- [ ] 只有管理员可以创建/修改智能体的层级关系
- [ ] 普通用户只能查看智能体列表（包含层级信息），不能修改
- [ ] 委派操作受 RLS 保护，按 `user_id` 隔离

## 4. 非功能需求

### 4.1 性能

- 单次委派的额外开销（不含子智能体执行时间）应小于 200ms
- 并行委派的总时间取决于最慢的子智能体，而非所有子智能体时间之和
- SSE 事件流中委派事件的传输延迟小于 100ms

### 4.2 可观测性

- 所有委派操作有结构化日志记录（structlog）
- 委派记录包含完整的执行元数据（耗时、token 用量、状态）
- 异常和超时有独立的日志级别标记

### 4.3 向后兼容

- 现有智能体无层级关系，行为完全不变
- 现有 API 端点的请求和响应格式保持兼容（新增字段为可选）
- 现有 SSE 事件类型不受影响（委派事件为新增类型）
- 现有前端代码不处理 `delegation_*` 事件时不影响正常使用

## 5. 未来扩展（不在本期范围）

- **跨用户智能体共享**：允许用户 A 的智能体委派给用户 B 的智能体
- **委派结果缓存**：相同任务委派给相同子智能体时复用历史结果
- **动态子智能体创建**：父智能体在运行时自动创建专家子智能体
- **委派编排策略**：管理员可配置委派策略（如：总是先委派给 A，A 失败再委派给 B）
- **委派成本预算**：为每次委派设置 token 预算上限
