# 文档与图片工具

## 功能与默认依赖

新增四个内置工具，沿用智能体工具白名单、当前工作区、沙箱执行和文件产物展示。

| 工具 | 默认支持 | 返回内容 |
| --- | --- | --- |
| `read_document` | PDF、扫描 PDF、DOCX、XLSX、PPTX、常见图片 OCR | 带来源位置的文本/表格单元格块、覆盖范围、翻页游标 |
| `document_search` | 在上述格式的指定范围内做不区分大小写的字面检索 | 原文片段、页码/章节/段落/单元格/幻灯片位置 |
| `render_document` | PDF 页面渲染 | 工作区 PNG 路径、页码和尺寸；作为文件产物展示 |
| `view_image` | PNG、JPEG、WebP、GIF、BMP、TIFF | 元数据进入工具结果，实际图像通过临时多模态消息发送给视觉模型 |

默认镜像**不安装 LibreOffice**。解析使用 pdfplumber、python-docx、openpyxl、python-pptx；PDF 渲染使用 PDFium；OCR 使用 Tesseract 及中英文语言包。

Office 版式渲染、Word 按页读取、旧版 DOC/XLS/PPT 转换是可选能力，使用 LibreOffice。未启用时返回明确错误，提示使用原生 DOCX/XLSX/PPTX 读取或上传 PDF，不生成冒充原始版式的简化截图。

## 使用方式

用户仍通过会话上传文件；智能体使用返回的 `uploads/...` 工作区相对路径。也接受指向当前工作区的 `/workspace/{workspace_slug}/...` 路径，不接受其他工作区路径。

```json
{"path":"uploads/report.pdf","start_page":1,"end_page":5,"ocr":"auto"}
```

```json
{"path":"uploads/contract.docx","section":"预算说明","offset":0,"limit":40}
```

```json
{"path":"uploads/budget.xlsx","sheet":"预算表","cell_range":"A1:H100"}
```

```json
{"path":"uploads/slides.pptx","start_page":2,"end_page":4}
```

`document_search` 在同样的选择参数上增加 `query`：

```json
{"path":"uploads/contract.docx","query":"付款条件","offset":0,"limit":20}
```

检查 PDF 版式时先调用 `render_document`：

```json
{"path":"uploads/report.pdf","start_page":1,"end_page":2,"dpi":120}
```

再把返回的 `document-renders/{id}/page-1.png` 传给 `view_image`。渲染本身不要求视觉模型；查看图像要求当前模型配置 `is_multimodal=true`。非视觉模型会得到明确失败，不会假装已经看过图片；文字识别可继续使用 `read_document`。

## 来源和分页约定

- PDF：`location.page` 为 1 开始的原始页码；可识别表格返回 table/row/column/bbox（单位 pt）。扫描件返回 `ocr_text`，不保证恢复表格单元格。
- DOCX：保留正文顺序，返回章节路径、段落号和表格单元格位置。`section` 按标题精确匹配，包含子章节。页码需要可选 Office 转换，属于 LibreOffice 分页，可能与 Word 不同。
- XLSX：保留工作表、单元格坐标和公式表达式；不计算公式。默认仅首个工作表的前 200 行、50 列，覆盖范围明确返回。扩大检索需选择其他工作表或范围。
- PPTX：页码对应幻灯片号，返回形状和段落位置。原生文本读取不识别嵌入图片、图表中的文字；需要时渲染或自行上传对应图片/PDF。
- DOCX 原生读取覆盖正文段落和表格；页眉、页脚、文本框等版式内容需要渲染检查。
- `offset/next_offset` 是同一选择范围中的块游标；继续调用必须保持路径、页码、章节、工作表与查询不变。`next_page` 用于继续选择下一批页面。
- `document_search` 只检索返回的 `coverage` 范围，不能将某个页码范围或工作表内没有匹配描述为全文没有匹配。每个匹配块返回一段上下文。

## OCR 与资源限制

- `ocr=auto`：对无文本 PDF 页面启用 OCR；图文混排中已有文本但仍需识别图片文字时，用 `ocr=always`。
- `ocr=never`：关闭 PDF OCR。直接读取图片文字必须启用 OCR。
- `ocr_language` 支持 `chi_sim+eng`（默认）、`chi_sim`、`eng`。
- `ocr_layout` 支持 `auto`（自动布局，空结果尝试单文本块）、`block`（单文本块）、`sparse`（散布文字）。简单扫描页漏字时可换用 `block`。OCR 内容带警告，不承诺零误识别。
- 输入最大 50 MiB；Office ZIP 解包声明总大小最大 200 MiB。
- PDF/PPT 默认读取最多 10 页，每次最多 20 页；渲染默认 1 页，每次最多 5 页。
- XLSX 每次最多选择 20,000 个单元格。
- 每次最多返回 100 块并应用约 32,000 字符的内容预算；长段落分块，可继续分页读取。
- 图片和渲染页面最多 2,500 万像素；`view_image` 将最长边缩至 2048 像素，按 EXIF 方向处理并以白色合成透明背景。动画、多帧图片只查看第一帧。
- 渲染 DPI 为 72–144，默认 120。worker 总时间预算 170 秒，Office 子进程最多 90 秒，单次 OCR 最多 45 秒。

## 执行与数据边界

`document_tools.py` 定义 Schema，`document_runtime.py` 为独立 worker；ToolExecutor 将 worker 及参数编码后在沙箱执行，不在 API 宿主机运行文档解析器。所有依赖均预装，不在每次对话中自动安装。

模型调用仍经过现有 `allowed_tools` 检查。worker 解析真实路径，拒绝越过当前工作区的路径和符号链接，渲染只写入工作区 `document-renders/` 下的随机子目录。

`view_image` 的 Base64 仅暂存于 ToolResult 的非展示字段，AgentLoop 在所有 tool 回复之后追加 provider 对应的图像消息，并立即清空临时字段。工具文本、SSE、会话记录不包含图片 Base64；模型调用的 Langfuse 脱敏复用现有图像清理逻辑。安全续跑时重新读取图像，不复用只有元数据的历史缓存。

上传流程同步修复了旧沙箱调用：Web 与渠道上传在对象存储写入后，通过 `inject_uploaded_file` 按用户查找现有沙箱，分块写入正确的工作区。没有运行中的沙箱时不启动容器，由下次初始化载入上传文件。渲染产物沿用既有工作区文件同步与预览机制。

## 构建与启用

默认轻量沙箱：

```bash
docker build -t aio-agent-platform-sandbox:documents backend/sandbox
```

需要可选 Office 版式渲染时：

```bash
docker build --build-arg INSTALL_OFFICE_RENDERER=true \
  -t aio-agent-platform-sandbox:documents-office backend/sandbox
```

部署时将 `SANDBOX_IMAGE` 指向对应镜像并使用新镜像创建沙箱。运行中的旧容器不会自动获得依赖，切换前应通过现有生命周期同步文件；不要直接删除仍有未同步文件的容器。原有配置若明确列出了 `enabled_tools`，需勾选新增工具。查看图片还需选择已开启视觉能力的模型。无需数据库迁移。

## 验证

`backend/tests/test_document_tools.py` 使用真实 DOCX、XLSX、PPTX、文本 PDF、扫描 PDF 和图片样例，覆盖范围读取、来源位置、表格、检索、分页、实际 PNG/JPEG、Office 可选依赖、权限、路径与符号链接、模型图片注入和日志隔离。

Office 渲染测试需要本机安装 LibreOffice，OCR 测试需要 Tesseract；未安装时明确跳过。`test_sandbox_lifecycle.py` 的上传同步测试使用模拟 Docker，覆盖不启动新容器、正确工作区和重启后发现容器。

本次已验证本机 Office 转换、英文扫描件 OCR、中文扫描件识别及前端构建。当前 Docker 服务未启动，因此尚未验证镜像构建、真实 Docker/MinIO 联动和真实模型端到端调用，不能把本地测试当作已部署成功。
