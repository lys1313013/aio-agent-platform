# 智能体协作聊天室 — 需求文档

> 版本：1.0（MVP 需求草案）
> 日期：2026-09-12
> 范围：一个用户与多个已有智能体在同一聊天室内协作
> 状态：待开发；本文描述目标行为，不代表功能已实现

## 1. 背景与目标

当前平台提供单智能体会话，以及父智能体通过 `delegate_task` 调用子智能体的能力。用户需要多个专业视角时，仍缺少一个能直接邀请成员、点名提问、交叉评审和保留共同讨论记录的入口。

聊天室围绕一个持续的讨论目标组织多个已有智能体。用户控制谁发言，成员能够阅读此前的公开讨论，并保留各自的专业身份、模型和授权能力。

| 要解决的问题 | 目标行为 |
|---|---|
| 在不同智能体之间反复复制背景材料 | 同一房间共享目标、讨论记录和授权附件 |
| 单个智能体难以覆盖多个专业视角 | 邀请产品、架构、测试等成员分别提出意见 |
| 委派结果不便直接追问 | 每个房间成员拥有独立发言身份，可被用户直接点名 |
| 多份回答重复或冲突，需要用户自行整理 | 指定成员总结共识、分歧、待确认事项和下一步 |
| 多智能体执行难以控制成本和进度 | 明确本次接收成员、执行顺序、停止入口和用量 |
| 长期讨论缺少连续性 | 保存房间、成员变动、消息和产物，支持后续继续讨论 |

首要验收场景为需求评审；方案比较、资料研究和故障分析可使用相同流程。

## 2. 开源项目参考

以下根据本次调研读取的官方文档整理，侧重功能相关性，不作热度排名。借鉴产品和编排思路，不要求引入这些框架。

| 项目 | 参考能力 | 本项目的采用方式 |
|---|---|---|
| [Open WebUI Channels](https://docs.openwebui.com/features/channels/) | 多个人类和模型共享对话空间，使用 `@model` 按需触发回答 | 借鉴成员身份、点名交互、共享上下文；MVP 只支持一个人类用户 |
| [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html) | 根据角色和历史选择下一位发言者，并设置终止条件 | MVP 使用确定的发言顺序；后续自动讨论参考其选择与终止机制 |
| [LangGraph Supervisor](https://github.com/langchain-ai/langgraph-supervisor-py) | 主持人协调专业智能体，可选择共享完整历史或最终回复 | 借鉴上下文分层和后续主持人模式；其仓库建议多数场景直接用工具实现 supervisor 模式 |
| [MetaGPT](https://github.com/FoundationAgents/MetaGPT) | 按产品、架构、工程等角色组织流程和交付物 | 借鉴角色分工和明确产出，后续提供团队模板 |

## 3. 版本范围

### 3.1 MVP 必须支持

- 一个房间归属于一个用户，邀请该用户当前有权使用的已有智能体。
- 创建、重命名、置顶、归档房间；添加和移除成员。
- 单成员点名、多成员点名、全体回答、默认成员回答。
- 成员顺序执行、共享公开上下文、引用消息追问、手动触发总结。
- 流式消息、工具执行详情、用户确认、停止执行、失败重试和历史恢复。
- 沿用现有附件、工作区文件产物和权限能力。

### 3.2 MVP 不包含

- 多个人类用户入群、公开房间、跨租户共享、外部渠道群聊。
- 智能体自动互相点名、自动主持、多轮自主讨论、成员并行执行。
- 房间内创建临时智能体、嵌套子智能体委派和自动拉入新成员。
- 独立话题分支、消息编辑后重算下游、自动重放工具副作用。
- 将已有单聊直接转换为群聊、群聊专属长期记忆和新的文件版本系统。

这些限制仅作用于聊天室；现有单聊和父子智能体委派行为保持兼容。

## 4. 核心概念与默认规则

| 概念 | 定义与规则 |
|---|---|
| 聊天室 | 持久保存讨论目标、成员和消息的会话，归属于创建用户 |
| 房间成员 | 被邀请的已有智能体；无需预先建立父子关系 |
| 默认回答成员 | 未点名时接收用户消息的成员，不自动调度其他成员 |
| 一次运行 | 用户一次发送或点击总结所触发的一组成员执行 |
| 成员任务 | 一次运行中一个成员的执行，可包含多次模型和工具调用 |
| 公开消息 | 房间中可供其他成员读取的用户消息和成员最终发言 |

- 创建时选择 1～5 个不同智能体；同一个智能体不能重复加入。
- 默认回答成员初始为第一个选中的成员，用户可以修改。
- 一个房间同一时间只允许一次运行；运行期间可编辑输入草稿，不能提交新任务。
- 一次运行中，每个被选中的成员最多执行一个成员任务；不自动开启下一轮。
- 成员任务内部沿用现有 AgentLoop 的迭代、超时和用量限制；不允许调用 `delegate_task` 扩大本次执行范围。
- 添加/移除成员、修改目标和默认回答成员仅在房间空闲时生效，避免运行中的上下文和队列发生变化。

## 5. 功能需求

### R01 创建与管理聊天室

- 在现有会话入口增加“新建聊天室”，会话列表能区分单聊和聊天室。
- 创建表单包含房间名称、讨论目标、成员选择和默认回答成员；名称未填写时可使用默认名称，讨论目标必填。
- 成员选择只展示当前用户有权使用且可运行的智能体，显示名称、头像和职责描述。
- 支持重命名、置顶、归档和恢复；归档房间保留历史，恢复后才能继续执行。
- 支持沿用现有会话删除交互删除空闲房间，不提供删除正在运行房间的入口。

### R02 成员管理

- 展示成员名称、头像、职责和当前状态；普通用户不因此获得查看系统提示词、凭据或工具配置的权限。
- 添加成员后，该成员可使用房间目标、历史摘要和近期公开记录接上讨论；不自动导入任何私聊历史。
- 成员加入、移除、默认回答成员变更均保留系统记录。
- 移除成员不删除历史消息；历史发言保留当时的名称和头像信息。
- 移除默认回答成员时必须同时指定另一位有效成员；至少保留一位成员。
- 智能体被删除、停用或权限被撤销时显示“不可用”，历史消息仍可阅读；再次执行前重新校验权限。

### R03 选择发言成员

| 用户操作 | 接收与执行规则 |
|---|---|
| 从 `@` 候选中选择一个成员 | 只执行该成员 |
| 选择多个 `@` 成员 | 按用户点名顺序执行，每位成员一次，重复点名去重 |
| 在输入框中选择 `@全体成员` | 按成员列表顺序执行所有有效成员，每位一次 |
| 不点名且未插入 `@全体成员` | 由默认回答成员执行 |

- 在消息输入框输入 `@` 弹出成员候选，支持搜索、方向键选择、Enter 确认，并将选中成员高亮插入正文；不设置独立的点名选择框或全体回答开关。
- 输入框在发送前显示实际接收对象及顺序；`@全体成员` 与具体成员点名互斥，删除或修改点名文本同步取消对应接收对象，草稿保留点名绑定。
- 点名基于成员标识，不靠名称字符串推断；仅粘贴普通 `@名称` 文本不自动改变接收对象。
- 引用回复不自动改变接收对象，仍以上述显式选择为准。
- 智能体输出中的 `@` 仅展示为文本，不触发新的成员任务。
- 提交时发现指定成员不可用，应拒绝本次提交并提示调整；全体回答需明确显示被排除的不可用成员。
- 提交成功后冻结本次目标成员和顺序；排队期间成员权限变化时，将对应任务标记失败并继续处理其余有效成员。

### R04 共享上下文与引用追问

- 每个成员使用自己的专业身份和系统配置；房间目标及其他成员发言作为讨论材料，不能覆盖平台权限约束。
- 输入上下文包含房间目标、成员职责、历史摘要、近期公开消息、本次问题和被引用内容。
- 后发言成员能够读取本次运行中前序成员已完成的公开发言；界面说明全体回答为依次回答。
- 其他成员发言保留来源，不伪装成当前智能体自己的历史回答。
- 支持引用一条已有消息并附带问题，引用展示来源成员和原消息入口。
- 工具详细日志和内部执行记录不默认广播给其他成员；公开发言可包含必要结论、来源和产物引用。
- 历史超过上下文预算时保留摘要和近期记录；当前问题、房间目标和引用内容优先。引用过长需要截取时应明确标识，不能声称已完整阅读。
- 失败或停止产生的部分回复保留状态标识，不作为已经完成的结论；必要时将“该成员未完成”提供给后续成员。

### R05 共享附件与文件产物

- 用户上传的附件可在本房间内供授权成员使用，限制沿用当前上传和存储规则。
- 文件读取和写入必须同时满足用户、智能体工具和当前工作区权限；邀请成员不扩大资源访问范围。
- 不支持某类附件的成员应说明能力限制，不虚构读取结果。
- 成员产生的文件变更附着在该成员消息下，支持现有预览和下载能力。
- 房间内顺序执行，避免同一轮多个成员同时修改同一文件；其他会话对工作区的并发访问仍遵循平台现有机制，不承诺全局文件锁。
- 文件链接读取当前文件，文件删除后提示不可用，遵循现有文件产物模块规则。

### R06 总结讨论

- 用户点击“总结讨论”后选择一个有效成员，默认选中默认回答成员。
- 总结属于一次新的运行，只调用所选成员，不自动邀请其他成员补充。
- 总结内容包含：讨论目标、已有共识、存在分歧及来源、待确认事项、建议下一步。
- 无充分依据时明确写“尚未达成共识”；不能把多数成员重复同一说法视为事实验证。
- 上一轮存在失败、停止或未完成成员时，总结指出缺失意见。
- 总结作为普通消息保存在房间中，支持引用和继续追问；待办为建议，不自动创建外部任务或执行操作。

### R07 执行状态、确认与停止

- 房间展示当前执行成员及等待队列，每个成员任务显示等待、执行中、等待用户、完成、失败、已取消或已停止状态。
- 文本流、工具详情、确认卡片和文件变更必须归属于具体成员及其任务。
- 成员发起用户确认时暂停该任务及后续队列；只有当前房间所属用户可以回答。
- 用户答复只恢复对应任务；重复提交不得重复恢复。拒绝按现有确认机制处理，不将拒绝视为同意。
- 点击“停止”后立即阻止后续成员启动，并请求终止当前任务；未结束前显示“停止中”。
- 已完成的消息和工具动作不回滚；无法立即取消的外部操作需要显示真实状态，不能提示已撤销。
- 停止使未答复确认失效，迟到的确认或旧任务输出不得重新启动队列或覆盖新任务状态。

### R08 异常、重试与恢复

- 单个成员失败时保留失败原因和已有输出，其余成员可继续；全部失败显示失败，部分失败显示部分完成。
- 支持单独重试失败成员，作为新的运行记录追加，保留原失败记录；不重新执行原运行中的其他成员。
- 重试使用原始问题、引用和截至原成员任务开始时的公开上下文；资源访问仍按当前权限校验，文件仍为当前版本。
- 有写文件、外部请求等副作用已完成或结果不明时，重试前展示相关记录，由用户确认是否重新执行；不得自动重放。
- 停止的任务不自动续跑，用户可根据已有部分结果重新发起问题。
- 页面刷新或断网不视为用户停止；恢复连接后加载消息及当前运行状态，不重复提交原请求。
- 服务重启后若无法继续原任务，应明确标记执行中断并允许适用的失败重试；MVP 不承诺自动从任意工具步骤恢复。
- 同一发送请求重复到达时不得重复创建运行；重复、迟到的流式事件不得导致消息重复或串到其他成员。

### R09 历史、权限与用量

- 持久保存成员变动、消息身份、引用关系、执行顺序、任务状态及停止原因；刷新前后展示一致。
- 房间、运行、消息、确认、事件订阅和附件访问均校验所属用户及租户；仅知道标识不能获得访问权。
- 成员继续运行前重新校验权限，不因曾经加入房间而长期保有授权。
- 记录每个成员任务及整次运行的 Token 用量和耗时；供应商缺少用量时显示“未知”，不能记为零。
- 用量和配额沿用现有平台规则；房间运行不能绕过配额，达到执行上限时显示明确原因。

## 6. 页面与示例流程

### 6.1 页面布局

- 左侧：会话列表，聊天室标识、新建、重命名、置顶和归档入口。
- 顶部：房间名称、目标、成员头像、成员管理入口和当前运行状态。
- 中间：统一消息时间线，成员头像和名称常显；工具及执行详情折叠在所属消息下。
- 底部：文本与附件输入、引用预览、`@成员`、全体回答、接收顺序、总结和停止入口。
- 运行期间保留输入草稿，提供“停止后继续提问”的明确提示；不隐式排队新问题。

### 6.2 需求评审示例

1. 用户创建“订单系统需求评审”，填写目标，邀请产品助手、架构助手、测试助手。
2. 上传需求文件，发送“@产品助手 请整理用户场景和待确认问题”。
3. 产品助手独立回复，其他成员不运行。
4. 用户引用其中一个场景，发送“@架构助手 @测试助手 请分别评估实现难点和遗漏”。
5. 架构助手先回答；测试助手读取其公开意见后补充测试视角。
6. 用户点击“总结讨论”，选择产品助手，得到共识、分歧和建议待办。
7. 用户归档房间，之后可恢复并邀请新成员继续讨论。

## 7. 与现有系统的衔接要求

以下为实现必须满足的边界，具体表结构、API 和调度方案在技术方案中确定。

| 现有能力 | 衔接要求 |
|---|---|
| Session / Message | 区分单聊与聊天室；群消息必须能识别成员、引用、所属运行和稳定顺序 |
| Agent 与父子委派 | 新增独立的房间成员关系，不要求修改智能体原有父子关系 |
| AgentLoop / ToolExecutor | 复用执行和权限能力；房间层控制顺序，聊天室任务禁用嵌套委派 |
| 会话历史与上下文压缩 | 按当前成员构建上下文，保留发言者身份和摘要来源 |
| SSE 与聊天状态管理 | 事件可定位房间、运行、成员和消息，支持重连后的状态恢复和去重 |
| AskUserQuestion | 确认绑定具体成员任务；沿用 AgentLoop 拦截流程，不在工具执行器中阻塞等待 |
| 工作区和附件 | 复用权限、上传、预览及文件变更记录，不增加隐式资源共享权限 |
| 日志与用量 | 能从一次运行追踪到每个成员任务、模型调用、工具结果和错误 |

## 8. 验收标准

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A01 | 创建房间 | 可选择 1～5 个不同的可用智能体；无权限成员不能通过直接请求加入 |
| A02 | 单成员点名 | 点名 A 时，仅 A 发生模型与工具调用，B 不执行 |
| A03 | 多成员点名 | 点名 B、A、B 后按 B→A 各执行一次，界面显示相同顺序 |
| A04 | 全体与默认回答 | 全体按展示顺序各回答一次；不点名仅默认成员回答；发送前显示接收对象 |
| A05 | 禁止自动扩展 | 成员输出 `@B` 不触发 B，模型无法通过委派工具启动额外智能体 |
| A06 | 共享与引用 | B 能引用 A 已完成的公开意见，并识别其来源；用户引用可跳转原消息 |
| A07 | 成员变动 | 新成员可依据房间摘要继续讨论，无法读取其他私聊；移除成员后历史身份保留 |
| A08 | 总结 | 只运行指定成员，输出共识、分歧、待确认事项和下一步，并注明缺失意见 |
| A09 | 用户确认 | 确认期间后续成员不启动，答复仅恢复对应任务，重复答复不重复执行 |
| A10 | 用户停止 | 后续成员不再启动，当前部分消息有停止标识，已完成工具动作不被声称回滚 |
| A11 | 单成员失败 | 失败原因可见，其他成员可继续；重试只追加该成员的新任务，副作用不自动重放 |
| A12 | 刷新与重连 | 消息身份、引用和状态恢复一致；重复发送、重连及重复事件不造成重复运行或消息 |
| A13 | 服务中断 | 无法恢复的运行明确显示中断，不永久显示执行中、不静默重跑 |
| A14 | 权限变化 | 排队期间撤销权限后，对应成员不能执行；越权读取消息、确认、事件和附件均被拒绝 |
| A15 | 文件与用量 | 文件产物归属正确成员；用量按成员和运行汇总，缺失用量显示未知 |
| A16 | 并发提交 | 同一房间已有运行时，新提交被明确拒绝并保留草稿，多标签页不能绕过限制 |
| A17 | 单聊兼容 | 原有单聊、子智能体委派、用户确认和历史读取继续按原有方式工作 |

## 9. 后续演进

| 阶段 | 目标 | 前置条件 |
|---|---|---|
| MVP | 用户控制的多智能体协作聊天室 | 完成本文全部验收项 |
