# 表格录入交互（Table Input）技术方案

## 1. 背景与目标

当前智能体已支持"选择框"交互：通过内置工具 `AskUserQuestion`，配合内存级 `ConfirmationManager`（`asyncio.Event`），实现"弹出卡片 → 暂停对话 → 等待用户操作 → 恢复对话"的闭环。已有 4 种 mode：`single_select`、`multi_select`、`free_input`、`approve`。

本方案新增第 5 种 mode：**`table_input`（表格录入）**。智能体可以弹出一个**可编辑表格**，让用户按列定义逐行填写数据并提交，提交结果以结构化数据回传给智能体继续推理。

设计原则：**复用现有"暂停-恢复"基础设施，只新增一个 mode，不改核心流程。** SSE 转发、`ConfirmationManager`、REST 回传 API 都是 mode-agnostic 的，会自动支持新 mode。

---

## 2. 整体数据流（复用现有机制）

```
LLM 调用 AskUserQuestion(mode=table_input, table_schema=[...], rows=[...])
   │
   ▼
agent.py 拦截 → _run_ask_user_flow
   │  Step1 create_confirmation（存内存）
   │  Step2 push {type:'confirmation_required', mode:'table_input', table_schema, rows} → event_queue
   │  Step2 yield 'confirmation_flow:...:waiting'（让 SSE drain）
   ▼
SSE generator drain event_queue → 前端收到 confirmation_required 事件
   │
   ▼
前端 ConfirmationCard 按 mode 分发 → 渲染 <TableInputCard>（antd Table 可编辑）
   │  用户增删行、逐格填写
   │  点击「提交」→ confirmationsApi.respond(id, {status:'approved', table_data:[...]})
   ▼
POST /api/confirmations/{id}/respond
   │  confirmation_manager.resolve_confirmation → event.set()
   ▼
agent.py Step3 wait_for_response 解除阻塞
   │  Step4 push {type:'confirmation_resolved', table_data} → event_queue
   │  Step5 _format_ask_user_output → 把表格格式化为 markdown 表喂给 LLM
   ▼
LLM 看到表格数据，继续下一轮推理
```

**关键点**：用户提交走的是独立的 REST 请求；原 SSE 流一直挂着（agent 协程阻塞在 `wait_for_response`），REST 请求 `set` event 后原 SSE 流自然继续流式输出。这是现有架构已验证的"两个 HTTP 请求协作"设计，本方案完全沿用。

---

## 3. 表格列定义（table_schema）

智能体调用工具时通过新参数 `table_schema` 定义表格有哪些列。每一列字段如下：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `key` | string | 是 | 列的唯一标识，作为提交数据每行对象的 key |
| `title` | string | 是 | 列显示名（表头） |
| `type` | enum | 否 | 单元格类型：`text`(默认) / `number` / `date` / `select` / `boolean` |
| `required` | boolean | 否 | 该列是否必填，默认 `false`。提交前做非空校验 |
| `default` | any | 否 | **该列默认值**，新增行时自动填入 |
| `options` | string[] | 否 | 当 `type=select` 时的可选项 |
| `placeholder` | string | 否 | 输入提示文案 |
| `width` | number | 否 | 列宽（px），不填则自适应 |

并新增控制整张表的可选参数：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `rows` | object[] | `[]` | **初始行数据（默认值）**，每行是 `{key: value}`。智能体可预填若干行供用户修改 |
| `min_rows` | number | `1` | 最少行数，低于此数不允许删行、提交时校验 |
| `max_rows` | number | 无限制 | 最多行数，达到后禁用「增行」 |
| `allow_add_row` | boolean | `true` | 是否允许用户增行 |
| `allow_delete_row` | boolean | `true` | 是否允许用户删行 |

### 默认值的两个层级

1. **列默认值** `column.default`：用户点「新增行」时，新行该列自动填入此值。
2. **预填行** `rows`：智能体可以直接给出几行已填好的数据作为草稿，用户在此基础上修改 / 增删。

### 示例（报销明细录入）

```json
{
  "question": "请填写本次报销的明细",
  "mode": "table_input",
  "table_schema": {
    "columns": [
      { "key": "item",    "title": "费用项目", "type": "text",   "required": true,  "placeholder": "如：高铁车票" },
      { "key": "amount",  "title": "金额(元)", "type": "number", "required": true,  "default": 0 },
      { "key": "date",    "title": "发生日期", "type": "date",   "required": true,  "default": "2026-06-08" },
      { "key": "category","title": "类别",     "type": "select", "default": "交通",
        "options": ["交通", "餐饮", "住宿", "办公", "其他"] },
      { "key": "remark",  "title": "备注",     "type": "text",   "required": false, "default": "" }
    ],
    "rows": [
      { "item": "高铁车票", "amount": 553, "date": "2026-06-05", "category": "交通", "remark": "上海→北京" }
    ],
    "min_rows": 1,
    "max_rows": 20,
    "allow_add_row": true,
    "allow_delete_row": true
  },
  "context": { "risk_level": "low", "category": "clarify", "timeout_seconds": 600 }
}
```

用户提交后回传：

```json
{
  "status": "approved",
  "table_data": [
    { "item": "高铁车票", "amount": 553, "date": "2026-06-05", "category": "交通", "remark": "上海→北京" },
    { "item": "酒店住宿", "amount": 480, "date": "2026-06-05", "category": "住宿", "remark": "1晚" }
  ]
}
```

## 4. 后端改动清单

### 4.1 工具 Schema — `tools/builtin.py`（`ASK_USER_QUESTION`，约 462-540 行）

- mode enum（480 行）增加 `"table_input"`：
  ```python
  "enum": ["single_select", "multi_select", "free_input", "approve", "table_input"],
  ```
- properties 中新增 `table_schema` 字段（仅 `table_input` 用），定义 `columns` / `rows` / `min_rows` / `max_rows` / `allow_add_row` / `allow_delete_row`，结构见第 3 节。
- 更新 `description`，告知 LLM 新增了 table_input 模式及其用途（结构化批量数据录入，支持列默认值和预填行）。

### 4.2 确认流程 — `core/agent.py`

- `_run_ask_user_flow`（473-580 行）：
  - Step1 `create_confirmation` 时把 `table_schema` 一并存入（透传，见 4.4）。
  - Step2 推送 `confirmation_required` 事件（521-532 行）时带上 `table_schema`。
  - Step4 推送 `confirmation_resolved` 事件（570-577 行）时带上 `table_data`。
- `_format_ask_user_output`（59-105 行）：新增 `table_input` 分支，把 `response["table_data"]` 渲染为 **markdown 表格文本**喂给 LLM。空表 / rejected 走对应提示。示例输出：
  ```
  User submitted the following table (2 rows):
  | 费用项目 | 金额(元) | 发生日期 | 类别 | 备注 |
  | --- | --- | --- | --- | --- |
  | 高铁车票 | 553 | 2026-06-05 | 交通 | 上海→北京 |
  | 酒店住宿 | 480 | 2026-06-05 | 住宿 | 1晚 |
  ```
  （列标题用 `table_schema.columns[].title`，按 `key` 取值。）

### 4.3 REST 回传 — `interface/routes/confirmations.py`

- `ConfirmResponseRequest`（24-29 行）新增字段：
  ```python
  table_data: list[dict] | None = None
  ```
- `respond_to_confirmation`（61-68 行）response dict 透传 `table_data`：
  ```python
  response={
      "status": body.status,
      "selected_options": body.selected_options or [],
      "user_input": body.user_input,
      "table_data": body.table_data,
  }
  ```
- `PendingConfirmationResponse`（39-48 行）新增 `table_schema: dict | None`，并在 `get_pending`（84-94 行）回填 —— 用于页面刷新后恢复未决表格。

### 4.4 确认管理器 — `core/confirmation.py`

- `PendingConfirmation` dataclass 新增字段 `table_schema: dict | None = None`。
- `create_confirmation(...)` 增加 `table_schema` 形参并存储。
- **无需改动** `wait_for_response` / `resolve_confirmation`（response 是 `dict[str, Any]`，已通用）。

## 5. 前端改动清单

### 5.1 类型 — `frontend/src/lib/types.ts`（约 364-406 行）

```ts
export type ConfirmationMode =
  | 'single_select' | 'multi_select' | 'free_input' | 'approve' | 'table_input';

export type TableColumnType = 'text' | 'number' | 'date' | 'select' | 'boolean';

export interface TableColumnDef {
  key: string;
  title: string;
  type?: TableColumnType;
  required?: boolean;
  default?: unknown;
  options?: string[];
  placeholder?: string;
  width?: number;
}

export interface TableSchema {
  columns: TableColumnDef[];
  rows?: Record<string, unknown>[];
  min_rows?: number;
  max_rows?: number;
  allow_add_row?: boolean;
  allow_delete_row?: boolean;
}

// ConfirmationRequest 增加：
//   table_schema?: TableSchema;
// ConfirmationResponse 增加：
//   table_data?: Record<string, unknown>[];
// ConfirmationResolvedInfo 增加：
//   table_data?: Record<string, unknown>[];
```

### 5.2 SSE 事件处理 — `frontend/src/pages/AgentChatPage.tsx`

- `case 'confirmation_required'`（约 339-358 行）：把 `event.table_schema` 一并存入 `streaming.confirmations`。
- `case 'confirmation_resolved'`（约 360-374 行）：把 `event.table_data` 存入 `confirmationsResolved`。
- 对应的 SSE 事件类型 union（types.ts 约 94-137 行）补上 `table_schema` / `table_data` 字段。

### 5.3 新建组件 — `frontend/src/components/confirmation/TableInputCard.tsx`

参考 `FreeInputCard.tsx` 结构，用 **antd `Table`** 渲染可编辑表格：

- 初始 state = `table_schema.rows`（深拷贝），为空则按 `min_rows` 生成默认行（每列填 `column.default`）。
- 单元格按 `column.type` 渲染编辑控件：`text→Input`、`number→InputNumber`、`date→DatePicker`、`select→Select(options)`、`boolean→Switch`。`placeholder` 透传。
- 操作列：每行一个「删除」按钮（`allow_delete_row` 且行数 > `min_rows` 时可用）；表底一个「+ 新增行」按钮（`allow_add_row` 且行数 < `max_rows` 时可用），点击时新行各列填入 `column.default`。
- 提交前校验：所有 `required` 列非空、行数 ≥ `min_rows`，否则禁用「提交」并提示。
- 「提交」→ `onSubmit({ status: 'approved', table_data: rows })`；「跳过」→ `onSubmit({ status: 'rejected' })`。

### 5.4 分发器 — `frontend/src/components/confirmation/ConfirmationCard.tsx`（约 95-104 行）

增加分支：
```tsx
if (mode === 'table_input') {
  return <TableInputCard schema={request.table_schema!} onSubmit={handleSubmit} />;
}
```
并在 `frontend/src/components/confirmation/index.ts` 导出 `TableInputCard`。

### 5.5 API — `frontend/src/lib/api.ts`

`confirmationsApi.respond` 的 body 类型已是 `ConfirmationResponse`，新增 `table_data` 字段后自动透传，**无需改逻辑**。

### 5.6 已解决态展示（可选）— `ConfirmationResolved.tsx`

若希望对话历史里把已提交的表格以只读小表展示，扩展 `ConfirmationResolvedInfo.table_data` 并在该组件渲染只读 `Table`。不做也不影响功能（LLM 侧已通过 `_format_ask_user_output` 拿到数据）。

## 6. 校验与边界

| 场景 | 处理 |
| --- | --- |
| 必填列为空 | 前端禁用提交并标红；后端 `_format_ask_user_output` 对空表回退提示 |
| 行数 < `min_rows` | 前端禁用提交 |
| 用户「跳过」 | `status=rejected`，`_format_ask_user_output` 走 rejected 分支 |
| 超时（默认 600s） | `ConfirmationManager` 设 `{status:'timeout'}`，提示 LLM 重试或采用默认值 |
| 页面刷新 | `GET /sessions/{id}/pending` 返回含 `table_schema` 的未决项，前端重建 TableInputCard |
| 后端重启 | 确认纯内存，未决表格会丢失（与现有 mode 一致的已知约束）。如需审计留痕，可在 `respond_to_confirmation` 时额外落库 |

---

## 7. 改动影响面汇总

**后端（4 文件）**：`tools/builtin.py`、`core/agent.py`、`core/confirmation.py`、`interface/routes/confirmations.py`。

**前端（4 文件 + 1 新建）**：`lib/types.ts`、`pages/AgentChatPage.tsx`、`components/confirmation/ConfirmationCard.tsx`、`components/confirmation/index.ts`，新建 `components/confirmation/TableInputCard.tsx`。

**无需改动**：SSE 转发逻辑（`chat.py` drain 循环）、`confirmationsApi.respond`、`ConfirmationManager` 暂停/恢复机制、`actionOrder` 渲染顺序 —— 均 mode-agnostic。

**唯一需注意的坑**：确认请求纯内存、无 DB 持久化。表格数据若较大或需审计，建议 resolve 时额外落库。
