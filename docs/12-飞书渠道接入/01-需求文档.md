# 飞书渠道接入需求文档

> 本文档定义平台接入飞书对话的需求边界、功能拆分、接口设计与验收标准。
> 绑定方式参考 WorkBuddy 连接器模式：管理员填入 App ID / App Secret、选择连接模式、注册生效，不走 OAuth。
> 身份映射采用方案 B：绑定码关联已有平台账号 + 影子账号兜底。

---

## 1. 背景

平台目前仅支持 Web UI（SSE）与 CLI 两种对话入口。为让终端用户在飞书中直接与 Agent 对话，需要新增「渠道接入」能力：平台作为飞书自建应用的服务端，接收飞书消息事件、驱动 `AgentLoop` 执行、将回复回发飞书。

关键约束：

- 平台是多租户架构，数据库以 `user_id` 做 RLS 隔离，飞书用户必须映射到平台 user 才能复用会话、记忆、权限体系
- 部署形态多样：私有化/内网部署无公网地址，需支持 WebSocket 长连接；有公网网关的部署需支持 Webhook 回调
- 飞书无 SSE，流式体验需用「占位消息 + 更新消息」模拟

---

## 2. 需求边界

### 2.1 范围内

| 项 | 说明 |
|---|---|
| 接入方式 | 飞书自建应用，连接器式绑定（App ID / App Secret 凭证注册，非 OAuth） |
| 连接模式 | WebSocket 长连接 + Webhook URL 回调，渠道级二选一、可切换 |
| 对话场景 | 单聊（P2P）；群聊仅响应 @机器人 |
| 消息类型 | 文本收发；回复按飞书长度限制分片 |
| 文件/图片 | file / image 消息下载存储到用户工作区，随下一条文字消息注入 Agent 处理（与 Web 页面上传一致）；绑定视觉模型时图片以 base64 直喂 LLM，非视觉模型降级为工作区路径引用 |
| 流式体验 | 占位消息 + 节流更新（约 1 次/秒合并刷新） |
| 身份映射 | 绑定码关联已有账号（方案 B）+ 影子账号兜底 |
| 会话映射 | `chat_id + open_id` → 平台 session，保留多轮上下文 |

### 2.2 范围外（本期不做）

- 语音 / 视频消息收发
- Interactive 消息卡片（含 AskUserQuestion 卡片化）
- 飞书其他 OpenAPI 能力：日历、云文档、多维表格、审批、机器人菜单
- 其他 IM 渠道（企微 / 钉钉 / Slack）——仅保留 `ChannelAdapter` 抽象，不实现
- 飞书会话在 Web UI 的展示与接管（二期）
- 一个渠道绑定多个 Agent / 群内按关键词路由 Agent

## 3. 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| R1 | 管理后台可创建飞书渠道：填 app_id / app_secret / 连接模式 / 绑定 Agent，保存前调 `tenant_access_token` 接口校验凭证有效性 | P0 |
| R2 | Webhook 模式：平台生成公网回调 URL 供复制，正确响应 URL 验证 challenge，校验事件签名与 encrypt_key 解密 | P0 |
| R3 | WebSocket 模式：渠道启用时拉起后台常驻连接（`lark-oapi-python` 的 `ws.Client`），断线自动重连，进程重启后自动恢复所有已启用渠道 | P0 |
| R4 | 同一渠道同一时刻仅一种模式生效；切换模式先停旧连接再启用新连接；禁用/删除渠道时释放对应连接资源 | P0 |
| R5 | 单聊文本消息驱动 Agent 执行并回发回复；两种模式的事件归一化为统一结构，下游管线完全复用 | P0 |
| R6 | 飞书用户首次发消息自动创建影子账号（受限平台 user），`open_id ↔ user_id` 绑定落表，后续对话复用 | P0 |
| R7 | 绑定码流程：飞书内发送 `/bind` 获取 6 位绑定码（10 分钟有效、一次性），Web 端登录后输入绑定码完成账号合并；合并后影子账号的会话与记忆迁移/归属到真实账号 | P0 |
| R8 | 会话映射：同一 `chat_id + open_id` 的对话追加到同一平台 session；发送 `/new` 开启新 session | P1 |
| R9 | 群聊仅响应 @机器人 的消息，且不携带其他成员的消息历史作为上下文 | P1 |
| R10 | 流式模拟：Agent 输出期间以占位消息承载，按节流窗口（默认 1s）合并增量更新消息；完成后写入最终内容；超长回复按飞书上限分片发送 | P1 |
| R11 | 渠道启停状态、最近错误（凭证失效、连接断开原因）在管理后台可见 | P1 |
| R12 | 飞书渠道会话从工具列表中过滤 `AskUserQuestion`（避免阻塞等待 Web 端确认导致死等） | P1 |
| R13 | 渠道级工具黑名单配置（如禁用沙箱命令执行等高危工具），默认空 | P2 |
| R14 | Web 端可查看/解绑自己的渠道绑定关系 | P2 |
| R15 | 飞书 file / image 消息下载存储：调用 `im/v1/messages/{id}/resources/{key}` 下载（需 `im:resource` 权限），存到用户默认工作区 `uploads/`（路径与 Web 页面上传一致），失败时回复明确错误 | P1 |
| R16 | 附件随文字消息处理：下载的文件/图片缓存为「待处理附件」（TTL 30 分钟），用户下一条文字消息到达时把文件引用注入 Agent 上下文（复用页面 `inject_file_refs_into_message`）一并驱动；绑定的模型为视觉模型（`is_multimodal=true`）时，图片压缩后以 base64 data URI 直喂 LLM（复用 `build_user_content`），否则降级为工作区路径引用由 Agent 文件工具处理；附件消息本身不触发 Agent，仅回复「已收到，请补充需求」 | P1 |

### 非功能需求

| 维度 | 要求 |
|---|---|
| **安全** | app_secret / encrypt_key 加密存储、不明文回显；webhook 验签失败一律 401 且不泄露原因细节；绑定码限次防爆破（同一 open_id 每分钟最多请求 3 次） |
| **性能** | 入站事件接收后立即 200 返回，Agent 执行异步化，不阻塞飞书重试机制 |
| **幂等** | 飞书事件重投（同一 `event_id`）不重复触发 Agent；消息回发失败可重试且不产生重复回复 |
| **隔离** | 渠道配置、绑定关系、会话均按平台 user / 租户隔离；影子账号数据不泄露给其他用户 |
| **可观测** | 记录渠道级日志：连接状态变更、事件接收数、回发成功率；Agent 执行复用现有 Langfuse trace |
| **可扩展** | 新增渠道类型（钉钉/企微）时只需实现 `ChannelAdapter`，不改入站管线与身份映射逻辑 |

## 4. 方案设计

### 4.1 总体架构

```
┌────────────┐   WebSocket    ┌──────────────────────────────────────────┐
│  飞书开放平台 │ ◄──────────► │  FeishuWsTransport（后台常驻 task）        │
│            │   Webhook POST │  FeishuWebhookTransport（FastAPI 路由）    │
└────────────┘ ─────────────► └──────────────┬───────────────────────────┘
                                              │ 归一化 InboundEvent
                                              ▼
                                   ┌──────────────────────┐
                                   │  ChannelInboundPipeline│
                                   │  身份解析/影子账号      │
                                   │  会话映射/指令拦截      │
                                   └──────────┬───────────┘
                                              ▼
                                   AgentLoop（复用现有，
                                   event_queue 消费 → 节流更新飞书消息）
                                              │
                                              ▼
                                   FeishuOutbound（回复/更新/分片）
```

- 新增 `channels/` 顶层模块：`adapter.py`（`ChannelAdapter` / `Transport` 抽象）、`pipeline.py`（统一入站管线）、`feishu/`（凭证管理、token 缓存、消息 API、两种 transport）、`binding.py`（影子账号与绑定码）
- `AgentLoop` 零改动；渠道侧复用 `chat.py` 中 `_build_agent_loop` / 系统提示词 / 记忆注入的装配逻辑（抽取为可复用函数，避免复制）
- WebSocket transport 注册为应用生命周期管理的后台任务：`app.state` 持有 `ChannelConnectionManager`，按 `channel_configs` 表中 `mode=websocket AND status=enabled` 的记录在启动时批量拉起；配置变更时增量启停

### 4.2 渠道绑定流程（连接器模式）

1. 管理员在飞书开放平台创建自建应用 → 添加机器人能力 → 开通权限（`im:message`、`im:message:send_as_bot`、`im:chat:readonly`、`im:resource`）→ 订阅 `im.message.receive_v1`；`im:resource` 用于下载用户发送的文件/图片资源
2. 管理后台「渠道管理」新建飞书渠道：填 `app_id` / `app_secret`（Webhook 模式另填 `encrypt_key` / `verification_token`）、选模式、选绑定的 Agent
3. 保存时平台用凭证请求 `tenant_access_token`，校验失败则拒绝保存并提示
4. 启用渠道：Webhook 模式展示回调 URL 供复制到飞书后台；WebSocket 模式拉起长连接并展示连接状态
5. 发布飞书应用后，用户在飞书中搜索机器人即可对话

### 4.3 身份映射（方案 B）

```
飞书用户发消息
   │
   ▼
查 channel_bindings(open_id)
   ├── 已绑定真实账号 ──► 以该 user_id 驱动 AgentLoop（全功能）
   ├── 已有影子账号 ────► 以影子 user_id 驱动（受限：仅渠道绑定 Agent，不写 L2 长期记忆）
   └── 无记录 ─────────► 创建影子账号（username=feishu_{open_id} 前缀，标记 is_shadow）
                          + 落绑定记录，回复中提示「发送 /bind 可关联已有账号」
```

- `/bind`：生成 6 位数字码写入 `channel_bind_codes`（TTL 10 分钟、一次性），回复用户
- Web 端「账号设置 → 渠道绑定」输入绑定码：校验通过后将该 open_id 的绑定指向当前登录账号；影子账号名下的 session 的 `user_id` 批量改挂到真实账号（保留历史连续性），影子账号标记停用
- 影子账号不可登录 Web 端（无密码、禁止签发 JWT）

### 4.4 会话与消息处理

- 会话映射表 `channel_session_mappings`：`(channel_id, chat_id, open_id)` 唯一 → `session_id`；`/new` 使旧映射失效并新建 session
- 入站指令拦截（不走 Agent）：`/bind`、`/new`、`/help`
- 事件去重：Redis/内存缓存 `event_id`（TTL 1h），重复事件直接 ACK
- 出站：收到事件先 ACK 200 → 后台 task 执行 AgentLoop → event_queue 消费 `text_delta` 按 1s 节流合并 → `PATCH /im/v1/messages/{message_id}` 更新占位消息 → 结束写入终稿；超过单条上限（约 4000 字符，以飞书实际限制为准）切片为多条
- 回复形式：单聊直接回发；群聊 reply 引用被 @ 的消息

### 4.5 附件（文件/图片）处理

飞书文件消息与文字消息分离，采用「先存储缓存、随文字注入」的时序（与 Web 页面上传一致）：

```
收到 file/image 消息
   │
   ▼
下载资源 (im/v1/messages/{id}/resources/{key}?type=file|image)
   │
   ▼
存用户默认工作区 uploads/{file_id}_{filename}（图片扩展名按 magic bytes 判定）
   │
   ▼
缓存「待处理附件」(会话级，TTL 30 分钟)
   │
   ▼
回复「📎 已收到 {name}，请补充你的需求」（不驱动 Agent）
```

- 用户随后发送文字消息 → 取出该会话待处理附件 → `inject_file_refs_into_message` 把 `[用户上传了以下文件到工作区：]` 列表注入用户消息 → Agent 通过文件工具读取 `/workspace/uploads/...` 路径处理
- **视觉模型直喂**：下载图片时已压缩（最长边 ≤2048px、JPEG 85，复用 `_compress_image`）并缓存 base64 data URI；绑定模型 `is_multimodal=true` 时，下一条文字消息经 `build_user_content` 构造多模态 content（anthropic / openai 格式）直喂 LLM；非视觉模型仅注入工作区路径引用
- AgentLoop 构造时传入 `workspace_id` / `workspace_slug`，系统提示词注入 `workspace_files`，与页面链路一致
- 附件消息同样要求身份绑定（未绑定用户仍引导 /bind）；群聊仍需 @机器人
- 下载失败 / 存储失败回复明确错误，不静默丢弃
- TTL 内无后续文字消息：文件保留在工作区，不额外提示，不触发 Agent

### 4.6 群聊规则

- 仅处理 `message.mentions` 含本机器人的事件，其余 ACK 丢弃
- 喂给 Agent 的只有当前这条消息文本（剥离 @ 占位符），不拉取群历史——避免泄露其他成员对话给模型
- 群聊会话映射以 `chat_id + open_id` 为单位：同一成员在同一群内的多轮 @ 共享 session，不同成员互不干扰

## 5. 接口设计

### 5.1 管理端（JWT + admin）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/channels` | 渠道列表（含状态、最近错误） |
| POST | `/api/channels` | 创建渠道，保存前校验飞书凭证 |
| PUT | `/api/channels/{id}` | 更新配置（改模式/凭证后需重新启用） |
| POST | `/api/channels/{id}/enable` | 启用：webhook 返回回调 URL；websocket 拉起连接 |
| POST | `/api/channels/{id}/disable` | 禁用并释放连接 |
| DELETE | `/api/channels/{id}` | 删除（连带清理绑定与会话映射） |
| GET | `/api/channels/{id}/bindings` | 该渠道的用户绑定列表 |

### 5.2 用户端（JWT）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/channel-bindings` | 我的渠道绑定列表 |
| POST | `/api/channel-bindings/bind` | 提交绑定码 `{code}` 完成账号合并 |
| DELETE | `/api/channel-bindings/{id}` | 解绑（飞书侧回退为影子账号或重新创建） |

### 5.3 飞书回调（无 JWT，验签）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/channels/feishu/events/{channel_key}` | Webhook 事件入口；`channel_key` 为渠道创建时生成的随机串，避免暴露自增 ID |

## 6. 数据表设计

```sql
-- 渠道配置（表结构支持多渠道/多类型，首期 UI 可限制单条）
CREATE TABLE channel_configs (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    channel_type  VARCHAR(32)  NOT NULL DEFAULT 'feishu',
    name          VARCHAR(128) NOT NULL,
    agent_id      UUID         NOT NULL,               -- 绑定的 Agent（应用层关联）
    app_id        VARCHAR(128) NOT NULL,
    app_secret_encrypted    TEXT NOT NULL,
    encrypt_key_encrypted   TEXT,                      -- 仅 webhook 模式
    verification_token_encrypted TEXT,                 -- 仅 webhook 模式
    mode          VARCHAR(16)  NOT NULL,               -- websocket | webhook
    status        VARCHAR(16)  NOT NULL DEFAULT 'disabled', -- enabled | disabled | error
    channel_key   VARCHAR(64)  NOT NULL UNIQUE,        -- webhook URL 随机串
    tool_blacklist JSONB       NOT NULL DEFAULT '[]',
    last_error    TEXT,
    created_by    UUID         NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 飞书用户 ↔ 平台用户绑定
CREATE TABLE channel_bindings (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    channel_id   UUID NOT NULL,
    external_id  VARCHAR(128) NOT NULL,                -- 飞书 open_id
    user_id      UUID NOT NULL,                        -- 平台 user（影子或真实）
    bind_type    VARCHAR(16) NOT NULL DEFAULT 'shadow',-- shadow | bound
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (channel_id, external_id)
);

-- 绑定码
CREATE TABLE channel_bind_codes (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code        VARCHAR(8)  NOT NULL,
    channel_id  UUID NOT NULL,
    external_id VARCHAR(128) NOT NULL,
    expires_at  TIMESTAMPTZ NOT NULL,
    used_by     UUID,                                  -- 消费该码的平台 user
    used_at     TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_bind_codes_code ON channel_bind_codes (code) WHERE used_at IS NULL;

-- 渠道会话映射
CREATE TABLE channel_session_mappings (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    channel_id  UUID NOT NULL,
    chat_id     VARCHAR(128) NOT NULL,
    external_id VARCHAR(128) NOT NULL,
    session_id  UUID NOT NULL,
    is_active   BOOLEAN NOT NULL DEFAULT true,          -- /new 后置 false
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_channel_session_active
    ON channel_session_mappings (channel_id, chat_id, external_id) WHERE is_active;
```

- `users` 表增加 `is_shadow BOOLEAN NOT NULL DEFAULT false`
- 所有表遵循现有约定：无外键、应用层维护关系；`channel_bindings` / `channel_session_mappings` 涉及用户数据的查询走 `user_id` 过滤
- Alembic 一个迁移包含以上全部表

## 7. 验收标准

| 编号 | 场景 | 预期 |
|---|---|---|
| A1 | 后台填入正确凭证创建 WebSocket 渠道并启用 | 凭证校验通过，后台显示「已连接」，飞书私聊机器人可收到 Agent 回复 |
| A2 | 填入错误 app_secret | 保存被拒绝，提示凭证无效 |
| A3 | WebSocket 渠道运行中杀掉进程再重启 | 服务启动后自动恢复连接，无需人工干预 |
| A4 | Webhook 模式：飞书后台填回调 URL 保存 | challenge 验证通过；篡改签名请求返回 401 |
| A5 | 渠道从 WebSocket 切换到 Webhook（反之亦然） | 旧连接/旧入口失效，新模式正常收发，无消息丢失或重复 |
| A6 | 同一事件重投（相同 event_id） | 只触发一次 Agent 执行 |
| A7 | 新飞书用户首次私聊 | 自动创建影子账号并可正常对话，回复中含绑定提示 |
| A8 | 影子用户 `/bind` 拿码 → Web 端输入绑定码 | 绑定成功；飞书侧后续对话以真实账号身份执行，历史会话在 Web 端可见 |
| A9 | 过期/错误/已使用的绑定码 | 分别提示失效原因；同一 open_id 每分钟请求绑定码超过 3 次被拒 |
| A10 | 群聊：@机器人 vs 普通消息 | @机器人 有回复且上下文不含其他成员消息；普通消息无响应 |
| A11 | Agent 长回复（>4000 字符） | 分片发送且顺序正确，无截断乱码 |
| A12 | Agent 输出期间观察飞书消息 | 占位消息按约 1s 节奏更新，结束后为终稿 |
| A13 | 飞书渠道会话中 Agent 尝试 AskUserQuestion | 工具已被过滤，不出现死等 |
| A14 | 绑定码合并后影子账号 | 标记停用、无法登录；其 session 归属真实账号 |
| A15 | 飞书发送文件/图片消息 | 机器人回复「已收到」，文件出现在用户工作区 `uploads/`，此消息不触发 Agent 执行 |
| A16 | 发送文件后跟一条文字「总结文件内容」 | Agent 读取工作区文件并正确总结；文件引用已注入该条文字消息上下文 |
| A17 | 绑定视觉模型后发图片+文字「描述这张图」 | 图片以 base64 data URI 直喂 LLM，Agent 能直接描述图片内容（无需文件工具）；非视觉模型下降级为路径引用不报错 |

## 9. 依赖与风险

- 依赖 `lark-oapi-python` 官方 SDK（WebSocket client、事件模型、加解密）；需评估其 ws.Client 在 asyncio 服务中的线程模型，必要时以独立线程 + 队列桥接进 async 管线
- 飞书消息更新接口有频率限制，节流窗口参数需可调；超限降级为「完成后一次性发送」
- 影子账号会污染 users 表统计，运营报表需过滤 `is_shadow`
- 私有化部署用 WebSocket 模式时，出口网络需可访问飞书开放平台
