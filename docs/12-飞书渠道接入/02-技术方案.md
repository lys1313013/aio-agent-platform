# 飞书渠道接入技术方案

> 需求文档见同目录 [01-需求文档.md](01-需求文档.md)。

---

## 1. 方案设计

### 1.1 总体架构

```
┌────────────┐   WebSocket    ┌──────────────────────────────────────────┐
│  飞书开放平台 │ ◄──────────► │  FeishuWsTransport（后台常驻 task）        │
│            │   Webhook POST │  FeishuWebhookTransport（FastAPI 路由）    │
└────────────┘ ─────────────► └──────────────┬───────────────────────────┘
                                              │ 归一化 InboundEvent
                                              ▼
                                   ┌──────────────────────┐
                                   │  ChannelInboundPipeline│
                                   │  身份解析/绑定引导      │
                                   │  会话映射/指令拦截      │
                                   └──────────┬───────────┘
                                              ▼
                                   AgentLoop（复用现有，
                                   event_queue 消费 → 节流更新飞书消息）
                                              │
                                              ▼
                                   FeishuOutbound（回复/更新/分片）
```

- 新增 `channels/` 顶层模块：`adapter.py`（`ChannelAdapter` / `Transport` 抽象）、`pipeline.py`（统一入站管线）、`feishu/`（凭证管理、token 缓存、消息 API、两种 transport）、`binding.py`（身份解析与绑定码）
- `AgentLoop` 零改动；渠道侧复用 `chat.py` 中 `_build_agent_loop` / 系统提示词 / 记忆注入的装配逻辑（抽取为可复用函数，避免复制）
- WebSocket transport 注册为应用生命周期管理的后台任务：`app.state` 持有 `ChannelConnectionManager`，按 `channel_configs` 表中 `mode=websocket AND status=enabled` 的记录在启动时批量拉起；配置变更时增量启停

### 1.2 渠道绑定流程（连接器模式）

1. 管理员在飞书开放平台创建自建应用 → 添加机器人能力 → 开通权限（`im:message`、`im:message:send_as_bot`、`im:chat:readonly`、`im:resource`、`cardkit:card:write`）→ 订阅 `im.message.receive_v1` 与 `im.message.recalled_v1`（撤回即停用，见 1.7）；`im:resource` 用于下载用户发送的文件/图片资源，`cardkit:card:write` 用于 CardKit 2.0 原生流式卡片回复
2. 管理后台「渠道管理」新建飞书渠道：填 `app_id` / `app_secret`（Webhook 模式另填 `encrypt_key` / `verification_token`）、选模式、选绑定的 Agent
3. 保存时平台用凭证请求 `tenant_access_token`，校验失败则拒绝保存并提示
4. 启用渠道：Webhook 模式展示回调 URL 供复制到飞书后台；WebSocket 模式拉起长连接并展示连接状态
5. 发布飞书应用后，用户在飞书中搜索机器人即可对话

### 1.3 身份映射（方案 B）

```
飞书用户发消息
   │
   ▼
查 channel_bindings(tenant_id, open_id)
   ├── 已绑定且账号有效 ──► 以该 user_id 驱动 AgentLoop（全功能）
   └── 无绑定记录 ────────► 不创建任何账号，回复绑定引导
                            （提示发送 /bind 关联平台账号），不驱动 Agent
```

- 绑定关系按租户生效：`channel_bindings` 以 `(tenant_id, external_id)` 唯一，租户内所有渠道共享同一绑定
- `/bind`：生成 6 位数字码写入 `channel_bind_codes`（TTL 10 分钟、一次性，同一 external_id 同时仅一个有效码，限流 3 次/分钟），回复用户
- Web 端「账号设置 → 渠道绑定」输入绑定码：校验通过（仅可在签发码的租户内消费）后创建绑定指向当前登录账号；已绑定其他账号时需先在 Web 端解绑

### 1.4 会话与消息处理

- 会话映射表 `channel_session_mappings`：`(channel_id, chat_id, open_id)` 唯一 → `session_id`；`/new` 使旧映射失效并新建 session
- 入站指令拦截（不走 Agent）：`/bind`、`/new`、`/help`、`/stop`（任务中断，见 1.7）
- 事件去重：Redis/内存缓存 `event_id`（TTL 1h），重复事件直接 ACK
- 出站：渠道配置 `enable_streaming=true` 时，收到事件先 ACK 200 → 创建开启 `streaming_mode` 的 CardKit 2.0 卡片实体并发送 → 后台 task 执行 AgentLoop → 消费 `text_delta`，通过 CardKit 流式更新文本接口按序列号推送全量文本 → 结束后关闭 `streaming_mode` 并更新摘要；该流程不编辑普通消息，不显示“已编辑”。`enable_streaming=false` 或未开通 `cardkit:card:write` 时，等待 Agent 完整生成后一次性发送。超过单卡上限的内容切片为后续消息
- 回复形式：单聊直接回发；群聊 reply 引用被 @ 的消息

### 1.5 附件（文件/图片）处理

飞书文件消息与文字消息分离，采用「先存储缓存、随文字注入」的时序（与 Web 页面上传一致）：

```
收到 file/image 消息
   │
   ▼
下载资源 (im/v1/messages/{id}/resources/{key}?type=file|image)
   │
   ▼
存用户默认工作区 uploads/{file_id}_{filename}（图片扩展名按 magic bytes 判定）
   │
   ▼
缓存「待处理附件」(会话级，TTL 30 分钟)
   │
   ▼
回复「📎 已收到 {name}，请补充你的需求」（不驱动 Agent）
```

- 用户随后发送文字消息 → 取出该会话待处理附件 → `inject_file_refs_into_message` 把 `[用户上传了以下文件到工作区：]` 列表注入用户消息 → Agent 通过文件工具读取 `/workspace/uploads/...` 路径处理
- **视觉模型直喂**：下载图片时已压缩（最长边 ≤2048px、JPEG 85，复用 `_compress_image`）并缓存 base64 data URI；绑定模型 `is_multimodal=true` 时，下一条文字消息经 `build_user_content` 构造多模态 content（anthropic / openai 格式）直喂 LLM；非视觉模型仅注入工作区路径引用
- AgentLoop 构造时传入 `workspace_id` / `workspace_slug`，系统提示词注入 `workspace_files`，与页面链路一致
- 附件消息同样要求身份绑定（未绑定用户仍引导 /bind）；群聊仍需 @机器人
- 下载失败 / 存储失败回复明确错误，不静默丢弃
- TTL 内无后续文字消息：文件保留在工作区，不额外提示，不触发 Agent

### 1.6 群聊规则

- 仅处理 `message.mentions` 含本机器人的事件，其余 ACK 丢弃
- 喂给 Agent 的只有当前这条消息文本（剥离 @ 占位符），不拉取群历史——避免泄露其他成员对话给模型
- 群聊会话映射以 `chat_id + open_id` 为单位：同一成员在同一群内的多轮 @ 共享 session，不同成员互不干扰

### 1.7 任务中断（`/stop` + 撤回即停）

Web 端的停止依赖「断开 SSE → FastAPI 取消请求 → `CancelledError` 级联取消 AgentLoop」；渠道场景没有 HTTP 连接可断，需自建任务登记与取消入口。

- **前置：chat 级串行排队**。现状 `submit()` 对每个事件直接 `create_task(_safe_handle)`，同一 `chat_key` 连发两条消息会并发驱动两个 AgentLoop（共享一个 session），任务中断的一对一登记无从谈起。先引入 chat 级队列：每个 `chat_key` 一个 `asyncio.Queue` + 消费者循环，消息入队、逐条驱动；语义与 Web 端 message queue 一致。`/stop` 在取消在跑任务的同时清空该 chat 的待处理队列
- **在跑任务登记表**：`ChannelInboundPipeline` 内维护进程级字典，key 为 `chat_key`（`{channel_id}:{chat_id}:{external_id}`，与 `task_registry` 的 chat_key 口径一致），value 为 `RunningAgentTask{task: asyncio.Task, trigger_message_id: str}`；另建 `trigger_message_id → chat_key` 反查索引供撤回事件使用。**登记的 task 不是消费者本身**——消费者为每条消息创建子任务（`create_task(_safe_handle)`）并登记该子任务，`/stop` 取消子任务不会杀死消费者循环。关键陷阱：子任务被取消会以 `CancelledError` 形式冒泡到消费者的 `await inner`，但**取消消费者也会连带取消其 await 的子任务**，`inner.cancelled()` 在两种场景下都为 True，无法用其区分取消来源；实现用消费者自身 `asyncio.current_task().cancelling() > 0` 判断（>0 即自身被取消，传播；为 0 即子任务被取消，吞掉继续消费下一条）。登记于子任务启动时、finally 清理。多副本部署时该表是进程本地的——撤回/`/stop` 事件与在跑任务落在同一进程才生效（飞书 WS 长连接天然满足；Webhook 多副本需 sticky 或退化为尽力而为，记录在案即可；后续可复用 `task_registry` 的 Redis pub/sub 通道广播取消指令消除该限制，本期不做）
- **`/stop` 命令**：在 `_handle` 的指令拦截段（`/new` 之前）处理：查登记表 → 有任务则 `task.cancel()` + 清空队列并回复「已中断」；无任务回复「当前没有进行中的回复」。不走统一命令注册表，避免 `cmd_stop` 的假确认语义（该 handler 保留给 Web/CLI——Web 端真实停止仍靠按钮断开 SSE，`/stop` 在 Web/CLI 维持现状）
- **取消语义**：`CancelledError` 沿 `AgentLoop.run()` 传播，终止 LLM 流与在途工具调用（`except Exception` 接不住 `BaseException`，取消不会被现有错误分支吞掉）。注意：**Web 端的 rescue（`_rescue_partial`）是 `chat.py` SSE generator 的局部函数，pipeline 里没有对应物**——渠道侧需新增 `except asyncio.CancelledError` 分支：用**新开的 DB session**（原 session 随被取消的 `_handle` 上下文一起关闭）持久化已累积的部分 assistant 消息（内容尾部标记「已中断」，含已产生的 tool_calls）；`event_logger.drain()` 冲刷缓冲事件；`stream_reply.finish("⏹ 已中断")` 收尾卡片并关闭 `streaming_mode`。该分支内所有出站/持久化调用用 `asyncio.shield` 包裹，防止外层再次取消导致「已中断」状态写不出去；处理完 `raise` 继续传播
- **撤回即停**：两个 transport 放行 `im.message.recalled_v1`；`events.py` 新增 normalize 分支产出撤回事件（携带 `message_id`、`chat_id`）。pipeline 收到后按反查索引定位任务并 `task.cancel()`；查不到映射（任务已结束/非触发消息）静默 ACK。两个边界：
  - **撤回人校验（已核实，无需身份校验）**：`im.message.recalled_v1` 事件体只含 `message_id` / `chat_id` / `recall_time` / `recall_type`（撤回方类别：message_owner / group_owner / group_manager / enterprise_manager），**不含操作人身份**。飞书权限模型下普通成员只能撤回自己的消息，能撤他人消息的只有群主/管理员/企业管理员——任何针对触发消息的撤回都来自有权撤回该消息的人，不存在路人代撤场景，故撤回触发消息即停，不做身份校验，仅将 `recall_type` 记入日志
  - **秒撤回竞态**：撤回事件可能先于登记完成（登记发生在身份解析、附件下载、历史加载之后）。维护一个 TTL（10 分钟）的「已撤回 message_id 集合」，撤回时先写集合再查表；任务登记时先自查集合，命中则直接放弃驱动——保证「先撤回后登记」也能拦下
- **一致性**：中断与正常结束共用 finally 清理路径，登记表、流式卡片、`task_registry`（宠物 widget）三处状态同步清除，不出现残留「运行中」状态

## 2. 接口设计

### 2.1 管理端（JWT + admin）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/channels` | 渠道列表（含状态、最近错误） |
| POST | `/api/channels` | 创建渠道，保存前校验飞书凭证 |
| PUT | `/api/channels/{id}` | 更新配置（改模式/凭证后需重新启用） |
| POST | `/api/channels/{id}/enable` | 启用：webhook 返回回调 URL；websocket 拉起连接 |
| POST | `/api/channels/{id}/disable` | 禁用并释放连接 |
| DELETE | `/api/channels/{id}` | 删除（连带清理绑定与会话映射） |
| GET | `/api/channels/{id}/bindings` | 该渠道的用户绑定列表 |

### 2.2 用户端（JWT）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/channel-bindings` | 我的渠道绑定列表 |
| POST | `/api/channel-bindings/bind` | 提交绑定码 `{code}` 完成账号合并 |
| DELETE | `/api/channel-bindings/{id}` | 解绑（删除绑定记录，平台账号保留；飞书侧回到未绑定状态） |

### 2.3 飞书回调（无 JWT，验签）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/channels/feishu/events/{channel_key}` | Webhook 事件入口；`channel_key` 为渠道创建时生成的随机串，避免暴露自增 ID |

## 3. 数据表设计

```sql
-- 渠道配置（表结构支持多渠道/多类型，首期 UI 可限制单条）
CREATE TABLE channel_configs (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    channel_type  VARCHAR(32)  NOT NULL DEFAULT 'feishu',
    name          VARCHAR(128) NOT NULL,
    agent_id      UUID         NOT NULL,               -- 绑定的 Agent（应用层关联）
    app_id        VARCHAR(128) NOT NULL,
    app_secret_encrypted    TEXT NOT NULL,
    encrypt_key_encrypted   TEXT,                      -- 仅 webhook 模式
    verification_token_encrypted TEXT,                 -- 仅 webhook 模式
    mode          VARCHAR(16)  NOT NULL,               -- websocket | webhook
    status        VARCHAR(16)  NOT NULL DEFAULT 'disabled', -- enabled | disabled | error
    channel_key   VARCHAR(64)  NOT NULL UNIQUE,        -- webhook URL 随机串
    tool_blacklist JSONB       NOT NULL DEFAULT '[]',
    last_error    TEXT,
    created_by    UUID         NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 飞书用户 ↔ 平台用户绑定（按租户生效，租户内所有渠道共享）
CREATE TABLE channel_bindings (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id    UUID NOT NULL,
    external_id  VARCHAR(128) NOT NULL,                -- 飞书 open_id
    user_id      UUID NOT NULL,                        -- 平台 user
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, external_id)
);

-- 绑定码
CREATE TABLE channel_bind_codes (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code        VARCHAR(8)  NOT NULL,
    tenant_id   UUID NOT NULL,                         -- 签发租户，消费时校验同租户
    channel_id  UUID NOT NULL,
    external_id VARCHAR(128) NOT NULL,
    expires_at  TIMESTAMPTZ NOT NULL,
    used_by     UUID,                                  -- 消费该码的平台 user
    used_at     TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_bind_codes_code ON channel_bind_codes (code) WHERE used_at IS NULL;

-- 渠道会话映射
CREATE TABLE channel_session_mappings (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    channel_id  UUID NOT NULL,
    chat_id     VARCHAR(128) NOT NULL,
    external_id VARCHAR(128) NOT NULL,
    session_id  UUID NOT NULL,
    is_active   BOOLEAN NOT NULL DEFAULT true,          -- /new 后置 false
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_channel_session_active
    ON channel_session_mappings (channel_id, chat_id, external_id) WHERE is_active;
```

- 所有表遵循现有约定：无外键、应用层维护关系；`channel_bindings` / `channel_session_mappings` 涉及用户数据的查询走 `user_id` 过滤
- Alembic 一个迁移包含以上全部表
