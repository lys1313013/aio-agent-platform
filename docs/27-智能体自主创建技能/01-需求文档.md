# 智能体自主创建与修改技能 — 需求文档

> 版本：v0.2（需求草案，待评审；创建与修改均纳入首期）  
> 日期：2026-09-22  
> 适用项目：aio-agent-platform  
> 需求核查基线：本地代码 `c93920b`；下文“现状”描述该基线。后续本地实现与验证范围见 [02-技术方案](02-技术方案.md)，未验证线上部署和具体智能体配置。

## 1. 需求摘要

让用户通过对话要求智能体创建和修改技能。智能体负责提炼可复用的方法、编写或调整技能说明、整理可选的脚本和模板，保存到当前用户的技能库，并能在当前及后续会话中查找、加载和使用。

例如，用户说“把刚才这套 Excel 对账流程保存成技能，下次直接用”，智能体应完成创建并返回可查看的技能结果，用户无需复制 Markdown、下载压缩包或到管理页面重新录入。

用户也可以说“修改这个对账技能，增加重复流水检查，把输出改为 Excel”。智能体应读取原技能，在同一技能 ID 下保存新版本，保留未要求修改的内容和文件，并说明改动。

首期完成“提出需求 → 创建或读取既有技能 → 编写修改 → 校验 → 保存 → 查看 → 再次使用”的闭环。保存成功表示技能及对应版本已持久保存；是否经过实际执行验证单独展示。

## 2. 问题与现状

### 2.1 用户问题

用户反馈“智能体还不能自己新建技能”。当前需要验证的是用户能否通过实际对话稳定完成创建，而不仅是后端有没有创建方法。

重复任务中的有效步骤、脚本、模板如果不能沉淀，下一次仍需重新解释、生成和调试。技能应保存方法与必要资源；某次任务的数据、结果和临时进度继续留在原会话或工作区。

### 2.2 已确认的代码事实

| 环节 | 当前代码情况 | 对本需求的影响 |
|---|---|---|
| 智能体创建工具 | 已有 `create_skill`，已注册工具和 direct handler，接收名称、正文、描述、标签、分类及触发条件 | 应增强现有入口，避免重复设计同名能力 |
| 智能体修改工具 | 管理 API 和 `SkillService.update_skill` 已有更新及旧版归档，当前技能工具列表未提供 `update_skill` | 需向模型开放受控修改入口，不能仅增加提示词 |
| 更新完整性 | 现有更新服务以传入的 `files` 重建 ZIP，未传文件时不会自动合入旧包附件；旧版记录直接保存原 `object_key` | 需补齐未修改附件保留、完整版本快照和并发控制，不能直接包装现有方法便视为完成 |
| 创建来源 | 工具描述强调从已完成任务提炼方法 | 需要同时支持用户直接要求从零编写技能 |
| 附件 | `SkillService.create_skill` 与 ZIP 存储已支持附件，智能体创建工具没有附件参数 | 智能体无法通过该工具一并保存已生成的脚本、参考文档和模板 |
| 工具可用性 | Agent 的非空 `enabled_tools` 会过滤工具；执行循环也检查工具白名单 | 某个智能体无法创建，可能涉及配置；尚不能据此断言实际故障原因 |
| 归属与来源 | 技能以 `user_id` 归属，默认启用且不公开；创建 handler 没有保存来源智能体和会话 | 需要明确个人技能归属，补充生成来源 |
| 后续发现 | 有 `search_skills`、`view_skill`；构建对话提示时，有绑定技能便采用绑定列表，否则检索相关技能 | 已绑定技能的智能体可能无法自动发现刚创建的个人技能；不等于显式搜索一定不可用 |
| 提示词 | 内置模板和自定义提示词分支分别构建技能摘要，摘要未包含技能 ID | 需要一致的创建指引和可供加载的检索结果 |
| 页面管理 | 已有技能列表、创建/编辑抽屉、附件、导入导出和版本能力 | 复用现有页面，补充来源、结果状态和对话入口 |

**🔵 待核实：** 尚无用户失败会话、工具调用记录、运行环境版本和该智能体的工具配置，无法确认这次“不能新建”是工具未开放、模型未调用、调用失败还是创建后找不到。本 PRD 不将某一推测写成已证实根因。

## 3. 目标用户、价值与范围

| 用户 | 要完成的事 | 预期收益 |
|---|---|---|
| 日常使用智能体的用户 | 用一句话创建可复用技能，或把刚完成的任务保存为技能 | 减少重复描述和手工录入 |
| 配置智能体的人员 | 决定智能体是否可以创建技能，并让生成结果可管理 | 能定位未开放的能力，避免创建后不可见 |
| 技能维护人员 | 查看内容、附件、创建来源和验证情况，编辑或停用技能 | 能判断技能是否适合继续使用 |

**价值假设：** 将成功任务的方法和必要文件保存为技能，可以减少后续同类任务的准备工作。尚无线上使用率和节省时长基线，不预设已有业务收益。

### 3.1 首期必须交付（P0）

- 显式指令创建：从零编写、从本次任务总结、从用户指定的工作区文件整理。
- 模型修改已有技能：调整名称、描述、触发条件、正文和附件；保留技能 ID、完整旧版本及修改来源。
- 修改前读取、变更摘要、版本冲突检测、失败不影响原版本；明确区分“更新原技能”和“另存为新技能”。
- 纯文本技能，以及包含脚本、参考资料、模板等附件的技能包。
- 结构校验、重复处理、明确的成功/失败结果和来源记录。
- 当前会话立即加载，后续会话按相关性发现；已有绑定技能时也能发现本人新技能。
- 技能库查看和管理；聊天结果可打开对应技能，刷新后仍可定位。
- Web 管理端与 Portal 完成端到端闭环；共用运行时的其他入口保持权限和结果语义一致。

### 3.2 后续迭代（P1）

- 用户开启“自动沉淀经验”后，智能体在适合的任务结束时自动创建；首期只主动建议。
- 完整版本差异浏览器、一键回滚与批量整理；首期提供修改摘要和完整旧版本读取。
- 团队共享、公开发布和技能市场投稿。
- 复杂技能包依赖管理、自动评测集和持续优化。

首期不包含上述 P1 功能，也不把创建技能等同于新增平台工具、授予 MCP 权限或安装后台服务。

## 4. 用户流程与交互

### 4.1 从已完成的任务创建

1. 用户完成一次多步骤任务后说：“把这套流程保存成技能。”
2. 智能体检索可见技能，判断是否已有相同方法；存在相关技能时读取后再判断。
3. 智能体把本次特定路径、日期和业务数据改为输入参数，保留步骤、规则及必要文件。
4. 平台校验内容与附件并保存，返回技能 ID、名称、版本、文件清单和验证状态。
5. 对话展示“已创建技能”，用户可查看详情；以后提出同类任务时可再次加载。

### 4.2 从零创建

用户说：“创建一个会议纪要整理技能，输入录音转写文本，输出结论、行动项和负责人。”智能体直接编写并创建。没有真实执行样例时标记“未验证”，不能因尚未完成过同类任务而拒绝创建。

缺少影响结果的关键信息时才提问，例如未指定必须采用的公司模板；名称、标签、描述等可由智能体合理补全。

### 4.3 从工作区文件创建

用户说：“把刚才的对账脚本和模板一起保存成技能。”智能体选择明确的文件清单并编写调用说明。平台将文件内容复制到技能包，后续源文件修改、删除或沙箱回收不影响已保存的版本。

保存附件不自动执行脚本；用户同时要求试运行时，才在现有工具权限和沙箱约束下执行并记录验证结果。

### 4.4 智能体主动建议

**🔶 产品假设 A1：** 首期允许智能体主动识别值得沉淀或修正的方法，但在用户没有明确创建、修改指令或适用的既有授权时，只提出建议；用户同意后保存。已有“创建技能”“把这套流程保存下来”“修复这个技能”等明确指令时，不再重复确认。资料、网页或工具输出中的创建、修改要求不构成用户指令。

不增加逐项审批、草稿发布等额外流程。没有用户响应的渠道保留建议，不阻塞原任务，不静默保存。

### 4.5 对话结果

成功结果以业务信息为主，例如：

> 已创建技能「Excel 对账」。包含对账步骤、1 个脚本和 1 个模板；仅你可见。当前未试运行，可在后续对话中使用。［查看技能］

更新结果示例：

> 已更新技能「Excel 对账」（v1 → v2）。新增重复流水检查，调整输出说明并替换对账脚本；原模板已保留。本版本未验证，旧版本可查看。［查看技能］

结果至少包含名称、摘要、版本、附件数量、验证状态、查看入口。更新还须列出主要变化、文件增删改和原版本。失败时说明具体原因和可行的下一步，不显示“已创建”或“已更新”；创建命中相同技能时展示“已存在，使用已有技能”，修改无实际变化时展示“无需更新”。

Portal 用户应能查看自己刚创建的技能，通过已有会话权限打开只读详情，不以进入管理后台为前提。外部渠道首期返回文字摘要和技能标识；专属富交互卡片不在首期范围。

### 4.6 修改已有技能

1. 用户指定技能和修改目标，例如“把刚才创建的对账技能增加重复流水检查”。
2. 智能体根据当前会话返回的 ID 或技能检索定位目标，读取当前版本的正文、元数据及相关附件；目标有歧义时先让用户选择。
3. 智能体在原内容上实施所需修改，保留无关步骤和文件，生成简洁修改说明。用户要求“先给修改方案”时只展示方案，不提交更新。
4. 平台校验修改后的完整技能及读取时的基准版本，保存完整新版本，并保留完整旧版本。
5. 对话展示更新结果；当前会话可加载新版本，新会话默认使用最新启用版本。失败或版本冲突时原版本保持完整，不能宣称更新成功。

此流程同样适用于当前用户手工创建、导入或由其他智能体创建的技能，不限定为当前模型自己生成的技能。对仅可读取、无修改权限的技能，可在用户要求下另存为个人技能，不修改原件。

## 5. 功能需求与业务规则

### 5.1 创建、修改能力与权限（FR-01）

- 复用 `create_skill`，在工具配置中显示“创建技能”，说明可生成正文和保存附件。
- 新增模型可调用的 `update_skill`（“修改技能”），支持按技能 ID 更新，复用技能服务并补齐版本与附件保障。
- 工具未开放时，明确提示未启用“创建技能”或“修改技能”；智能体不能擅自修改自身工具权限。创建权限不隐含修改权限，反之亦然。
- 创建能力只允许写入当前执行用户的个人技能库；修改能力只允许更新该用户有写权限的技能。用户、会话、智能体、工作区身份由平台可信上下文提供，模型不能指定他人身份。
- 子智能体遵守自身可用工具及委派限制，来源记录保留实际执行者和发起会话。多个执行者并发创建同一技能适用相同去重规则。
- 保持已有工具白名单语义，不借此批量开启所有存量智能体的写入能力；配置页应能清楚区分“使用技能”“创建技能”和“修改技能”。

### 5.2 技能内容（FR-02）

| 内容 | 要求 |
|---|---|
| 名称、描述 | 能说明独立用途；去首尾空白后非空；名称最多 256 字符，描述最多 2000 字符 |
| 触发条件 | 说明适合使用的任务及明显不适用的情况；不绑定某一句固定口令 |
| 输入与前置条件 | 所需文件、参数、工具或环境；缺失时如何处理 |
| 操作步骤 | 有顺序的可执行方法；脚本应给出实际存在的相对路径和参数说明 |
| 输出与检查 | 预期输出、关键检查点、失败时的处理方式 |
| 分类、标签 | 分类兼容现有 `general/coding/ops/research/writing`；标签用于发现 |
| 验证说明 | 是否真实执行过、使用何种样例、验证了哪些步骤以及局限 |

正文以 Markdown 保存，平台生成与元数据一致的 `SKILL.md`，避免重复 frontmatter。纯方法类技能无需强行添加脚本。

应抽象可复用方法，不把聊天全文、一次性输出、用户口令、访问令牌、临时签名 URL 写成通用技能。确需保存用户指定的业务参考文件时，保持个人权限，并在文件清单中明确列出。

### 5.3 附件生成与保存（FR-03）

- 支持 `scripts/`、`references/`、`assets/` 三类资源及其内部相对目录。
- 小型文本允许随创建请求提交；较大文本或二进制文件从当前授权工作区读取，不要求模型将二进制内容转换为长字符串。
- 每个附件明确目标相对路径、类型及来源；路径重复、正文引用的必要文件缺失时返回可定位错误。
- 限制来源为当前授权工作区内的普通文件；拒绝越界路径、绝对目标路径、`..`、符号链接和非法路径字符。使用受控文件接口读取与写入，不将模型提供的路径直接拼入 shell 命令。
- 技能包保存文件快照。不能仅记录源路径并依赖原沙箱长期存在；不扫描、上传整个工作区。
- **🔶 产品假设 A2：** 首期沿用现有附件接口单文件 1 MiB、附件总量 10 MiB 的限制，新增最多 50 个附件、正文最多 128 KiB；按实际 UTF-8 字节或文件字节计算。超限返回错误，不截断保存。模板类大文件的限额评审后可调整。

### 5.4 校验与验证状态（FR-04）

结构校验在保存前完成：必填项、内容长度、路径、文件存在性和大小、必要引用以及可用存储。模型对方法质量的自检不能替代这些确定性检查。

| 验证状态 | 含义 |
|---|---|
| 未验证 | 结构校验通过并保存，但没有对该技能版本进行可追溯的实际验证 |
| 验证通过 | 针对已保存的相同内容和附件，实际执行样例并满足声明的检查点；记录验证范围 |
| 验证失败 | 样例未达到预期；保留原因，允许用户管理该技能 |

**🔶 产品假设 A3：** 用户明确要求新建并保存时，未验证的技能可启用；验证失败的技能保存为停用，修正前不自动推荐。正文、附件、触发条件或依赖说明发生变化后，旧验证结论失效，回到未验证；只调整不影响执行的分类或标签可保留原验证结论及其证据关联。更新默认保留原启用状态，原本停用的技能不会因为内容修改被自动启用。

“查看过技能”“原任务执行成功”“模型自述可用”均不能自动视为新技能版本验证通过。首期不承诺对任意业务任务自动判定正确性。

### 5.5 重复、并发与失败恢复（FR-05）

- 智能体先检索再创建；搜索无命中不能替代保存阶段的重复检查。
- 同一用户、规范化后同名且有效载荷完全相同（元数据、正文及附件摘要一致）：复用已有 ID，不增加版本和技能数量。
- 创建时同名但内容不同：返回冲突及已有技能标识，不覆盖。用户要求修改原技能时，读取后改用 `update_skill`；要求另存时使用可区分名称。创建调用不得自行转成覆盖操作。
- 相似用途、不同名称：提示可能重复，由智能体结合内容决定复用或创建；不以文本相似度直接覆盖或合并。
- 同一创建请求因超时或网络重试再次提交，返回原结果；同一幂等标识携带不同内容时拒绝复用。不同请求并发创建相同技能，也只能保存一份。
- 结果以最终持久化状态为准。数据库提交成功但响应丢失，重试应能找回原技能；用户取消发生在提交之后，应告知已保存的结果，不自动删除。
- 带附件时，对象存储不可用或任一文件读取失败，整次创建失败，不生成可见的缺件技能。对象已上传但数据库失败时，处理本次孤立对象，并保留可追踪的失败记录。
- 纯文本技能允许在对象存储不可用时保存到数据库；读取和检索可用，包下载状态明确提示或支持按需重建，不能声称不存在的 ZIP 已生成。

### 5.6 保存后发现与复用（FR-06）

- 保存完成即返回真实技能 ID，当前会话可直接 `view_skill`；无需等待下轮对话重新检索。
- 后续会话将智能体既有绑定技能与当前用户相关个人技能作为候选，按 ID 去重、按相关性及上下文预算选择摘要，不全量注入正文。
- 已有绑定技能时，用户明确点名的新技能必须能被找到；普通自然语言匹配不承诺百分之百召回，但须通过验收样例。
- 内置提示词、自定义提示词、主智能体、子智能体及发布的对话 API 均应采用一致的可见性和加载规则。摘要提供可供加载的技能 ID、名称、描述和验证状态；正文按需读取。
- **🔶 产品假设 A4：** 默认保持当前“用户个人技能库”归属，同一用户的其他智能体可按权限使用；不自动向租户共享 Agent 的 `agent_skills` 写入个人技能。创建来源不是共享授权。
- 读取私有技能及文件必须校验当前用户；停用或删除后，面向任务执行的搜索、推荐和加载不再使用。所有者仍可通过管理或修改前读取查看停用技能，读取不触发执行；已删除技能不能更新。停用无法撤回已执行的动作，不承诺抹除历史消息。
- 附件在新沙箱中可以重新部署，部署目标按技能身份和版本区分，避免同名技能覆盖；返回实际可访问的路径，不依赖显示名称推断目录。
- 技能说明中要求的工具仍受当前智能体权限控制。缺少执行权限时提示能力缺失，不能通过加载技能绕过限制。

### 5.7 结果展示与技能库（FR-07）

- 复用现有技能列表及详情，新增来源类型、创建智能体、来源会话、验证状态及失败说明；旧数据无法追溯时显示“历史记录，来源未知”。
- 对话卡片根据真实创建或更新结果展示状态，不根据工具名、HTTP 200 或模型自然语言推断成功；更新时展示原版本、新版本和修改摘要。
- 结果随原消息持久化，刷新与历史会话重放不产生重复技能卡片。
- 打开技能详情后，URL 包含技能 ID，支持刷新和直接访问；无权限或已删除时展示明确状态，不退回空白页。
- 详情中的来源会话链接必须重新校验权限；来源会话已删除不影响已保存技能的使用。
- 保留已有手工编辑、停用、删除和导出方式；无需新建独立的“智能体技能库”。

### 5.8 最小结果信息（FR-08）

以下是需对模型及前端表达的业务信息，字段名供技术方案确定，并非已发布 API：

| 信息 | 内容 |
|---|---|
| 操作结果 | 已创建、复用已有、已更新、无需更新、创建失败、更新失败；均有明确业务状态 |
| 技能引用 | 成功或复用时提供 ID、名称、版本及可解析的查看入口 |
| 修改信息 | 更新时返回原版本、新版本、主要变化及文件增删改清单；无变化不递增版本 |
| 保存范围 | 当前用户私有；附件清单及保存是否完整 |
| 验证状态 | 未验证、验证通过、验证失败，与创建结果分离 |
| 来源 | 平台记录创建及每次修改的时间、用户、实际执行智能体、会话、调用/请求标识；保留原始创建来源，缺失可为空，不伪造 |
| 失败信息 | 可识别的错误类别、中文原因、相关字段或附件路径、是否可重试 |

最少区分：权限不足、参数不完整、同名冲突、版本冲突、技能不可访问、文件不存在、路径不合法、超限、存储不可用、持久化失败。前端与执行器对业务失败应保持一致，不能把返回错误文字的调用包装为业务成功。

### 5.9 模型修改与版本保留（FR-09）

**可修改范围**

- 支持名称、描述、分类、标签、触发条件、正文，以及附件新增、替换、重命名和移除；不通过该工具修改所有者、公开范围、工具权限、启用状态或验证结论。
- 以明确的技能 ID 和基准版本提交修改，不允许仅按模糊名称直接写入。修改前须读取原版本及相关文件，避免根据会话记忆重写整个技能。
- 未提交的字段和文件保持原样；清空可选字段与省略字段需有不同语义，名称和正文不得清空。修改正文不意味着替换或删除全部附件。
- 附件移除必须显式列出目标，且属于用户要求的变更范围；不能因模型未列出原文件而默认为删除。重命名或移除附件时同步修正必要引用。
- 用户要求修复脚本时允许修改该文件，未涉及的模板和参考资料按原字节保留；文件操作和完整新技能均遵守 FR-02 至 FR-04 的校验规则。

**版本与提交**

- 一次有实际变化的成功更新保留原技能 ID，版本递增一次；名称变更也不新建技能，不破坏既有绑定关系。更新为与其他技能冲突的名称时返回冲突，不合并记录。
- 每个版本保存完整元数据、正文、附件清单与文件快照，并记录修改摘要和来源；旧版本内容及对象不可被后续模型更新或手工附件编辑覆盖。
- 首期允许用户按版本读取旧内容、文件和修改说明，不要求完整差异浏览器或一键回滚。历史版本若原本缺失某些资料，应标记缺失，不补造快照。
- 版本比较与提交必须受并发保护，覆盖模型、手工编辑和附件接口。同一基准版本的两个不同更新只允许一个成功，另一项返回当前版本冲突；模型须重新读取，不能盲目覆盖。重新读取后可在原授权范围内处理互不冲突的改动；相互矛盾的改动交给用户决定。
- 同一更新请求重试只生成一个新版本；内容没有实际变化则返回“无需更新”。成功响应丢失后重试应找回原更新结果，不能因当前版本已变化再次递增。
- 元数据、正文和附件作为一个完整版本生效；任一读取、校验、存储或提交失败时，不切换最新版本，旧版保持可用。即使仅改正文，只要技能含附件，也须保证新包保留全部未修改附件，不得按纯文本降级而丢件。

**修改后的使用**

- 更新成功后刷新检索摘要和详情，新加载默认使用最新启用版本；原本停用的技能仍停用，用户可在现有管理入口启用。
- 当前会话收到明确的版本变化，继续使用前加载新版本；已开始执行的任务固定使用其已加载版本，不在执行中悄悄替换脚本。
- 运行目录按版本隔离，避免新版已删除的脚本残留在新版本目录中被误用。历史消息保留当时版本信息，不把旧执行结果改写成新版验证结果。

## 6. 成功指标

**🔵 待采集：** 当前没有创建完成率、复用率和节省时长基线。以下为建议验收及试点目标，不能作为已取得的结果。

| 指标 | 定义 | 首期目标与测量方式 |
|---|---|---|
| 创建闭环通过率 | 验收集中，从对话创建到刷新技能库后仍可读取完整内容的通过比例 | P0 场景全部通过，文本和附件分别统计 |
| 修改闭环通过率 | 验收集中，定位旧技能、修改、保存新版本及再次加载的通过比例 | P0 场景全部通过；旧版本和未修改附件完整保留 |
| 首次复用成功率 | 测试集中，新会话能发现、加载并完成既定样例的比例 | 固定回归样例全部通过，覆盖已绑定其他技能的 Agent |
| 保存可靠性 | 有效且有权限的创建、修改请求中，持久化成功、正确复用或无变化的比例；业务拒绝单列 | **建议**试点两周 ≥99%；创建、修改分开统计，记录超时与重试恢复，不隐藏基础设施失败 |
| 14 日复用率 | 创建后已满 14 天的技能中，被后续不同会话实际加载的比例 | 上线后采集，暂不设无依据的转化目标；加载与成功执行分开统计 |
| 风险护栏 | 越权访问、重试重复创建、缺件却报成功、未经验证却报已通过 | 验收测试中均为 0；上线监测异常样例 |

创建耗时分别记录模型编写、文件校验和持久化阶段，避免把长时间模型生成与存储慢混为一谈。不把现有 `use_count` 直接等同于业务执行成功次数。

## 7. 验收场景

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 用户要求从零创建文字技能 | 工具实际执行，技能库出现完整记录；显示未验证，刷新后仍存在 |
| AC-02 | 保存刚完成的任务经验 | 保存可复用步骤和参数；不复制聊天全文及无关结果；无需再次确认 |
| AC-03 | 保存脚本、参考文档及二进制模板 | 附件清单与字节内容一致；删除源文件或重建沙箱后仍可读取、部署 |
| AC-04 | 工具未开放或缺少后续执行工具 | 创建或执行受到相应限制；不给虚假成功反馈，不修改工具权限 |
| AC-05 | 智能体有绑定技能和自定义提示词 | 新会话明确要求本人新建技能时能够发现并加载；原绑定技能仍可用 |
| AC-06 | 跨用户及同租户另一成员访问 | 搜索、详情、附件、历史结果链接均不能泄露私有技能；无自动共享绑定 |
| AC-07 | 非法路径、越界链接、文件不存在或超限 | 错误定位到具体文件或字段；不产生半成品可见记录，不静默丢弃附件 |
| AC-08 | 请求重试、并发相同创建、成功响应丢失 | 返回同一个 ID，只有一份技能；同名不同内容返回冲突，不覆盖 |
| AC-09 | MinIO 或数据库失败 | 带附件创建不报成功；纯文本降级行为符合规则；孤立对象可追踪处理 |
| AC-10 | 保存后立即使用 | 当前会话按返回 ID 加载；无需重新开始对话；执行权限仍有效 |
| AC-11 | 验证及内容变更 | 未执行不标通过；失败保存为停用；执行相关内容修改后旧验证结论失效，纯分类或标签修改按 FR-04 保留证据 |
| AC-12 | 刷新、直接链接、来源会话删除 | 正确打开技能或显示明确不可访问状态；卡片不重复；来源删除不破坏技能 |
| AC-13 | 主动建议与拒绝 | 用户未同意或拒绝时无持久化写入，原任务正常完成 |
| AC-14 | Portal、子智能体和发布的对话 API | 在各入口相同身份和权限下，归属、结果状态与检索规则一致；Portal 可直接查看本人创建结果 |
| AC-15 | 停用与删除 | 后续不推荐和加载；历史卡片保留原事件并提示当前不可用，不伪造删除前不存在 |
| AC-16 | 技能目录冲突与新环境部署 | 不同技能或版本互不覆盖；脚本引用和返回的实际路径一致 |
| AC-17 | 兼容旧技能和手工创建 | 旧内容可读，来源未知显示正确，导入导出、手工编辑及工具原参数调用无非预期回归 |
| AC-18 | 用户要求修改现有正文和元数据 | 先读取目标，按要求保存；ID 不变，版本仅增一次，未涉及字段保留，展示修改摘要 |
| AC-19 | 仅改正文或替换单个脚本 | 所有未修改附件按原字节保留；只改正文也不会生成缺件 ZIP |
| AC-20 | 新增、重命名、移除附件 | 只操作明确目标，必要引用同步修正；新版本目录无已移除文件，旧版本仍可读取原文件 |
| AC-21 | 模型更新与人工编辑并发 | 相同基准版本的不同修改只提交一个，另一项返回版本冲突；无静默覆盖和丢失更新 |
| AC-22 | 更新重试、无变化及中途失败 | 重试返回同一结果，无变化不增版本；存储或提交失败保持原最新版本完整可用 |
| AC-23 | 修改工具未开放、目标有歧义或无写权限 | 明确权限失败或先定位目标；不能借创建工具覆盖，不按模糊名称修改，不泄露他人内容 |
| AC-24 | 更新后复用与历史保留 | 新加载使用新版本，在途任务继续使用旧版本；原验证结论按变更范围失效，历史结果不被改写 |
| AC-25 | 停用技能修改、跨来源修改及仅预览要求 | 停用状态保留；本人手工、导入或其他智能体创建的技能均可按权限修改；“先给方案”不写入 |

验证分层：参数和状态可使用单元测试；并发、事务和隔离必须在真实 PostgreSQL 验证；附件持久化和沙箱恢复必须使用真实 MinIO 与 Docker；对话和刷新须做浏览器及实际模型调用验证。项目 PostgreSQL 集成测试需显式启用 `--run-postgres`，跳过的测试不能记为通过。

## 8. 依赖、风险与交付顺序

| 依赖或风险 | 要求 |
|---|---|
| 已有工具入口但用户不可用 | 先在实际失败场景核对版本、工具配置、模型调用和返回结果，再决定配置修复与代码工作量 |
| DB 与对象存储跨系统写入 | 设计可恢复的保存流程和幂等边界，按最终可见结果验收 |
| 模型与管理页面使用不同修改路径 | 共同遵守版本冲突、旧包不可变和未修改附件保留规则；补齐旧版快照信息不足的问题 |
| 主/子智能体、自定义提示词、发布快照分支不同 | 统一创建和发现规则；明确发布快照下哪些能力随配置重新发布生效 |
| 个人技能误挂到租户共享智能体 | 个人检索与 Agent 共享配置分别处理，每次读取校验归属 |
| 长正文、附件过多或工具输出截断 | 保存前校验限额；结果保留关键 ID 和状态，正文按需读取 |
| 方法不完整或业务错误 | 显示验证范围，提供人工编辑与停用；不以自动生成替代业务验收 |

建议按以下里程碑交付，均为 P0 的组成部分：

1. **M1：文字创建与修改闭环。** 核实创建入口，开放修改工具，补齐读取后修改、来源、结果语义、版本并发控制与幂等；真实对话创建、修改并读回。
2. **M2：附件与版本完整性。** 接通工作区文件收集、局部附件修改、完整版本快照、错误恢复及新沙箱部署；验证真实对象存储与原附件保留。
3. **M3：复用与界面。** 补齐已有绑定技能场景的发现、跨入口权限、创建/更新卡片、旧版本查看和详情定位，完成完整验收集。

技术方案再确定工具参数结构、数据迁移、事务协调和前端组件拆分。本需求不预先承诺排期，需在实际故障定位和范围评审后估算。

## 9. 非目标与兼容边界

- 不允许技能创建或修改操作新增用户权限、启用未授权工具或改变智能体的系统身份。
- 首期支持模型按用户指令修改指定技能；无指令、无适用授权时只提出修改建议，不后台批量改写。删除整个技能、合并技能和存量批量整理不纳入模型工具范围。
- 不引入完整审批流、团队市场和无限版本审计。
- 不要求每次对话都生成技能；避免把普通问答、记忆和任务进度存成技能。
- 不承诺任意自然语言任务都能可靠提炼为技能，也不承诺未验证脚本执行成功。
- 附件限额、私有默认值及原有只传名称与正文的工具调用需兼容；新生成技能按本需求提高内容完整性要求，历史技能不批量强制重写。

## 10. 待确认决策与评审建议

| 编号 | 待确认事项 | 本草案采用的默认方案 |
|---|---|---|
| Q1 | 是否允许无指令自动沉淀 | 首期主动建议，用户明确要求或同意后创建；全自动模式放 P1 |
| Q2 | 新技能的默认使用范围 | 当前用户私有，同一用户其他智能体可按权限检索；不默认绑定共享 Agent |
| Q3 | 未验证技能是否立即可用 | 允许保存并启用，明确未验证；验证失败则停用 |
| Q4 | 大型模板与附件额度 | 采用 A2 限额；超过 1 MiB 的单模板需求需评审调整统一限制 |
| Q5 | 当前不可创建的实际原因 | 开发前获取一个实际失败会话和智能体配置，核对本地与部署版本 |

用户已明确要求首期同时支持模型创建和修改技能。表中默认策略用于评审，并非均已由用户确认。当前最明确的是创建、修改与复用的验收闭环；证据最弱的是实际故障根因和上线业务收益。评审优先确认 Q1—Q4，实施前完成 Q5；不要将配置修复和全量功能建设混为一个已确定工作量。
