# 大文件处理技术方案

## 1. 问题定义

LLM 上下文窗口有限（当前配置 128K tokens ≈ 30 万汉字 / 300KB 纯文本），而用户可能上传远超此体积的文件：

| 文件类型 | 典型大小 | 直接读入上下文 |
|---------|---------|-------------|
| CSV 数据表 | 10-200MB | 不可能 |
| PDF 文档 | 5-100MB | 不可能 |
| 代码压缩包 | 50-500MB | 不可能 |
| 日志文件 | 100MB-1GB | 不可能 |
| JSON 导出 | 1-50MB | 不可能 |

**核心原则：绝不将大文件内容放入 LLM 上下文。文件进入沙箱 / MinIO，智能体通过工具按需访问。**

## 2. 整体架构

```
┌──────────┐   上传文件     ┌──────────────┐   存储    ┌─────────┐
│  前端 UI  │ ────────────→ │  FastAPI 路由 │ ───────→ │  MinIO   │
└──────────┘               └──────┬───────┘          └────┬────┘
                                  │                       │
                         文件元数据 + 预览           注入文件到沙箱
                                  │                       │
                                  ▼                       ▼
┌─────────────────────────────────────────────────────────────┐
│                       智能体 ReAct 循环                       │
│                                                             │
│  系统提示 (轻量引用):                                        │
│  "用户上传了文件 sales_2024.csv (45MB, 1,200,000 行, 32 列)" │
│                                                             │
│  可用工具:                                                   │
│  file_info  → 获取结构化元数据 (schema, 统计, 行数...)        │
│  file_read  → 按行范围读取 (offset + limit, 自动截断)         │
│  file_grep  → 正则搜索 (返回匹配行 + 上下文)                  │
│  file_query → SQL 查询 (DuckDB 引擎, 针对结构化文件)          │
│  file_slice → 按字节/行范围切片                               │
│  run_shell  → head/tail/wc/awk/sed/jq (沙箱原生能力)         │
└─────────────────────────────────────────────────────────────┘
```

## 3. 分阶段设计

### 阶段 1: 文件上传

新增端点 `POST /api/chat/files`：

```python
# 请求: multipart/form-data
file: UploadFile          # 文件本体 (最大 500MB)
session_id: UUID (可选)    # 关联会话
workspace_id: UUID (可选)  # 目标工作区

# 响应: FileInfo
{
  "file_id": "uuid",
  "filename": "sales_2024.csv",
  "size": 47185920,        # 字节
  "mime": "text/csv",
  "workspace_path": "uploads/sales_2024.csv",
  "meta": {                # 异步补充
    "status": "analyzing"  # → "ready" / "error"
  }
}
```

**上传流程：**
1. 接收文件流，验证 MIME 类型（magic bytes）和大小配额
2. 按用户 + 工作区计算已用空间，超配额拒绝（默认 500MB/工作区）
3. 分片写入 MinIO：`workspace-files/{workspace_id}/uploads/{uuid}.{ext}`
4. 返回 file_id 后，**异步触发文件分析**（见阶段 2）
5. 通过 SSE 事件通知前端分析完成

### 阶段 2: 文件分析（异步）

上传完成后，在后台沙箱中运行分析脚本，提取结构化元数据：

```python
async def analyze_file(file_path: str, mime: str) -> FileMeta:
    """在沙箱中分析文件，返回元数据。不读取完整内容。"""
```

**分析策略按文件类型：**

| 类型 | 分析工具 | 提取信息 |
|------|---------|---------|
| CSV/TSV | `csvstat` / Python csv | 行数、列名、列类型、空值率、样本行(前5行) |
| JSON | `jq` / Python json | 顶层类型、key 列表、数组长度、深度 |
| JSONL | `wc -l` + 首行解析 | 行数、字段名、首行示例 |
| 纯文本 | `wc -l/c` + `file` 命令 | 行数、编码、前20行预览 |
| PDF | `pdfinfo` + `pdftotext` | 页数、标题、前1页文本 |
| DOCX | `python-docx` | 段落数、前3段文本 |
| 代码压缩包 | `unzip -l` / `tar tzf` | 文件树、文件计数、语言分布 |
| 日志 | 首行时间戳解析 | 时间范围、行数、格式 |
| SQL | 解析 DDL | 表名、行数估算 |

**元数据结构：**

```python
@dataclass
class FileMeta:
    file_type: str          # csv | json | jsonl | text | pdf | docx | archive | log | sql | binary
    encoding: str           # utf-8 | gbk | ...
    line_count: int | None  # 文本文件行数
    byte_size: int
    preview: str            # 前 2000 字符预览（供系统提示注入）
    schema: dict | None     # 结构化文件的 schema
    # CSV 特有
    csv_columns: list[ColumnInfo] | None
    csv_delimiter: str | None
    # PDF 特有
    page_count: int | None
    # 压缩包特有
    file_tree: list[str] | None
    # 日志特有
    time_range: tuple[str, str] | None
    log_format: str | None
```

### 阶段 3: 智能体感知

元数据就绪后，文件以**轻量引用**形式注入系统提示，**绝不注入文件内容**：

```
## 可用文件 (workspace/uploads/)

1. **sales_2024.csv** — CSV 文件，45MB，1,200,000 行
   列: order_id(str), customer(str), amount(float), date(date), category(str), ...
   预览(前3行):
   order_id,customer,amount,date,category
   ORD001,张三,1500.00,2024-01-15,电子产品
   ORD002,李四,230.50,2024-01-15,图书
```

这样智能体知道文件存在及其结构，但只消费 ~500 tokens，而不是 1,200,000 行数据。

### 阶段 4: 大文件访问工具

#### 4a. `file_info` — 获取文件元数据

```python
{
  "name": "file_info",
  "description": "获取工作区中一个文件的详细元数据（行数、列信息、预览等），不读取完整内容。",
  "parameters": {
    "path": {"type": "string", "description": "文件路径，相对于 /workspace"},
    "refresh": {"type": "boolean", "description": "是否强制重新分析（默认 false）"}
  }
}
```

直接返回阶段 2 缓存的 `FileMeta`，0 成本。

#### 4b. `file_read` — 安全的按范围读取（增强 read_file）

```python
{
  "name": "file_read",
  "description": "读取文件的一部分。对于大文件，必须指定 offset 和 limit。省略时默认读取前 200 行。",
  "parameters": {
    "path": {"type": "string"},
    "offset": {"type": "integer", "description": "起始行号 (0-based, 默认 0)"},
    "limit": {"type": "integer", "description": "读取行数 (默认 200, 最大 500)"}
  }
}
```

**安全机制：**
- 检测文件大小，超过 1MB 时**强制要求** offset/limit 参数
- 返回结果最大 10K 字符（复用 executor 现有截断逻辑）
- 返回内容末尾附 `[第 X-Y 行 / 共 N 行]` 位置信息

#### 4c. `file_grep` — 正则搜索

```python
{
  "name": "file_grep",
  "description": "在文件中搜索匹配正则表达式的行，返回匹配行及上下文。适合在大型日志、CSV 中查找特定内容。",
  "parameters": {
    "path": {"type": "string"},
    "pattern": {"type": "string", "description": "正则表达式"},
    "context_lines": {"type": "integer", "description": "匹配行前后各显示几行 (默认 2, 最大 10)"},
    "max_matches": {"type": "integer", "description": "最多返回多少个匹配 (默认 20, 最大 100)"},
    "ignore_case": {"type": "boolean", "description": "忽略大小写 (默认 true)"}
  }
}
```

底层用 `grep -n -i -A {n} -B {n} -m {max} '{pattern}' {path}` 实现，高效且不加载全文件。

#### 4d. `file_query` — SQL 查询结构化文件

```python
{
  "name": "file_query",
  "description": "对 CSV/TSV/JSON/Parquet 文件执行 SQL 查询。使用 DuckDB 引擎，支持聚合、过滤、JOIN。",
  "parameters": {
    "path": {"type": "string", "description": "文件路径"},
    "query": {"type": "string", "description": "SQL SELECT 语句。表名固定为 'data'。例如: SELECT category, SUM(amount) FROM data GROUP BY category ORDER BY 2 DESC LIMIT 10"},
    "format": {"type": "string", "enum": ["table", "json"], "description": "输出格式 (默认 table)"}
  }
}
```

**实现：** 在沙箱中安装 DuckDB CLI，执行：

```bash
duckdb -csv -c "SELECT category, SUM(amount) as total FROM '/workspace/uploads/sales_2024.csv' GROUP BY category ORDER BY total DESC LIMIT 10"
```

DuckDB 原生支持直接查询 CSV/JSON/Parquet 文件，无需导入，列名自动推断。

**安全措施：**
- 只允许 SELECT 语句
- 禁止 `sqlmeta` / `pragma` 等非查询语句
- 结果限制 1000 行 + 10K 字符截断
- 查询超时 30 秒

#### 4e. `file_summarize` — 分块 LLM 摘要

```python
{
  "name": "file_summarize",
  "description": "对较大文件进行分块摘要。将文件按固定大小分块，逐块调用 LLM 生成中间摘要，最后合并成总摘要。",
  "parameters": {
    "path": {"type": "string"},
    "chunk_lines": {"type": "integer", "description": "每块行数 (默认 500, 最大 2000)"},
    "max_chunks": {"type": "integer", "description": "最多处理多少块 (默认 10, 最大 30)"}
  }
}
```

**分块摘要流程（Map-Reduce）：**

1. **Map 阶段：** 将文件按 `chunk_lines` 行分块，每块调用快速 LLM 生成该块的摘要（100-200 字）
2. **Reduce 阶段：** 将所有块的摘要合并，调用 LLM 生成总摘要
3. 总摘要返回给主智能体，不占据主上下文

这利用了现有 LLM provider 基础设施，复用 `generate_summary()` 的模式。

### 阶段 5: 工具安全保障

#### 5a. 防误读大文件

`read_file` 工具增加守卫：

```python
async def _execute_in_sandbox(self, tool_name, args, ...):
    if tool_name == "read_file":
        path = args["path"]
        # 检查文件大小
        size = await self._get_file_size(sandbox, path)
        if size > 1_000_000:  # 1MB
            if "offset" not in args or "limit" not in args:
                return (
                    f"文件 {path} 大小为 {size:,} 字节，超过安全读取上限。"
                    f"请使用 file_read 并指定 offset 和 limit 参数，"
                    f"或使用 file_grep 搜索特定内容，"
                    f"或使用 file_query 进行 SQL 查询。"
                    f"\n文件前 500 字符预览:\n{preview}"
                )
        # 正常读取，增加行数限制
        args.setdefault("limit", 200)
```

#### 5b. SQL 注入防护（file_query）

```python
def _validate_sql(query: str) -> None:
    """只允许 SELECT 查询，禁止 DDL/DML/DCL。"""
    cleaned = query.strip().upper()
    if not cleaned.startswith("SELECT"):
        raise SecurityError("只允许 SELECT 查询")
    forbidden = ["INSERT", "UPDATE", "DELETE", "DROP", "CREATE", "ALTER",
                  "TRUNCATE", "GRANT", "REVOKE", "PRAGMA", "ATTACH"]
    for kw in forbidden:
        if kw in cleaned:
            raise SecurityError(f"禁止使用 {kw}")
```

#### 5c. 路径安全

复用现有 `_validate_path()` 逻辑，所有路径限制在 `/workspace/` 下，防止目录遍历。

### 阶段 6: 处理流水线（按文件类型）

不同类型文件智能体采用不同策略：

```
CSV/TSV 大文件:
  1. file_info → 了解列名和类型
  2. file_query → "SELECT column, COUNT(*) FROM data GROUP BY column"
  3. file_query → "SELECT * FROM data WHERE condition LIMIT 100"
  4. file_read  → 抽样验证特定行

PDF/文档:
  1. file_info   → 页数、标题
  2. file_read   → 前 500 行（pdf2txt 转换后）
  3. file_grep   → 搜索关键词
  4. file_summarize → 分块摘要长文档
  5. knowledge_retrieval → 如果文档已入库 RAGFlow

代码压缩包:
  1. run_shell "unzip -l file.zip" → 文件树
  2. run_shell "unzip file.zip -d /workspace/extracted/"
  3. 常规 read_file / grep 操作单个源文件

日志文件:
  1. file_info  → 时间范围、格式
  2. file_grep "ERROR|FATAL" → 搜索错误
  3. run_shell "awk '\$1 >= start && \$1 <= end' log" → 时间范围切片
  4. run_shell "awk '{print \$3}' log | sort | uniq -c | sort -rn" → 统计

JSON 大文件:
  1. file_info → 顶层结构
  2. run_shell "jq '.items | length' file.json" → 数组长度
  3. run_shell "jq '.items[0:10]' file.json" → 前10条
  4. run_shell "jq '[.items[] | {id, name}] | group_by(.type)' file.json"
```

## 6. 关键设计决策

**Q: 为什么不让智能体直接 `run_shell("cat huge_file.csv")`？**

A: `run_shell` 的输出会被 `ToolExecutor._truncate()` 截断到 10K 字符，而 `read_file` 同理。新工具不是替代 shell 能力，而是提供**结构化、可导航**的访问方式。智能体可以先了解文件结构，再有针对性地查询，而不是盲目 cat。

**Q: 为什么需要 DuckDB 而不是直接用 Python pandas？**

A: DuckDB 是零依赖的单一二进制文件，可直接查询磁盘上的 CSV/JSON/Parquet 文件而不需导入。启动快（<100ms），内存效率高。在 Docker 沙箱中只需 `apt install duckdb` 或复制一个静态二进制。

**Q: 分块摘要 vs RAGFlow 入库，选哪个？**

A: 互补关系。分块摘要是无状态的一次性操作，适合临时探索。RAGFlow 入库是持久化索引，适合反复查询的文档。P0-P2 先做分块摘要，P3 再做 RAGFlow 集成。

**Q: 上传文件大小限制？**

A: 默认 500MB/文件、500MB/工作区（可配置）。超过此限制建议用户自行预处理（分割文件、数据库导入等）。
