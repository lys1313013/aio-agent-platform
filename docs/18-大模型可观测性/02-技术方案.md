# 大模型可观测性技术方案

> 日期：2026-08-06
> 对应《01-需求文档.md》，说明实现要点：三张明细表、预聚合表、异步采集、接口、Prometheus、数据生命周期与实施计划。本期不接入 Langfuse，不启用成本。

## 1. 架构总览（三路并行）

```
                       ┌────────────────────────────┐
   AgentLoop / 工具执行 / 会话 / 后台任务
                       │  observation/recorder.py   │
                       │  (异步队列 + BatchWriter)   │
                       └────────────┬───────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  明细表(事实源)              预聚合表(报表秒查)             Prometheus(实时告警)
  llm_call_logs               token_usage_daily            /metrics
  tool_call_logs              tool_usage_daily             llm_requests_total ...
  agent_trace_logs            performance_daily
        │                           │                           │
        └───────────┬───────────────┘                           │
                    ▼                                           ▼
         /api/observability 聚合查询                    Alertmanager / 告警
                    ▼
            前端 /observability
```

- **明细表**为事实源：一次 LLM 调用、一次工具调用、一次 Agent.run 各一行，供精确聚合与 Trace 下钻。
- **预聚合表**由明细表按日/按用户归并（或采集时直接累计），供报表秒查。
- **Prometheus** 只承载实时计数/直方图，供监控板实时值与告警，不承载历史明细。

## 2. 明细表设计

三张表写入均为**异步 fire-and-forget**，失败只记日志，绝不阻塞主链路。

### 2.1 `llm_call_logs`（每次 LLM 调用一行）

```
id            UUID PK
trace_id      UUID      -- Agent 执行实例，见 §6 链路 ID
session_id    UUID
user_id       UUID
tenant_id     UUID
agent_id      UUID NULL
model_id      UUID NULL
model         String(128)   -- 模型标识
provider      String(32)
call_order    Int           -- 本次执行中的第几轮
prompt_tokens / completion_tokens / total_tokens  Int
cache_read_tokens / cache_creation_tokens         Int
context_window    Int NULL  -- 模型窗口，从模型能力表查得
context_utilization Float   -- prompt_tokens / context_window
ttft_ms       Int NULL      -- 首 token 延迟
duration_ms   Int           -- 总耗时
output_tokens_per_sec Float NULL
retry_count   Int           -- 重试次数
final_status  String(16)    -- success / failed
error_type    String(32) NULL
stop_reason   String(16) NULL
temperature   Float NULL
max_tokens    Int NULL
tools_count   Int           -- 本次请求携带的工具数
created_at    DateTime(tz)  -- 索引 (tenant_id, created_at), (session_id), (trace_id)
```

采集点：`llm/client.py` 的 `complete()` 与 `stream()`（`done` chunk 携带 usage）返回后调用 recorder 落一行。TTFT 在 stream 首个 chunk 到达时记录。

### 2.2 `tool_call_logs`（每次工具调用一行）

```

trace_id        UUID

user_id         UUID

is_truncated    Bool          -- 输出被 executor 截断

采集点：`tools/executor.py` 已有 `duration_ms`，在返回 `ToolResult` 处补记录。参数/输出大小在写入前计算字符数与字节数（可采样，超过阈值记录，控制存储）。

### 2.3 `agent_trace_logs`（每次 Agent.run 一行）

```
id                     UUID PK

## 3. 预聚合表设计

| 表 | 粒度 | 字段 | 说明 |
|---|---|---|---|
| `token_usage_daily`（扩展） | user+date+model | 增列 `cache_read_tokens`、`cache_creation_tokens` | 复用现有写入链路，cost_usd 维持 0 |
| `tool_usage_daily`（新） | user+date+tool | 调用次数、成功次数、失败次数、avg/p95 duration_ms、错误率、est_injected_tokens 合计 | 工具排行/工具错误率报表 |
| `performance_daily`（新） | tenant+date | trace 数、成功/失败/中断数、对话平均耗时、avg/p95 LLM 延迟、avg TTFT、平均 token/trace、压缩触发数及节省量、多轮占比 | 对话质量与平台健康 |

聚合方式：采集侧在写明细时同步 upsert 预聚合（与 `core/usage.py` 的 ON CONFLICT 累加同模式），避免事后跑批。后台每日零时补跑一次校正（处理漏写）。

## 4. 异步采集实现

`observation/recorder.py`（新建）：

```python
class Recorder:
    def __init__(self):
        self._queue: asyncio.Queue[Record] = asyncio.Queue(maxsize=10000)
        self._batch: list[Record] = []
        self._task: asyncio.Task | None = None

    def start(self) -> None:        # lifespan 中启动
        self._task = asyncio.create_task(self._flush_loop())

    async def _flush_loop(self) -> None:   # 每 2s 或攒满 500 条 flush
        while True:
            await asyncio.sleep(2.0)
            if self._batch:
                await self._write_batch(self._batch); self._batch = []

    def record_llm_call(self, **fields) -> None:   # 非阻塞，塞队列
        ...
    def record_tool_call(self, **fields) -> None:  # 同
    def record_trace(self, **fields) -> None:      # 同
```

- 队列满时丢弃最旧批次并打 `observation_queue_overflow` 日志（保主链路）。
- 写入用 `pg_insert` + `executemany` 风格批量 INSERT。
- 预聚合 upsert 在同一批事务内完成。
- `shutdown` 时 flush 剩余批次。
- 在 `interface/api.py` lifespan 中实例化并挂到 `app.state.recorder`，AgentLoop / executor / cron 通过 `get_recorder()` 获取。

## 5. 数据来源对照

| 指标 | 采集点 | 说明 |
|---|---|---|
| LLM 调用（token/耗时/TTFT/重试/stop_reason） | `llm/client.py` complete/stream | 从 provider 返回的 usage 与计时 |
| 缓存 token | `llm/client.py` | OpenAI `prompt_tokens_details.cached_tokens`、Anthropic `cache_creation/read_input_tokens`（补齐解析） |
| 工具调用（耗时/错误/输出体量） | `tools/executor.py` | `ToolResult.duration_ms` 已有，补 is_error/error_type/输出大小 |
| Trace 汇总 | `core/agent.py` run() finally | 累计 token、轮数、耗时、压缩信息 |
| 压缩事件 | `core/context.py` | 压缩前后 token、摘要 token |
| 委派耗时 | `delegation/handler.py` | 复用 `delegation_record.duration_ms`，join 到 tool_call_logs（exec_type=delegation） |
| 后台任务 | `cron_jobs/*` | 执行开始时构造 trace_id，结束统一走 recorder |
| 渠道维度 | `channel_session_mappings` | 会话关联渠道 |

**token 估算兜底**：本地模型/旧记录无 usage 时，用 `core/context.py` 现有估算函数（≈ chars/4）补 `est_injected_tokens`、`prompt_tokens`，并标记来源为 estimated。

## 6. 链路 ID、脱敏与时区

- **trace_id 贯穿**：HTTP 入口（chat/SSE/webhook）生成 `trace_id`，写入响应头 `X-Trace-Id`；cron、委派、宠物分别构造；SSE 事件流中携带，供前端下钻关联。
- **脱敏**：`tool_call_logs` 不存参数全文，只存大小；如需摘要存脱敏后的参数键名列表（敏感键如 api_key 打码）。LLM 调用不存输入/输出内容（仅 token 与耗时）。
- **错误分类枚举**：`timeout / connection / rate_limit / server_error / context_too_long / content_filter / invalid_request / tool_error / unknown`。LLM 错误在 `llm/client.py` 异常处归一，工具错误在 executor 归一。
- **时区**：明细表存带时区时间戳；预聚合按服务器日期（与 `token_usage_daily` 一致），MVP 不做时区对齐。

## 7. API 接口设计

统一前缀 `/api/observability`，鉴权为管理员角色（沿用 `_check_scope` 思路但强制 admin）。前端 `/observability` 各子模块对应：

| 接口 | 用途 | 对应模块 |
|---|---|---|
| `GET /api/observability/overview?window=1h\|24h\|7d` | 指标卡 + 序列：LLM 调用量/失败率、工具调用量/失败率、延迟 P95、token 速率、上下文利用率 P95 | 实时监控板 |
| `GET /api/observability/traces?page=&page_size=&filters=` | Trace 分页列表 | Trace 明细 |
| `GET /api/observability/traces/{trace_id}` | 单 trace 逐步下钻（LLM 调用+工具调用+压缩事件） | Trace 详情 |
| `GET /api/observability/stats?by=model\|agent\|user\|tenant&metric=tokens\|duration\|error&start=&end=` | 聚合分布 | 聚合报表 |
| `GET /api/observability/tool-ranking?metric=duration\|error\|count\|tokens&start=&end=&top=20` | 工具排行 | 工具排行 |
| `GET /api/observability/tools/{tool}/trend?granularity=minute\|hour\|day&start=&end=` | 单工具调用量/失败率时间序列（趋势下钻） | 工具趋势 |
| `GET /api/observability/quality?start=&end=` | 对话质量 + 压缩监控 + 首响分布 | 对话质量 |
| `GET /api/observability/alerts` | 告警历史（第二期） | 告警 |
| `GET /api/observability/export?` | CSV 导出（复用当前筛选） | 各模块导出 |
| `GET /metrics` | Prometheus 文本格式 | 监控/告警 |

查询均落在预聚合表；Trace 下钻查明细表（限制单 trace 查询范围，trace 内行数可控）。

**趋势查询策略**：监控板/单工具趋势的**分钟、小时序列查明细表**（`llm_call_logs` / `tool_call_logs` 按时间 bucket 聚合，近 24h 量级可控、已有时间索引）；**日及更长窗口查预聚合日表**。该策略统一封装为查询层函数，前端只传 `granularity`，不感知数据来源。

## 8. Prometheus 指标（/metrics）

在 `interface/api.py` 挂 `/metrics`（prometheus-client），Prometheus 每 15s 抓取：

```
llm_requests_total{model,provider,status}
llm_latency_seconds{model}                    # Histogram → P50/P95/P99
llm_ttft_seconds{model}
llm_tokens_total{model,type}                  # type=prompt|completion|cache_read|cache_creation
llm_retries_total{model}
tool_requests_total{tool,status}
tool_duration_seconds{tool}                   # Histogram
agent_turns_total{status}
agent_trace_duration_seconds{}                # Histogram
context_utilization_ratio{model}              # Gauge，窗口内 P95（由采集端周期性计算）
```

指标更新在 recorder 的 flush 循环内顺带维护（原子更新 Counter/Histogram），避免在热路径加锁。

**告警规则**（Alertmanager，第二期落地）：

```yaml
- alert: LLMErrorRateSpike
  expr: rate(llm_requests_total{status="failed"}[10m]) / rate(llm_requests_total[10m]) > 0.05
  for: 5m
- alert: ToolErrorRateHigh
  expr: rate(tool_requests_total{status="failed"}[10m]) / rate(tool_requests_total[10m]) > 0.2
- alert: LLMLatencyHigh
  expr: histogram_quantile(0.95, rate(llm_latency_seconds_bucket[5m])) > 30
- alert: ContextUtilizationHigh
  expr: context_utilization_ratio > 0.9
```

## 9. 数据生命周期与容量

| 数据 | 存储 | 保留期 | 容量预估 |
|---|---|---|---|
| 明细表 ×3 | PostgreSQL | 永久 | 按调用量：每 10 万 LLM 调用 ≈ llm_call_logs 数十 MB；需关注总行数，必要时 3 期引入分区 |
| 预聚合表 | PostgreSQL | 长期 | 低 |
| Prometheus | 独立实例 | 15 天默认 | 按指标基数 |

- 明细表建议**按 created_at 做 PostgreSQL 分区（月分区）**，配合永久保留策略避免单表膨胀与索引退化。
- 预聚合表与明细表同库，查询走预聚合，明细仅用于下钻。
- 写入量监控：`observability_write_lag`、队列长度暴露到 /metrics。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 采集拖慢主链路 | 全异步队列 + 批量写；队列满丢弃并告警 |
| 明细表膨胀 | 月分区 + 预聚合先行；观察写入量决定是否采样 |
| 缓存 token 解析不全 | OpenAI/Anthropic 两 provider 分别兜底解析，缺失置 0 并标记 |
| 错误分类口径不一致 | 统一枚举在 llm/executor 归一，测试覆盖各异常分支 |
| trace 下钻性能 | 按 trace_id 索引 + 单 trace 行数上限（如 200 行） |
