## 2. 后端核心依赖

### 2.1 LLM 调用 — `openai` + `anthropic`

**选型**：同时使用 OpenAI 和 Anthropic 两个官方 Python SDK，通过一个轻量的 Provider 抽象层统一调用。

**理由**：
- OpenAI 和 Anthropic 是目前最重要的两家 LLM 供应商，API 格式有本质差异
- OpenAI 的 function calling 格式已成为事实标准，DeepSeek、OpenRouter、Ollama 等均兼容
- Anthropic 的 Messages API 有独立的格式规范（system 独立参数、content block 数组、tool_use/tool_result block 等），无法通过 `base_url` 兼容
- 用两套原生 SDK + 一层薄 Provider 抽象，既能利用各家最新特性，又不让上层代码感知差异

**Provider 抽象层设计**：

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import AsyncIterator

@dataclass
class LLMMessage:
    """统一的内部消息格式"""
    role: str                           # system / user / assistant / tool
    content: str | list[dict] | None    # 文本或结构化内容块
    tool_calls: list[dict] | None = None
    tool_call_id: str | None = None

@dataclass
class LLMResponse:
    """统一的响应格式"""
    content: str
    tool_calls: list[ToolCall] | None = None
    usage: TokenUsage | None = None
    stop_reason: str | None = None      # end_turn / tool_use / max_tokens

@dataclass
class LLMStreamChunk:
    """统一的流式片段"""
    type: str                           # text_delta / tool_call_start / tool_call_delta / done
    content: str | None = None
    tool_call: dict | None = None

class LLMProvider(ABC):
    """Provider 抽象基类"""
    
    @abstractmethod
    async def complete(
        self,
        messages: list[LLMMessage],
        tools: list[dict] | None = None,
        temperature: float = 0.7,
        max_tokens: int | None = None,
    ) -> LLMResponse: ...
    
    @abstractmethod
    async def stream(
        self,
        messages: list[LLMMessage],
        tools: list[dict] | None = None,
        temperature: float = 0.7,
        max_tokens: int | None = None,
    ) -> AsyncIterator[LLMStreamChunk]: ...
```

**OpenAI Provider 实现**：

```python
from openai import AsyncOpenAI

class OpenAIProvider(LLMProvider):
    """
    支持: OpenAI, DeepSeek, OpenRouter, Ollama, vLLM, LocalAI
    所有兼容 OpenAI Chat Completions API 格式的服务
    """
    
    def __init__(self, model: str, base_url: str, api_key: str):
        self.client = AsyncOpenAI(base_url=base_url, api_key=api_key)
        self.model = model
    
    async def complete(self, messages, tools=None, **kwargs) -> LLMResponse:
        # 将 LLMMessage 转为 OpenAI 格式
        openai_messages = self._convert_messages(messages)
        openai_tools = self._convert_tools(tools) if tools else None
        
        response = await self.client.chat.completions.create(
            model=self.model,
            messages=openai_messages,
            tools=openai_tools,
            **kwargs
        )
        return self._parse_response(response)
    
    def _convert_messages(self, messages: list[LLMMessage]) -> list[dict]:
        """统一格式 → OpenAI 格式"""
        result = []
        for msg in messages:
            if msg.role == "tool":
                result.append({
                    "role": "tool",
                    "content": msg.content,
                    "tool_call_id": msg.tool_call_id,
                })
            elif msg.role == "assistant" and msg.tool_calls:
                result.append({
                    "role": "assistant",
                    "content": msg.content,
                    "tool_calls": [
                        {
                            "id": tc["id"],
                            "type": "function",
                            "function": {
                                "name": tc["name"],
                                "arguments": json.dumps(tc["arguments"]),
                            }
                        }
                        for tc in msg.tool_calls
                    ],
                })
            else:
                result.append({"role": msg.role, "content": msg.content})
        return result
```

**Anthropic Provider 实现**：

```python
from anthropic import AsyncAnthropic

class AnthropicProvider(LLMProvider):
    """
    支持: Anthropic Claude 系列模型
    使用 Anthropic Messages API 原生格式
    """
    
    def __init__(self, model: str, api_key: str):
        self.client = AsyncAnthropic(api_key=api_key)
        self.model = model
    
    async def complete(self, messages, tools=None, **kwargs) -> LLMResponse:
        # 提取 system message（Anthropic 的 system 是独立参数，不在 messages 数组中）
        system, anthropic_messages = self._convert_messages(messages)
        anthropic_tools = self._convert_tools(tools) if tools else None
        
        response = await self.client.messages.create(
            model=self.model,
            system=system,                        # system 独立参数
            messages=anthropic_messages,           # content 为 block 数组
            tools=anthropic_tools,
            max_tokens=kwargs.get("max_tokens", 8192),
        )
        return self._parse_response(response)
    
    def _convert_messages(self, messages: list[LLMMessage]) -> tuple[str, list[dict]]:
        """
        统一格式 → Anthropic 格式
        关键差异:
        - system 消息提取为独立字符串
        - assistant 消息的 content 是 block 数组（TextBlock + ToolUseBlock）
        - tool 结果用 role=user + ToolResultBlock
        """
        system_parts = []
        result = []
        
        for msg in messages:
            if msg.role == "system":
                system_parts.append(msg.content)
            elif msg.role == "assistant" and msg.tool_calls:
                # Anthropic: assistant 的 tool_use 放在 content block 数组中
                blocks = []
                if msg.content:
                    blocks.append({"type": "text", "text": msg.content})
                for tc in msg.tool_calls:
                    blocks.append({
                        "type": "tool_use",
                        "id": tc["id"],
                        "name": tc["name"],
                        "input": tc["arguments"],
                    })
                result.append({"role": "assistant", "content": blocks})
            elif msg.role == "tool":
                # Anthropic: tool 结果用 role=user + tool_result block
                result.append({
                    "role": "user",
                    "content": [{
                        "type": "tool_result",
                        "tool_use_id": msg.tool_call_id,
                        "content": msg.content,
                    }],
                })
            else:
                result.append({"role": msg.role, "content": msg.content})
        
        return "\n\n".join(system_parts), result
    
    def _convert_tools(self, tools: list[dict]) -> list[dict]:
        """
        OpenAI function calling 格式 → Anthropic tool 格式
        OpenAI:  {"type": "function", "function": {"name": ..., "parameters": ...}}
        Anthropic: {"name": ..., "input_schema": ...}
        """
        return [
            {
                "name": t["function"]["name"],
                "description": t["function"].get("description", ""),
                "input_schema": t["function"]["parameters"],
            }
            for t in tools
        ]
```

**模型配置架构**：

模型配置由管理员通过 `llm_providers` 和 `llm_models` 两张表统一管理，聊天运行时自动使用 `is_default=True` 的模型。全局环境变量配置仅作为数据库中没有默认模型时的回退方案。

```
管理员 ──► llm_providers (供应商: name, provider_type, base_url, api_key)
           └─ llm_models (模型: name, model_name, is_default)
                                 │
聊天请求 ──► 查询 is_default ────┘
```

**不选 LiteLLM 的理由**：
- LiteLLM 的核心价值（统一多供应商 API）通过 Provider 抽象层 + `base_url` 已解决
- 自己写 Provider 层只有 ~200 行代码，但能完全掌控两套 API 的格式差异（如 Anthropic 的 system 独立参数、content block 数组、tool_result 格式等）
- LiteLLM 的依赖链较重，且其抽象层会掩盖各家模型的特有特性（如 Anthropic 的 extended thinking、OpenAI 的 response format 等）
- 调试自己写的 Provider 比调试 LiteLLM 的黑盒容易得多

### 2.2 数据验证 — `pydantic` + `pydantic-settings`

**选型**：Pydantic v2 用于所有数据结构的定义和验证。

**理由**：
- OpenAI / Anthropic SDK 的工具调用返回都是结构化数据，用 Pydantic 做类型安全校验
- `pydantic-settings` 处理配置文件的加载和环境变量覆盖，开箱即用
- 生成 JSON Schema 用于工具参数定义，与 OpenAI function calling 格式天然对齐

**使用场景**：

```python
from pydantic import BaseModel, Field
```

### 2.3 数据存储 — `SQLAlchemy 2.0` + `asyncpg` + `alembic` + `jieba`

**选型**：使用 PostgreSQL 作为统一数据存储，通过 `user_id` 字段 + **Row Level Security (RLS)** 实现双层多租户隔离。使用 SQLAlchemy 2.0 异步 ORM + asyncpg 驱动 + alembic 迁移。文本检索使用 PostgreSQL `tsvector` + jieba 中文分词。

**理由**：
- PostgreSQL 原生支持并发读写，多租户场景下性能优异（数百用户无压力）
- **Row Level Security (RLS)** 在数据库层面强制多租户隔离，比纯应用层过滤更可靠（即使代码有 bug 也不会泄漏数据）
- SQLAlchemy 2.0 异步模式与 FastAPI 的 async 特性完美匹配，类型安全的 ORM 减少 SQL 注入风险
- alembic 提供数据库迁移管理，Schema 变更可追踪、可回滚
- PostgreSQL `tsvector` + `ts_rank_cd` 提供内置全文检索，配合 jieba 中文分词效果好
- 支持 JSONB、数组、UUID 等丰富数据类型，减少序列化开销

**多租户数据隔离 — 双层防护**：

```
+----------------------------------------------------------+
|  第一层: 应用层过滤 (SQLAlchemy WHERE user_id = :uid)      |
|  Repository 基类自动注入 user_id 过滤条件                   |
|  v                                                        |
|  第二层: 数据库层 RLS (Row Level Security)                 |
|  PostgreSQL 强制: USING (user_id = app.current_user_id)   |
|  即使应用层代码有 bug，数据库层面也不会泄漏数据              |
+----------------------------------------------------------+
```

```python
async def get_db() -> AsyncSession:

        if user_id:

            await session.execute(
                text("SET LOCAL app.current_user_id = :uid"),
                {"uid": user_id}
            )

            await session.commit()
        except Exception:
            await session.rollback()
            raise
```

**多租户感知的记忆检索**：

```python
import jieba
from sqlalchemy import select, func

class MemoryRepository:
    """记忆数据访问 — 应用层过滤 + RLS 双层保障"""
    
    def __init__(self, db: AsyncSession):
        self.db = db
    
    async def get_l1_memories(self, user_id: uuid.UUID) -> list[Memory]:
        """获取当前用户的 L1 常驻记忆"""
        result = await self.db.execute(
            select(Memory)
            .where(Memory.user_id == user_id, Memory.layer == "L1")
            .order_by(Memory.created_at)
        )
        return list(result.scalars().all())
    
    async def search(self, user_id: uuid.UUID, query: str, top_k: int = 5) -> list[Memory]:
        """
        全文检索: jieba 中文分词 -> PostgreSQL tsvector @@ tsquery + ts_rank_cd 排序
        RLS 会自动附加 user_id 过滤，显式传入作为双保险
        """
        tokens = jieba.lcut(query)
        ts_query = " | ".join(tokens)  # OR 查询
        
        result = await self.db.execute(
            select(Memory)
            .where(
                Memory.user_id == user_id,
                Memory.search_vec.op("@@")(func.to_tsquery("simple", ts_query))
            )
            .order_by(
                func.ts_rank_cd(Memory.search_vec, func.to_tsquery("simple", ts_query)).desc()
            )
            .limit(top_k)
        )
        return list(result.scalars().all())
    
    async def create(self, user_id: uuid.UUID, layer: str, content: str, metadata: dict = {}) -> Memory:
        """写入记忆，自动生成 search_vec"""
        tokens = jieba.lcut(content)
        ts_vector_str = " ".join(tokens)
        
        memory = Memory(
            user_id=user_id,
            layer=layer,
            content=content,
            search_vec=func.to_tsvector("simple", ts_vector_str),
            metadata_=metadata,
        )
        self.db.add(memory)
        await self.db.flush()
        return memory
```

**SandboxManager 实现**：

```python
import docker
from docker.types import Mount
from pydantic import BaseModel
from datetime import datetime

class SandboxConfig(BaseModel):
    image: str = "aio-agent/sandbox:latest"
    cpu_limit: float = 1.0              # CPU 核心数
    memory_limit: str = "512m"          # 内存上限
    tmpfs_size: str = "512m"            # /tmp 大小
    network_disabled: bool = True       # 默认禁止网络
    command_timeout: int = 60           # 单次命令超时（秒）
    session_ttl: int = 3600             # 沙盒最大存活时间（秒）
    workspace_quota_mb: int = 500       # workspace 容量上限

class Sandbox:
    """单个沙盒容器的封装"""
    
    def __init__(self, container, user_id: str, session_id: str, created_at: datetime):
        self.container = container
        self.user_id = user_id
        self.session_id = session_id
        self.created_at = created_at
    
    def is_expired(self, ttl: int = 3600) -> bool:
        return (datetime.utcnow() - self.created_at).total_seconds() > ttl
    
    async def execute(self, command: str, timeout: int = 60, workdir: str = "/workspace") -> "ExecResult":
        """在容器内执行命令"""
        exec_result = self.container.exec_run(
            cmd=["bash", "-c", command],
            workdir=workdir,
            user="sandbox",
            stdout=True,
            stderr=True,
            demux=True,
        )
        stdout, stderr = exec_result.output
        return ExecResult(
            stdout=(stdout or b"").decode("utf-8", errors="replace"),
            stderr=(stderr or b"").decode("utf-8", errors="replace"),
            exit_code=exec_result.exit_code,
        )

class SandboxManager:
    """
    沙盒管理器 — 管理临时容器的创建、复用、销毁
    
    核心原则:
    1. 所有命令在容器内执行，绝不接触宿主机
    2. 容器用完即销毁（ephemeral）
    3. 用户 workspace 通过 Docker named volume 挂载
    4. 同一会话复用同一容器（保持 pip install 等状态）
    5. 不同用户/会话的容器完全隔离
    """
    
    def __init__(self, config: SandboxConfig):
        self.config = config
        self.docker = docker.from_env()
        self._active: dict[str, Sandbox] = {}   # key: "{user_id}:{session_id}"
    
    def _key(self, user_id: str, session_id: str) -> str:
        return f"{user_id}:{session_id}"
    
    async def get_or_create(self, user_id: str, session_id: str) -> Sandbox:
        """获取会话级沙盒，不存在则创建"""
        key = self._key(user_id, session_id)
        
        if key in self._active:
            sandbox = self._active[key]
            if not sandbox.is_expired(self.config.session_ttl):
                return sandbox
            await self.destroy(sandbox)
        
        sandbox = await self._create(user_id, session_id)
        self._active[key] = sandbox
        return sandbox
    
    async def _create(self, user_id: str, session_id: str) -> Sandbox:
        """创建临时容器"""
        volume_name = f"workspace_{user_id}"
        
        try:
            self.docker.volumes.get(volume_name)
        except docker.errors.NotFound:
            self.docker.volumes.create(name=volume_name)
        
        container = self.docker.containers.run(
            image=self.config.image,
            command="sleep infinity",
            detach=True,
            user="sandbox",
            read_only=True,                       # 根文件系统只读
            mounts=[
                Mount(target="/workspace", source=volume_name, type="volume"),
            ],
            tmpfs={"/tmp": f"size={self.config.tmpfs_size}"},
            mem_limit=self.config.memory_limit,
            cpu_quota=int(self.config.cpu_limit * 100000),
            network_disabled=self.config.network_disabled,
            security_opt=["no-new-privileges"],
            cap_drop=["ALL"],
            labels={
                "aio.user_id": user_id,
                "aio.session_id": session_id,
                "aio.ephemeral": "true",
            },
        )
        return Sandbox(container, user_id, session_id, datetime.utcnow())
    
    async def destroy(self, sandbox: Sandbox):
        """销毁沙盒容器（workspace volume 保留）"""
        try:
            sandbox.container.stop(timeout=5)
            sandbox.container.remove(force=True)
        except docker.errors.NotFound:
            pass
        key = self._key(sandbox.user_id, sandbox.session_id)
        self._active.pop(key, None)
    
    async def destroy_all_for_user(self, user_id: str):
        """销毁某用户的所有沙盒"""
        for key, sandbox in list(self._active.items()):
            if sandbox.user_id == user_id:
                await self.destroy(sandbox)
    
    async def cleanup_expired(self):
        """清理所有过期沙盒（由定时任务调用）"""
        for key, sandbox in list(self._active.items()):
            if sandbox.is_expired(self.config.session_ttl):
                await self.destroy(sandbox)
    
    async def shutdown(self):
        """平台关闭时销毁所有沙盒"""
        for sandbox in list(self._active.values()):
            await self.destroy(sandbox)
```

**工具执行引擎**：

```python
from pathlib import Path

class ToolExecutor:
    """统一的工具执行引擎 — 权限检查 + 路径安全 + 沙盒调度 + 输出控制"""
    
    MAX_OUTPUT_SIZE = 10_000
    DANGEROUS_COMMANDS = [
        "rm -rf /", "mkfs", "dd if=/dev/zero", ":(){ :|:& };:",
        "chmod -R 777 /", "wget|sh", "curl|sh",
    ]
    
    def __init__(self, registry, sandbox_mgr, audit_log):
        self.registry = registry
        self.sandbox_mgr = sandbox_mgr
        self.audit_log = audit_log
    
    async def execute(self, tool_name, args, ctx) -> ToolResult:
        tool = self.registry.get(tool_name)
        start = time.monotonic()
        
        # 1. 危险命令拦截
        if tool_name == "run_shell":
            self._check_dangerous_command(args.get("command", ""))
        
        # 2. 路径安全检查
        if tool.requires_sandbox and "path" in args:
            self._validate_path(args["path"])
        
        # 3. 沙盒执行 or 直接执行
        if tool.requires_sandbox:
            sandbox = await self.sandbox_mgr.get_or_create(ctx.user_id, ctx.session_id)
            result = await self._execute_in_sandbox(sandbox, tool_name, args)
        else:
            result = await tool.execute(**args, context=ctx)
        
        # 4. 输出截断
        output = self._truncate(str(result.output))
        
        # 5. 审计日志
        duration_ms = (time.monotonic() - start) * 1000
        self.audit_log.record(
            user_id=ctx.user_id, session_id=ctx.session_id,
            tool=tool_name, args=args, success=result.success, duration_ms=duration_ms,
        )
        
        return ToolResult(output=output, success=result.success, duration_ms=duration_ms)
    
    def _validate_path(self, path: str):
        """防止路径穿越"""
        normalized = Path("/workspace", path).resolve()
        if not str(normalized).startswith("/workspace"):
            raise SecurityError(f"Path traversal blocked: {path}")
    
    def _check_dangerous_command(self, command: str):
        cmd_lower = command.lower().strip()
        for pattern in self.DANGEROUS_COMMANDS:
            if pattern in cmd_lower:
                raise SecurityError(f"Dangerous command blocked: {pattern}")
    
    def _truncate(self, output: str) -> str:
        if len(output) > self.MAX_OUTPUT_SIZE:
            return output[:self.MAX_OUTPUT_SIZE] + f"\n\n... [输出已截断，共 {len(output)} 字符]"
        return output
```

```python
# ## 你需要记住的关于用户的信息
# {% for memory in persistent_memories %}
# - {{ memory.content }}
# {% endfor %}
# {% endif %}
#
# {% if relevant_skills %}
# ## 可能相关的经验
# {% for skill in relevant_skills %}
# ### {{ skill.name }}
# {{ skill.description }}
# {% endfor %}
# {% endif %}
#
# 当前时间: {{ current_datetime }}
# """

template = env.get_template("system_prompt.j2")
system_prompt = template.render(
    soul_content=soul_content,
    persistent_memories=l1_memories,
    relevant_skills=matched_skills,
    current_datetime=datetime.now().isoformat()

```

## 3. 前端技术栈

### 3.1 框架与构建 — `React 18` + `Vite` + `TypeScript`

**选型**：React 18 作为 UI 框架，Vite 作为构建工具，TypeScript 作为开发语言。

**理由**：
- React 生态最成熟，组件库和社区资源丰富
- Vite 构建速度极快（基于 ESM），HMR 毫秒级响应
- TypeScript 提供类型安全，与后端 Pydantic 模型对齐，前后端接口不易出错

**不选其他框架的理由**：
- **Next.js**：SSR/SSG 对 Agent 管理面板是 overkill，我们只需要 SPA
- **Vue / Svelte**：生态成熟度不如 React，shadcn/ui 等高质量组件库以 React 为主
- **CRA (Create React App)**：已被官方废弃，Vite 是事实标准

### 3.2 样式方案 — `Tailwind CSS` + `shadcn/ui`

**选型**：Tailwind CSS 做原子化样式，shadcn/ui 提供高质量组件。

**理由**：
- Tailwind 的 utility-first 方式开发效率高，无需维护 CSS 文件
- shadcn/ui 不是传统组件库（不需要 npm install），而是直接拷贝组件源码到项目中
- shadcn/ui 基于 Radix UI（无头组件），无障碍支持好，样式完全可定制
- 暗色/亮色主题切换开箱即用
- 与 Agent 管理面板的「专业工具」气质匹配

**使用的 shadcn/ui 组件**：

|------|------|
| `Dialog` | 确认弹窗、配置弹窗 |
| `Sheet` | 侧边面板（会话列表、记忆详情） |
| `Tabs` | 记忆层级切换、技能分类 |

### 3.4 状态管理 — `Zustand`

**选型**：Zustand 做全局状态管理。

**理由**：
- 极轻量（~1KB），API 极简
- 不需要 Provider 包裹，直接使用 hook
- 支持 persist 中间件，状态可持久化到 localStorage
- 比 Redux 简单，比 Context 性能好（自动细粒度订阅）

**不选其他方案的理由**：
- **Redux Toolkit**：对 Agent 管理面板的复杂度来说太重了
- **Jotai**：原子化状态在跨组件联动时不如 Zustand 直观
- **React Context**：更新时会触发所有消费者重渲染，性能差

### 3.5 WebSocket 通信 — 原生 `WebSocket` + 自定义 Hook

**选型**：使用浏览器原生 WebSocket API，封装为 React Hook。

**理由**：
- 原生 API 足够简单，不需要 Socket.io 等额外依赖
- 后端 FastAPI 的 WebSocket 实现也是标准协议，无需特殊客户端
- 封装为 Hook 后可复用连接管理、重连、心跳等逻辑

**不选 Socket.io 的理由**：
- Socket.io 提供自动重连、房间管理等高级功能，但对我们的场景过重
- 它是私有协议，不是标准 WebSocket，增加了后端耦合
- 我们自己实现重连逻辑只需 ~20 行代码

**WebSocket 消息协议**：

## 5. 不使用的技术（及理由）

### 后端

| 技术 | 不用的理由 |
|------|-----------|
| **LiteLLM** | 自写 Provider 抽象层（~200 行）即可统一 OpenAI + Anthropic，不需要额外适配层 |
| **LangChain** | 框架过重，抽象层太多，调试困难；我们的 Agent Loop 自己实现更可控 |
| **LangGraph** | 图状态机对 ReAct 循环是 overkill，增加复杂度但不带来对应价值 |
| **CrewAI / AutoGen** | 多 Agent 编排框架，本项目单 Agent 足够，未来扩展时再考虑 |
| **Redis** | 当前规模无需内存级缓存，PostgreSQL 查询性能足够；高并发场景可引入 |
| **SQLite** | 不支持并发写入，无 RLS，无法满足多租户隔离需求 |
| **Docker (运行时)** | Agent 本身不依赖 Docker 运行；Docker 仅作为代码沙箱的可选方案 |
| **Celery** | 分布式任务队列，对单进程 Agent 过重，APScheduler 足够 |
| **raw SQL (asyncpg only)** | 无 ORM 层则缺少迁移管理、类型映射、关系管理；多租户 Schema 复杂度需要 ORM |
| **ChromaDB (当前)** | 初期记忆量小，BM25 文本检索足够；后续可通过预留接口无缝引入 |
| **sentence-transformers** | 避免安装 PyTorch / ONNX 等重量级依赖；当前阶段不需要 Embedding |

### 前端

| 技术 | 不用的理由 |
|------|-----------|
| **Next.js** | Agent 管理面板是纯 SPA，不需要 SSR/SSG，Vite SPA 足够且更简单 |
| **Redux / Redux Toolkit** | 对当前状态管理复杂度来说太重，Zustand 更轻量 |
| **Socket.io** | 标准 WebSocket 已足够，Socket.io 是私有协议，增加后端耦合 |
| **axios** | 基于 XMLHttpRequest，体积更大，ky（基于 fetch）更现代更轻量 |
| **Ant Design** | 组件风格偏企业管理后台，shadcn/ui 更现代且完全可定制 |
| **MUI (Material UI)** | 包体积大，样式定制不如 shadcn/ui 灵活 |

## 9. 关键架构决策记录 (ADR)

### ADR-001: 双 SDK (OpenAI + Anthropic) + Provider 抽象层

- **状态**：已决定
- **决策**：同时使用 `openai` 和 `anthropic` 两个官方 SDK，通过自写的 Provider 抽象层（~200 行代码）统一上层调用
- **理由**：
  - OpenAI 兼容接口已是事实标准，`base_url` 可接入 DeepSeek / OpenRouter / Ollama 等
  - Anthropic 的 Messages API 格式有本质差异（system 独立参数、content block 数组、tool_use/tool_result block），无法通过 `base_url` 兼容
  - 两套原生 SDK 能第一时间利用各家新特性（如 Anthropic extended thinking、OpenAI response format）
- **代价**：需要维护 Provider 抽象层，两套 API 的格式转换逻辑需要自己处理
- **替代方案**：LiteLLM 可以统一两套 API，但额外抽象层会掩盖差异特性，且调试困难

### ADR-002: 文本检索优先，后续可升级向量检索

- **状态**：已决定
- **决策**：当前阶段使用 PostgreSQL tsvector + jieba + ts_rank_cd 做全文检索，不引入向量数据库
- **理由**：
  - 初期记忆数据量小（< 1000 条），文本检索效果足够
  - 零额外依赖，避免引入 onnxruntime 等重量级包（ChromaDB 间接依赖 ~500MB）
  - 已预留 `SearchBackend` 抽象接口，后续引入 ChromaDB 只需实现 `VectorSearchBackend`
- **代价**：无法做语义检索（如 "汽车" 搜不到 "轿车"），但在记忆量小时影响有限

### ADR-003: PostgreSQL 而非 SQLite

- **状态**：已决定
- **决策**：使用 PostgreSQL 作为主数据库，配合 SQLAlchemy 2.0 异步 ORM + asyncpg 驱动 + alembic 迁移
- **理由**：
  - PostgreSQL 原生支持并发读写，多租户场景下性能优异
  - **Row Level Security (RLS)** 在数据库层面强制多租户隔离，即使应用层代码有 bug 也不会泄漏数据
  - 丰富的数据类型（UUID、JSONB、TSVECTOR、数组）减少序列化开销
  - alembic 提供 Schema 迁移管理，变更可追踪、可回滚
  - 原生支持 tsvector 全文检索 + GIN 索引，配合 jieba 中文分词效果好
- **代价**：需要额外部署 PostgreSQL 服务（可通过 Docker Compose 一键启动）
- **替代方案**：SQLite 虽然零运维，但不支持并发写入、无 RLS、无原生全文检索，无法满足多租户平台需求

### ADR-004: 自实现 Agent Loop 而非使用 LangGraph

- **状态**：已决定
- **决策**：自己实现 ReAct 循环，不依赖 LangGraph 等编排框架
- **理由**：ReAct 循环逻辑清晰（~200 行代码），LangGraph 的状态机抽象增加了理解成本但不带来对应价值
- **代价**：需要自己处理循环控制、超时、错误恢复等边界情况

### ADR-005: React SPA 而非 Next.js

- **状态**：已决定
- **决策**：使用 Vite + React SPA，不使用 Next.js
- **理由**：Agent 管理面板是纯客户端应用，不需要 SSR/SSG；Vite SPA 更简单、构建更快
- **代价**：无 SEO 能力（管理面板不需要 SEO）

### ADR-006: shadcn/ui 而非 Ant Design / MUI

- **状态**：已决定
- **决策**：使用 shadcn/ui（基于 Radix UI）作为组件方案
- **理由**：
  - 组件源码直接拷贝到项目中，完全可定制
  - 基于 Tailwind CSS，与样式方案统一
  - 包体积更小（只引入使用的组件）
  - 暗色主题开箱即用
- **代价**：组件数量不如 Ant Design 丰富，缺少的组件需要自己写

### ADR-007: 共享数据库 + user_id 行级隔离

- **状态**：已决定
- **决策**：所有租户共享同一个 PostgreSQL 数据库，通过 `user_id` 字段 + **Row Level Security (RLS)** 实现双层数据隔离
- **理由**：
  - 简单高效，无需管理多个数据库实例
  - PostgreSQL 提供 RLS，即使应用层代码有 bug 也不会泄漏跨租户数据
  - 通过 `TenantRepository` 基类统一注入 `user_id` 过滤，从架构层面防止数据泄漏
  - 管理员可通过不带 `user_id` 过滤的查询查看所有数据（运维需求）
- **代价**：
  - 需要在每个 Repository 方法中确保 `user_id` 过滤（通过基类强制）
  - 如果某个租户数据量特别大，可能影响其他租户的查询性能（中小规模下影响可忽略）
- **替代方案**：
  - 每租户独立数据库：隔离性更强，但管理复杂（连接池、迁移、备份），当前规模不需要
  - 纯应用层过滤（无 RLS）：实现更简单，但缺少数据库层面的兜底保护

### ADR-008: JWT 无状态认证

- **状态**：已决定
- **决策**：使用 JWT（access_token + refresh_token）进行用户认证
- **理由**：
  - 无状态，服务端不需要维护 session 存储
  - access_token 短效（15 分钟），refresh_token 长效（7 天），兼顾安全和体验
  - Token 中包含 `user_id` 和 `role`，FastAPI Depends 可直接提取
  - 天然适合 SPA 前后端分离架构
- **代价**：
  - JWT 签发后无法主动失效（除非引入黑名单机制）
  - refresh_token 需要数据库存储以支持主动吊销

### ADR-009: 强制沙盒执行 — 所有命令在临时 Docker 容器中运行

- **状态**：已决定
- **决策**：所有涉及文件操作和命令执行的工具强制在临时 Docker 容器中执行，容器用完即销毁，绝不接触宿主机
- **理由**：
  - **安全性**：Agent 执行的命令由 LLM 生成，无法保证安全；沙盒确保即使命令恶意也不会影响宿主机
  - **多租户隔离**：每个用户/会话有独立容器，进程级隔离比文件系统权限更可靠
  - **环境一致性**：所有用户使用相同的沙盒镜像，避免"在我机器上能跑"的问题
  - **资源控制**：Docker 原生支持 CPU/内存/网络限制，防止单个用户耗尽平台资源
  - **清洁性**：容器用完销毁，不留下任何临时文件或副作用
- **代价**：
  - 沙盒创建有 ~1-3 秒延迟（使用预拉取镜像可降至 < 1 秒）
  - 需要宿主机安装 Docker
  - 沙盒容器消耗额外的 CPU/内存资源
  - 沙盒内无网络访问（默认配置），某些需要网络的工具受限
- **替代方案**：
  - gVisor：更强的系统调用隔离，但部署复杂，当前 Docker 安全配置已足够
  - Firecracker microVM：隔离性最好，但启动慢、运维复杂
  - 本地执行 + 文件权限：最简单，但安全性不足，多租户场景下风险大
